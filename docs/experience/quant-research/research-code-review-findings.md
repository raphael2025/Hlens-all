# 研究代码 review：真实发现的问题与可复用的检查项

研究代码有一个特殊处境：它的输出是**数字**，而数字看起来永远是对的。一个 bug 不会让程序崩溃，它会让你得到一条略微不同的资金曲线——然后你据此做决策。

这份文档记录一次对某个量化研究代码库的静态 review 中真实发现的问题，以及从中提炼出的检查项。绝大多数条目与具体策略无关，适用于任何"pandas + 特征 + 回测"形态的代码库。

---

## 一、最严重的一条元观察

review 的最大发现不是任何单个 bug，而是这个代码库**缺少的实践**：

1. **没有单元测试**（grep 不到任何测试文件）；
2. 类型标注只有部分函数有；
3. **没有 CI**，所以这些问题不会被自动发现；
4. **没有任何 code review 记录**——那次 review 本身是第一次。

> 一个没有测试的研究代码库，它输出的每一个数字都只有"作者当时觉得对"这一层保障。

补救的起点很低：先给最基础的工具函数和核心打分函数写行为测试，覆盖关键不变量，几十个测试就能挡住绝大多数回归。

---

## 二、NaN 填 0 会让其他特征的贡献被放大

**问题代码**（加权求和多个特征）：

```python
vals = pd.to_numeric(out[col], errors="coerce") \
         .replace([np.inf, -np.inf], np.nan) \
         .fillna(0.0)
raw += float(weight) * vals.to_numpy()
```

**为什么错**：在一个已经中心化的特征上，`0` **不是"无信号"，而是"中位信号"**。把缺失值填成 0 再乘权重加进去，相当于断言"这个特征此刻处在中性位置"——这是一个具体的、可能错误的断言，不是一个中立的占位。

后果是在某个特征缺失的那些 bar 上，**其他特征的相对贡献被系统性放大**。六特征等权时，一个特征缺失就是约 0.17 的权重偏移；长期累积会让信号整体漂移。

**修法**：不填 0，让缺失的那一项不参与求和：

```python
vals = pd.to_numeric(out[col], errors="coerce").replace([np.inf, -np.inf], np.nan)
raw += np.where(np.isnan(vals), 0.0, weight * vals)
```

注意两段代码在数值上很像，区别在于**权重是否被计入分母/是否被当作"观测到了中性值"**。这类 bug 在 review 时最容易被眼睛滑过去。

**更一般的检查项**：代码库里每一处 `fillna(0)` 都应当有一行注释回答"0 在这个量纲下是什么意思"。答不上来就是 bug。

## 三、文档说的和代码做的不是一回事（死代码方向字段）

配置里有一个 `direction: -1.0`，项目记忆文档里写着"这是一个做空 alpha"。

实际代码路径：

```python
out["alpha_signal"] = float(cfg["direction"]) * out["alpha_raw_score"]
out["alpha_side"]   = np.where(out["alpha_signal"] > 0, "long", "short")
out["alpha_abs_signal"] = out["alpha_signal"].abs()
```

而下游的信号选择函数**只用绝对值**：按 `alpha_abs_signal` 的分位数取阈值，选出绝对值最大的若干条。

于是 `direction` **对选择完全没有影响**，选出来的信号有多有空。代码实际在做双向交易，而文档说它在做空。

> 这不是一个"多余的字段"，它是一个**文档与实现的语义漂移**。如果仓位应该是 100% 做空还是 50/50，对资金的影响是完全不同的。

**检查项**：任何一个配置字段，如果删掉它之后行为不变，它就要么是死代码（删）要么是没接上的意图（修）。不允许第三种状态。同理，项目记忆/README 里关于"这个策略在做什么"的描述，应该有一个测试或一次实际运行的交易方向分布来印证。

## 四、切分前的 `dropna` 会系统性删除尾部

```python
df = pd.read_parquet(...).sort_values("bucket")
data = df.dropna(subset=factor_cols + [args.target]).copy()
```

`dropna` 本身不引入未来信息，但目标列是前瞻收益（`shift(-h)` 得到的），因此序列末尾的 h 根 bar 的目标必然是 NaN，整行被删。

后果有两层：

1. **最新的 h 根数据永远不在训练集里**；
2. 如果实盘脚本复用了同一段"特征构造 + dropna"逻辑，那么**实盘也会拒绝使用最新的 h 根数据**——而实盘根本不需要前瞻标签。

**修法**：把"训练用 target"与"实盘用 feature"的过滤逻辑拆开；实盘路径不得因为前瞻列为 NaN 而丢行。

（这一条同时属于泄漏面清点的范畴，详见《Point-in-Time 数据契约与泄漏面清点》。）

## 五、同一个工具函数在两个文件里各写了一份

两个模块各自定义了一个字节级完全相同的安全 z-score 函数。这类重复的危害不是当下，而是**未来**：某天有人在其中一处把窗口或 `ddof` 改了，两条管道会安静地分叉，而两边的数字仍然"看起来正常"。

**检查项**：任何被复制到第二个文件里的数值函数，立刻提取到共享模块。研究代码里最值得去重的正是这类"看起来很小"的函数——因为它们被所有下游数字依赖。

## 六、性能 bug 也会改变研究结论（O(N²) → O(N)）

一个滑动窗口比值的实现，每次调用都遍历整个双端队列：

```python
def ratio(self, symbol, now_ms):
    buf = self._flows[symbol]
    cutoff = now_ms - self.window_ms
    signed = total = 0.0
    for ts, s, t in buf:          # ← 每次调用都遍历整个 deque
        if ts >= cutoff:
            signed += s
            total  += t
    return signed / total if total else 0.0
```

deque 的 `maxlen` 是二十万，而这个函数每秒被调用一次。复杂度是 O(N × W)。

**修法**是标准的运行和 + 左端过期：

```python
def on_trade(self, trade):
    signed = trade.notional if not trade.is_buyer_maker else -trade.notional
    self._flows[trade.symbol].append((trade.ts_ms, signed, trade.notional))
    self._signed_sum[trade.symbol] += signed
    self._total_sum[trade.symbol]  += trade.notional

def ratio(self, symbol, now_ms):
    buf = self._flows[symbol]
    cutoff = now_ms - self.window_ms
    while buf and buf[0][0] < cutoff:      # 只从左端过期
        _, s, t = buf.popleft()
        self._signed_sum[symbol] -= s
        self._total_sum[symbol]  -= t
    total = self._total_sum[symbol]
    return self._signed_sum[symbol] / total if total > 0 else 0.0
```

整体复杂度降到 O(N)（每笔成交进出队列各一次）。实测单次回测从三十余秒降到零点几秒，约 **260 倍**。内存同时改善：队列稳定在"窗口长度 × 成交率"而不是顶着上限。

**为什么这属于研究问题而不只是工程问题**：一次回测三十秒意味着参数扫描、bootstrap、walk-forward 全部变得不可行。**跑得慢的验证 = 不会被跑的验证。** 性能直接决定了你的研究纪律上限。

顺带一个好习惯：这个修改的公开接口完全不变，且在稳态下行为等价（实测同样的信号、同样的 PnL）——**先证明等价，再替换**。

## 七、合成数据上的漂亮结果几乎总是生成器的假象

一条微观结构信号在**合成数据**上胜率接近 100%；在**真实数据重放**上，各种阈值下胜率都被钉在三成多，全部配置亏钱。

根因很直接：合成数据生成器里嵌入了一个前向信号（"某个失衡条件出现后的若干秒内价格朝某方向漂移并延续"）。真实市场里这个链条不存在——失衡在几十到几百毫秒内被吃掉，没有持续性；而且因果方向反了，是价格变动造成了失衡，不是失衡预测了价格。

**四条可复用的结论**：

1. **合成数据会骗人**：即使噪声看起来很真实，嵌入的前向信号也会造出接近 100% 的胜率；
2. 粗糙的**真实数据代理**（例如用 K 线近似）给出的平庸数字，反而是诚实的；
3. **真实高频数据重放是唯一有意义的验收**；
4. **调阈值救不了错误的假设**：十几个配置全部亏钱，说明问题不是参数没调好。

> 合成数据只能用来测代码逻辑（会不会崩、边界条件对不对），不能用来评估策略是否有效。

## 八、把异常吞成"正常结束"

```python
except asyncio.TimeoutError:
    break
```

在较新的 Python 里 `asyncio.TimeoutError` 就是内建的 `TimeoutError`。于是"长时间没有任何数据"被当成正常收尾，错误列表为空、重连次数为零。一个需要调查的异常状态，被记录成了"正常但没数据"。

**检查项**：任何 `except ...: break` / `except ...: pass` / `except ...: continue` 都要回答一句"被吞掉的这个状态，在下游还能被看见吗"。看不见就要显式记录成一条**正向的**事件，而不是沉默。

---

## 九、失败要被记录，不能静默回退

一条从评审闸里来的要求：当某个模型族的**所有候选都失败**时，必须显式记录这次族级失败，**不允许静默跳过后回退到第一个配置**。

静默回退制造的是最糟糕的一类结果：报告里有一行数字、看起来是这个模型族的表现，而实际上那是一个从未被选中的默认配置。

## 十、NaN 策略要"失败关闭"

一个很优雅的设计约定，值得推广：**两类条件用相反的 NaN 策略，但都解析到"空仓"**。

- 入场条件无法求值（NaN）→ **拒绝许可**（fail closed）；
- 退出条件无法求值（NaN）→ **执行退出**（fail open 到退出）。

> 一台"失败即关闭"的机器，没法把自己说服进一个仓位里。

并且这条有专门的测试钉住（`test_nan_policy_fails_closed_on_entry_and_open_on_exit` 这类命名本身就是文档）。

## 十一、新增能力必须默认是 no-op，并用逐位 parity 测试保护

在一个已有基线的引擎上加新功能时的做法：

- 每一个新增参数**默认值就是"什么都不做"**；
- 有一个测试断言"全部新参数取默认值时，引擎输出与加功能之前**逐位相同**"；
- 另有一个针对历史基线结果的 parity 测试始终保持通过。

这样"新功能引入了回归"和"新功能确实改变了行为"这两件事可以被机械地区分开。**只有一套引擎**：基线和所有被搜索的变体走完全相同的成交语义，所以两者之间的比较是条件的比较，而不是引擎实现差异的比较。

## 十二、区分"实现 bug"与"判据设计 bug"

一个实际案例：某个合理性检查闸要求"风控层开启后的年化波动率必须落在目标波动率附近"。某次实验里这个闸失败了，判决自动变成"拒绝"。

排查后发现：风控层的数学完全正确（它按公式把仓位缩放到目标波动率），失败的原因是**输入信号的平均幅度太小**，缩放之后自然达不到目标波动率。

> 这是一个**闸设计 bug**，不是实现 bug。闸的写法隐含假设了"输入信号幅度足够大"。

处理方式：把这个区别写进实验记录，把"按原判据的裁决"和"修正判据后的裁决"分别列出，并明确说明判据尚未在代码里修复以及为什么（修它需要先定义"低幅度信号的合理性是什么"）。**没有当场改判据**——在看到结果之后改判据，正是预注册要防的那件事。

## 十三、研究档案仓的卫生（交接与审计用）

最后一组，关于"研究代码最终怎么交出去"：

- **README 写清楚"没包含什么以及为什么"**：没有数据库、没有大体积原始数据、没有服务器凭据——这些只记录本地路径，不上传。
- **维护一份被拒方案日志**：`某某方向：已拒绝，样本外表现差`。被拒记录和被采纳记录同等重要。
- **明确的使用边界声明**：所有结果只能作为研究线索，上真钱前必须重做样本外验证、成本与滑点压测、风控、小额干跑。
- **安全说明单独成文**：配置里的密码/密钥一律替换成占位符；部署脚本从环境变量读凭据；**任何曾经出现在聊天窗口或终端历史里的 token 都当作已泄露，直接撤销重发**。
- **raw 会话日志 / agent 转录不要进档案仓**：它们体积大、对读者无价值，而且是最容易漏过密钥清理的文件类型——关键字扫描通常只扫配置文件，会跳过 shell 历史这类文件。
- 配一个**防御性的忽略规则 + 推送前自检**，并在文档里写明"这些模式是防御性排除，推送前请确认确实不存在"。

## 十四、检查清单

对任何研究代码库做 review 时按这张表走：

- [ ] 有没有测试？有没有 CI？没有就先写最基础的不变量测试
- [ ] 每处 `fillna(0)` 都能回答"0 在这个量纲下是什么意思"
- [ ] 每个配置字段都影响行为；删掉会改变结果
- [ ] 文档/记忆里关于"这个策略在做什么"的描述，有运行证据印证
- [ ] 切分前的行级过滤审过，没有系统性删除尾部
- [ ] 没有被复制到第二个文件里的数值函数
- [ ] 热路径没有 O(N²)；验证跑得动才会被跑
- [ ] 任何"异常漂亮"的结果先当 bug 查（尤其来自合成数据）
- [ ] 没有把异常吞成正常结束的 except 分支
- [ ] 族级/批量失败被显式记录，而不是静默回退到默认值
- [ ] NaN 策略明确，且方向是"失败关闭"
- [ ] 新增能力默认 no-op，有逐位 parity 测试
- [ ] 判据失败时，区分清楚是实现错了还是判据设计错了——并且**不在看到结果之后改判据**
