# 行情数据记录器的工程坑（交易所公开接口实测）

这份文档来自一个专门的项目：为某主流交易所的 USDⓈ-M 永续合约做一个**只读公开市场数据记录器**。项目的固定范围是"只用公开数据、不使用 API Key、不接账户数据、不具备任何下单能力"，所以这里没有任何策略内容——全是采集侧的工程事实。

下面每一条都是实测踩到的，不是文档转述。

---

## 一、最贵的一条：订阅成功 ≠ 这个流会推数据

第一轮探测里，有三类 WebSocket 流在 **15 分钟内零消息**，同时：

- 连接成功建立，零异常、零重连；
- 服务端对 `SUBSCRIBE` 返回成功，`LIST_SUBSCRIPTIONS` 确认订阅**在册**；
- 同一时段另外两个流正常收到数万条消息——**市场是活跃的，不是静默**。

当时的判定是 `UNDETERMINED`，并猜测"可能与网络位置相关"，据此把"换记录主机"的优先级抬高了。

**第二轮重测查明了真正的根因：连接 URL 用的是已废弃的未路由端点。** 该交易所把公开流拆到了不同的路由路径下（高频公开流一条路径、常规行情流另一条路径），而**未路由的连接只会收到第一类数据**。零推送的那三类恰好全在第二类里，收到数据的两类恰好全在第一类里，无一例外。

更有价值的是**反向受控复现**：把一个本属于第一类的流故意订到第二类路径上——订阅回执照样返回成功、照样在册、**零消息**。异常签名完全一致，而且是主动制造出来的。

### 1.1 教训不是"用错了 URL"

真正的教训是：**探测器没有对"订阅成功 + 零数据"做出正向判定，它把这个状态记成了沉默。**

代码长这样：

```python
except asyncio.TimeoutError:
    break
```

在较新的 Python 里 `asyncio.TimeoutError` 就是内建的 `TimeoutError`。于是"长时间收不到任何消息"被当成正常收尾，`errors` 为空、`reconnects` 为 0。三个零消息流看起来像"正常但没数据"，而不是"需要调查的异常"。

> **未被记录下来的缺失，等于不存在的缺失。**

### 1.2 对记录器的强制要求

每个订阅流必须有：

- 独立的 `last_message_at` 水位；
- 一个**逐流设定**的"预期最大静默期"；
- 超过阈值时发出**正向的** gap 事件（我们定义了一个 `SUBSCRIBED_BUT_SILENT` 的 kind）。

阈值必须逐流设定：最活跃的报价流静默 20 秒是异常，而一个"仅在合约信息变更时推送"的事件流静默 30 天是完全正常的。用一个全局阈值会同时产生大量误报和漏报。

## 二、完整性要分级，不能一句"数据完整"带过

不同的流提供的缺口原语强度完全不同，必须在 schema、UI 和研究报告里都保留这个区别。我们定义了三档：

| 等级 | 含义 | 典型 |
|---|---|---|
| `PROVABLE` | 有逐一递增的序号，能证明没丢消息 | 聚合成交流（`a` 逐一递增）；订单簿增量流（`pu` 链式指向前一条的 `u`） |
| `SCHEDULE_BOUNDED` | 没有序号，但有可预期的推送节奏 | 定期推送的标记价格、轮询类端点 |
| `OBSERVATIONAL_ONLY` | 只能证明顺序，不能证明完整 | 最优买卖报价流 |

### 2.1 单调 ≠ 计数器（这一条推翻了我们之前的结论）

早期文档里写着"最优报价流的 `u` 字段单调递增，所以完整性可证"。实测发现：**`u` 是订单簿的全局更新 ID，不是这条流自己的计数器**——相邻消息的差值等于 1 的比例只有百分之几。

结论修正为：**顺序可证、完整性不可证**。这条流恰好是整套方案里体积最大的流，也就是说数据量最大的那条流反而无法证明没丢包。

> 检查一个 ID 字段到底是"本流计数器"还是"全局序号"的最简单办法：统计相邻消息 ID 差值等于 1 的比例。接近 100% 才是计数器。

### 2.2 采样流不是完整流

有一类强平/清算事件流，官方文档写明：**每个标的在任意 1000ms 窗口内只推送"最大的那一笔"**，其余全部丢弃且不可恢复。

这意味着：

1. 它不是完整清算流，而是**按规模取最大值的抽样流**；
2. 抽样丢失在清算最密集的时候最严重——也就是说，**缺失与你最关心的变量强相关**（与统计上的 MNAR 同构）；
3. 没有任何公开历史端点，不实时记录即永久丢失。

把这种流当成"清算全貌"去做热力图，是在一个系统性偏斜的样本上建模。记录阶段的约束因此写成：**只记录原始 payload 与必要元数据，不在记录器里生成热力图、估算持仓或估算清算价**——把估算写进 Recorder 会让"数据"和"模型"在事后无法分离。

## 三、字段语义必须逐流解析，禁止全局假设

一个实测细节：某个标记价格流的 `T` 字段**不是事务时刻，而是下一次资金费结算时间**，而其他流的同名字段是事件/成交时刻。

> **禁止"一个字段名在全系统只有一个含义"的假设。** 每条流的时间/序号字段都要单独解析、单独写进 golden vector。

同类的一条：某些配置参数必须**从 API 读取而不是假设**。资金费的结算周期常被默认成 8 小时；实测确认当前确实是 8 小时，但这个值**必须持续记录**，因为它会变。写死成常数的那一刻，你的历史数据就开始悄悄失真了。

---

## 四、历史墙与不可逆性

这一条对"要不要现在就开始采"这个决策有决定性影响：

- 部分端点（K 线、资金费结算历史、标记价/指数价 K 线）可以回溯到合约上市日；
- 逐笔成交可以按**时间窗**回补一年以上，且不需要凭据（我们最初以为回补不可得，是因为只试了按 ID 回补的那条路径，而那条路径需要凭据）；
- 但另一类"持仓量历史 / 多空比 / 大户持仓比 / taker 买卖比"的统计端点，**只有 30 天历史**（回看 40 天直接返回参数错误）；
- 最优报价流、订单簿增量流、清算事件流**完全没有历史端点**。

> **有历史墙的数据源，"不采"就是一个不可逆决策。** 这类项目必须把"哪些数据不采就永久丢失"单独列一张表，并作为一个需要显式拍板的决策项，而不是让它悄悄地默认为"以后再说"。

配套的一条纪律：**不要用 A 冒充 B**。不要用 REST 轮询顶替 WS 流并当作等价，不要用聚合成交冒充逐笔成交，不要用历史统计端点冒充实时值。需要降级时，降级本身必须是一条显式记录在案的决策，附带轮询计划，而不是悄悄替换。

---

## 五、需要凭据的只读端点

在"不使用 API Key"的范围下扫了 25 个公开端点，23 个可用。两个返回 401：一个是逐笔成交的按 ID 深度回补，一个是杠杆档位/维持保证金率分档表。

这两个的处理方式值得说明：

- 它们的状态记为 `BLOCKED`（因本项目自设的范围约束而不可得），**不是 `UNAVAILABLE`**（能力不存在）；
- 缺失的后果要写清楚：分档保证金表拿不到，意味着清算价距离建模在执行阶段会受影响；合约元数据里虽然有单一的维持保证金率和清算费率，但那**不是完整的分档表**，不能拿来顶替；
- 401 的响应体本身要归档——它是"我们确实试过、确实需要凭据"的证据。

## 六、限流观测

- 权重头（`x-mbx-used-weight-*`）正常返回，单轮几十次调用的累积权重可以直接读出来；
- **但不是所有子服务都返回权重头**——那组统计类端点属于不同的服务路径，完全不返回权重头，也就是说它们的限流规则**不可观测**，只能靠保守轮询和错误率反推；
- 单轮扫描**无法估计**持续轮询下触及限流的频率。想知道这个，只能做长时间试点。

---

## 七、主机时钟：这是整个项目最意外的发现

用持久连接重测时钟偏差时出现矛盾：**RTT 稳定到 5ms 以内，而偏差估计在同一批样本内摆动 183ms。** 网络解释不了这个差距。

于是做了一次纯本地诊断（完全不涉网）：对比 `CLOCK_REALTIME` 与 `CLOCK_MONOTONIC` 的分歧，150 秒、0.5 秒采样。结果：

- 检出 4 次阶跃，**幅度中位数约 −1,020 ms**；
- **阶跃间隔中位数约 32 秒**，恰好等于时间同步守护进程的轮询周期；
- 阶跃之间两个时钟的分歧**精确为 0**；
- 推算出的主机时基增益约 **+3.17%**。

机制：这台虚拟机的时基比真实时间快约 3%。时间同步守护进程能做的频率修正上限只有百万分之几十，差了两个多数量级，因此它**无法平滑校正，只能每次轮询就把墙钟硬回拨约一秒**。

### 7.1 后果

1. **墙钟每 32 秒倒退约 1 秒。** 用墙钟排序的记录器每天会产生数千次乱序。
2. 本机上**一切亚秒级的延迟解读全部失效**，包括之前所有报告里的延迟数字。
3. 同时记录单调时钟（`recv_mono_ns`）不是冗余，而是**唯一可靠的本地时基**。
4. NTP 偏移量必须来自同步守护进程本身，**不能**用与交易所的往返时间推算。
5. **时钟阶跃必须作为运维事件被记录。** 一个每 32 秒触发一次的时钟阶跃事件，本身就是"这台主机不合格"的信号。

### 7.2 记录主机的验收标准

从这次诊断直接推导出来的：候选主机必须通过**连续 ≥ 1 小时的 `CLOCK_REALTIME` vs `CLOCK_MONOTONIC` 轨迹检查，零阶跃**，并且 NTP 守护进程报告的频率修正在正常范围内。这个检查很便宜（一个小脚本），但能在你写下第一行记录器代码之前就否决掉一台主机。

另外：**代理/脚本不应该去"修好"系统时钟**。时钟是基础设施操作，属于主机所有者；研究侧能做的是设计诊断、报告证据。

## 八、延迟测量方法本身的坑

第一版的时钟偏差测量有方法缺陷：**每次调用服务器时间接口都新建 TCP + TLS 连接**，于是测出来的"RTT"（约 600ms）主要是连接建立开销，不是网络往返。基于它做对称性假设的偏差估计是有偏的。

改用持久连接后 RTT 减半到 340ms 左右，批内极差只有 5ms。注意第一版的归因（"是握手开销"）**也是错的**——持久连接把 RTT 减半了，但偏差摆动分毫未减，摆动来自本地时钟而不是网络。

坏时钟下仍然能给出估计：把本地墙钟建模成"真实时刻 + 一个周期性锯齿波偏移"，然后用多个次序统计量（p50、p99、max）分别反卷积。三个互相独立的估计落在同一区间，再用持久连接测得的 RTT 折半做交叉验证——两个方法论完全不同的估计一致时，才敢报这个数。

## 九、容量测量的正确限定写法

我们测了各条流的消息率、字节率和压缩比，并投影了每天的落盘量（单标的下，完整订单簿增量流 + 逐笔 + 最优报价压缩后约 0.31 GB/天）。但报告开头写了一整节"效力声明"，因为这些数字非常容易被过度解读：

- 这是 **15 分钟的单次探测**，不是长周期试点；
- 采样发生在**单一时段、单一市场状态**，高波动时段的峰值可能是数倍，完全没覆盖；
- 探测跑在开发机上，**不是**未来的记录主机——而 §1 恰好表明流的行为可能与连接配置相关；
- **压缩比的三个限定**：(a) 比值是在样本片段上测的，对高速率流只覆盖窗口的一部分；(b) 真实压缩效果取决于**分块粒度**——按 checkpoint 段整体压缩接近本测量值，逐记录压缩会显著更差；(c) 报价类流压缩得特别好是因为相邻消息高度相似，这个特性**在高波动时会变差**——也就是在你最需要容量的时候变差；
- 探测进程的 CPU/内存开销**不等于**记录器开销，后者还要分帧、算哈希链、fsync、写 checkpoint、做异地锚定。

> 一份容量报告最该写清楚的不是数字，而是**这些数字不能用来做什么决定**。

## 十、探测器与记录器必须是两个东西

一条贯穿全项目的纪律：

- 探测脚本是**一次性工具，不演进为记录器**。发现探测脚本自身有缺陷时，我们用另外三种独立方法重新验证结论，但**不去修那个脚本**。
- 探测产物**不得进入任何后续研究分析**：它们没有 seq、没有哈希链、没有 point-in-time 保证。报告里专门写了一句"样本性质声明"来钉住这一点。
- 探测状态（数据拿不拿得到）与组件状态（记录器写没写）是两条独立的轴，全部数据源都探测成功时记录器仍然可以是零代码——而我们的状态表当时正是如此。
- **"原型"不是绕过验收闸的借口**：一个写 canonical 数据的原型，仍然是记录器实现。

## 十一、清单

搭建任何行情采集系统时按这张表检查：

- [ ] 每条流有独立的 `last_message_at` 与逐流静默阈值，超时产生**正向**事件而不是沉默退出
- [ ] 异常处理里没有 `except Timeout: break` 这类把"异常"吞成"正常结束"的写法
- [ ] 每条流标注完整性等级（可证 / 计划有界 / 仅观测），并且"可证"有实测的跳号统计支撑
- [ ] 检查过每个 ID 字段到底是本流计数器还是全局序号
- [ ] 每条流的时间/序号字段单独解析，没有全局字段语义假设
- [ ] 列出"不采即永久丢失"的数据源，并作为显式决策拍板
- [ ] 没有用 REST 顶替 WS、聚合顶替逐笔；任何降级都是记录在案的决策
- [ ] 周期性参数（结算周期等）从接口读取并持续记录，不写死
- [ ] 记录主机通过连续 1 小时的 REALTIME vs MONOTONIC 零阶跃检查
- [ ] 同时记录墙钟与单调钟；NTP 偏移来自守护进程
- [ ] 容量报告附带效力声明，明确写出这些数字不能用来冻结什么
- [ ] 探测代码与记录器代码物理隔离；探测产物不得进入研究分析
