# 市场状态驱动的量化系统架构

这份文档讲的是系统设计的**为什么**，不是某一份代码的 API。核心主张只有一句：

> 不要预测市场，先识别市场处于什么状态，再决定用哪套规则。
> **让系统适应市场，而不是让市场适应系统。**

---

## 一、为什么是"状态驱动"而不是"单策略"

单策略系统隐含一个假设：存在一套在所有市场环境下都有效的规则。我们的实测结论反复否定了这个假设——趋势跟随类在震荡期系统性亏损，均值回归类在趋势期系统性亏损，而大部分标的在大部分时间里处于震荡状态。

所以架构上的第一个决策是：**把"现在是什么行情"和"这种行情该用什么规则"拆成两个独立可验证的问题。**

好处：

- 两个问题可以分别验收（regime 分类的准确性 / 每套策略在其目标 regime 内的表现）；
- 策略失效时能定位是"分类错了"还是"规则本身不工作"；
- 新增策略是插拔式的，不需要改动分类逻辑。

代价：**regime 分类器本身是新的自由度**，同样会过拟合，同样要进反过拟合验收。这一点必须明确——很多"regime 切换"方案的收益其实来自分类阈值被调参调出来的。

---

## 二、状态识别层（Regime Engine）

典型的状态划分：**趋势 / 震荡 / 高波动 / 极端风险**。

判断依据用多个互补维度，而不是单一指标：

- 趋势强度（如 ADX 分桶）
- 波动率（如 ATR、EWMA 已实现波动率）
- 成交量变化
- 资金费率（衍生品情绪）
- 订单簿结构

### 一条重要的设计纪律：规则先于模型

**Regime 判断优先用简单阈值，不要一上来就用 HMM / Transformer。**

理由不是"简单就好"，而是：

- 复杂模型的自由度会直接吃掉本就不多的样本；
- 我们实测过隐马尔可夫状态的方向性预测，不显著；
- 也实测过简单 EWMA 波动率优于更"先进"的波动率估计量。

复杂模型要用，但必须先证明简单阈值不够用，且复杂模型在同一套 walk-forward 口径下确实更好。

### 阈值标定是会翻车的

一个真实过程：某波动率阈值第一次设定导致几乎所有时段都被判为"高波动"（因为年化换算用错了），调整两次之后才得到合理的状态分布。**状态分布本身（各状态占比）是阈值是否合理的第一道体检。** 如果某个状态占了九成以上，阈值大概率错了。

---

## 三、策略切换层

不同状态挂不同的策略，并且**包含"不交易"这个选项**：

| 市场状态 | 处置 |
|---|---|
| 趋势 | 趋势跟随类规则 |
| 震荡 | 均值回归类规则 |
| 高波动 | 降仓或暂停 |
| 极端风险 | 停止交易，仅观察 |

"降仓/暂停/观察"必须是一等公民，和"开多/开空"同等地位。一个只会开仓的系统在不该交易的环境里会持续放血。

**互斥性是硬要求**：同一时刻最多一个方向主导。多个信号同时指向相反方向时，必须有明确的裁决规则，而不是让它们各自下单互相对冲。

---

## 四、多因子评分层

**看到信号不等于交易，先打分。**

把多个维度（趋势强度、成交量确认、资金费率是否正常、订单簿偏向等）各自映射成分数，累加后与阈值比较，只有达标才允许开仓。

这个设计的真正价值不在"打分"这个动作，而在：

- 把"要不要交易"变成一个**单旋钮**（阈值），可以直接用来调节交易频率；
- 让"降频"成为一个可执行的动作——这很重要，见下一节。

### 降频往往是正确方向，但容易过头

一个真实的标定过程：在短周期上用默认参数会**过度交易**（全样本明显负收益）；提高评分阈值 + 加长冷却、降到更长周期，方向是对的（收益转正），但阈值再严一档就只剩个位数笔交易，**完全没有统计意义**。

> **降频的甜点区通常很窄：一边是过度交易被成本吃掉，另一边是样本量不足以证明任何事。** 这个区间需要在"moderate"和"strict"之间继续网格搜索，而不是二选一。

---

## 五、meta-labeling / 二阶段确认

主信号决定**方向**，二阶段模型决定**要不要下注、下多大**（经典的 meta-labeling / triple-barrier 方法）。

这一层的价值是把"方向预测"和"置信度估计"解耦：方向模型可以保持简单，置信度模型专门负责过滤低质量信号。

**但要注意**：这本质上也是"加一层过滤"，而我们的实测经验是**二次融合默认会破坏原始 alpha**（见《回测失效模式目录》）。所以 meta-labeling 层必须和"不加这一层"的基线在同一套 walk-forward 口径下对比，打不赢就撤掉。

---

## 六、完整流水线

一个端到端的决策链大致是：

```
市场数据
  → 订单簿增强 / 反 spoofing 过滤
  → 状态识别（Regime Engine）
  → 策略选择
  → 情绪 / 心理过滤器
  → 多因子评分
  → meta-labeling 二阶段确认
  → 资金费率 / carry 调整
  → 风险检查
  → 回测验证门禁
  → 仓位计算
  → 执行规划（滑点 + 幂等）
  → 动态风控
  → 健康监控
```

关键点：**验证门禁（validation gate）在流水线内部，不在流水线外部。** 也就是说，"这条策略当前是否仍然通过统计验收"是一个运行时检查，而不是上线前检查一次就完事。

### 实盘前的运行时检查清单

每次决策前必须同时满足：

- 验证层判定通过（DSR 显著、PBO 达标）
- meta-labeling 置信度达标
- 反 spoofing 未告警
- 情绪过滤器允许（极端情绪不逆势）
- 健康监控状态非 critical

---

## 七、执行层与监控层

- **执行幂等**：重复下单防护必须在执行层，不能指望上游不重发。
- **滑点模型**：用真实的 L2 订单簿滑点模型，而不是固定 bp 假设。我们自建的模拟盘（带 Mark Price 驱动的浮盈与强平、真实 L2 滑点模型）比通用框架的 dry-run 更接近实盘，**应该优先用更真实的那个做最终验证**。
- **健康监控**：见下一节，这是最容易被做成摆设的一层。

### 监控系统本身会撒谎

一个来自另一个领域（设备运维）但完全适用的教训：监控系统可能显示"一切正常"，而实际上离线设备丢失了身份信息因而从统计里消失了。同理，在交易系统里：

- 进程活着 ≠ 策略在工作（信号输出文件长期为空 = 已死）；
- "无告警" ≠ "无问题"（要监控的是**产出**，不只是存活）；
- 监控必须有"最近一次成功产出的时间"这类**正向**指标，而不只是"有没有报错"这类**负向**指标。

## 八、构建纪律：六条铁律

这是数据平台/研究框架层面的建设纪律，来自一次彻底重构之后的总结：

1. **先验后建** —— 任何引擎在回测证明其前置假设之前，不实现。
2. **数据不可覆盖** —— 所有快照 append-only，只增不删。
3. **规则先于模型** —— 先用简单阈值，证明不够用了再上模型。
4. **摩擦优先** —— 一切回测强制含进场延迟、手续费、滑点、资金费计提；无摩擦结果一律无效。
5. **时点纪律（PIT）** —— 任何选标的/评分/状态判定只能用该时点已可见的数据。
6. **反过拟合铁律** —— 独立样本数 ≥ 自由参数数 × 20；结论必须在 held-out 时段复验；负面结论照样入库。

其中第 3、4、5 条是多个独立项目各自收敛到的同一结论，可信度最高。

---

## 九、基础设施：不要重复造轮子

一个反复出现的浪费模式是：新研究项目开始时，重新搭一套比现有基础设施**更简陋**的数据采集 + 回测 + 验证工具，然后用它得出精度更低的结论。

值得沉淀成共享基础设施、不该在每个项目里重写的东西：

- **数据仓库**：全量公开衍生品数据（多周期 K 线、逐笔与聚合成交、L2 深度快照与增量、持仓量、资金费率、多空比、基差、爆仓数据）。有了真实订单流数据就不要再用成交量去"代理"订单流。
- **模拟盘**：带真实 L2 滑点模型、Mark Price 浮盈与强平逻辑的模拟撮合服务。
- **反过拟合工具包**：DSR / PSR / PBO / bootstrap / placebo / walk-forward / 参数平台，一套实现，所有项目调用。
- **特征级 IC 评估框架**：策略级验证工具的互补品。

**纪律**：新项目开工前先盘点"这件事是不是已经有更严谨的实现"。如果有两套独立实现同时存在，应该主动对比并合并，而不是任由它们分叉。
