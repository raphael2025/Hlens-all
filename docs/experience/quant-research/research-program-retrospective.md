# 研究项目复盘：为什么"做了很多"却"没有进展"

前面几份文档讲方法论。这一份讲**组织层面**的失败模式——它们不会被任何统计检验抓住，但它们对研究产出的伤害比任何一个回测 bug 都大。

这些观察来自一次跨约三十个自有仓库的系统性整理：把分散在多个仓库、多个研究阶段的结论合并起来，回答"到底测过什么、结论是什么、现在什么东西还活着"。整理过程本身暴露出的问题，比整理出的结论更值得写下来。

---

## 一、核心模式：验证出结果之后，转向而不是执行

最反复出现、也最耗费时间的一个模式，由三个互相强化的行为组成：

1. **设定"无限持续自主研究"模式** —— 明确要求流程永不宣告"任务完成"，持续寻找新 alpha；
2. **验证出结果后不去执行，而是转向建更大的框架或换新研究方向** —— 多条"接近验证但没人跟进"的线索就这样被搁置；
3. **同一个数据平台被推倒重建多次** —— 每次重建都写了更严格的方法论文档，但每次都是推倒重来而不是在已验证的基础上迭代。

三者叠加的结果是：**方法论文档越写越好，产品越来越没有跑起来。**

### 最刺眼的证据：收敛计划定了，但没有被执行

在某个时间点，一份深度读完十几个仓库后写成的战略总结，**准确诊断出了上面这个问题**（多套数据采集器同时在跑、多个半成品项目、一堆 agent 记忆仓库是"研究沉淀不是产品"），并且定下了明确的收敛计划：停止找新 alpha、停止重复造轮子、主线收敛到当时唯一已在 dry-run 的候选，其余全部归档。

但从此后新增的仓库和项目来看，**这个收敛计划没有被执行，反而又长出了更多平行项目**。

这不是事后猜测出来的模式，是一份有明确日期、明确文字的"计划做了，没照做"的记录。

**教训**：诊断本身没有价值，执行才有。一份准确的战略诊断如果没有配套的**强制机制**（比如"新项目必须先关掉一个旧项目"），它会变成又一份被归档的文档。

## 二、自主研究模式的设计缺陷

"永不宣告完成"这个约束，初衷是防止流程偷懒提前收工。实际效果是：**它让流程永远不会进入"执行已验证结论"的阶段**，因为"继续研究"永远是一个合法的、看起来在产出的选择。

更健康的设计应该是：

- **"完成"必须可达**，且有明确的完成定义（例如"该候选通过 deploy gate 或被明确证伪"）；
- 把"研究"和"执行"设成两个独立的、有各自成功标准的模式，而不是让研究模式吞掉一切；
- 给研究模式设**预算上限**（时间/算力/资金），到了上限强制进入裁决，而不是无限延长。

### 自主循环需要存活证明

我们至少有两个"自主研究循环"的独立实例（多 agent 交叉验证流程、以及一个数十并行 worker 的挖掘循环）。两个的共同问题是：

- 循环**实际上只手动运行了几天**就停了，没有被安装成常驻服务（安装脚本是空文件）；
- 停止的时间点和原因都没有记录；
- 几个月之后回头看，"它现在还活着吗"这个问题**没有人能直接回答**，得去翻机器。

**教训**：任何长期运行的自动化，必须自带"我还活着且在产出"的可观测信号（最近一次成功产出的时间戳），并且这个信号要出现在一个人会定期看的地方。否则它死了也没人知道。

同样的问题在交易侧出现过：一个 dry-run 的策略，其信号输出文件在某个日期之后连续数周都是**零字节空文件**——进程技术上还在，但已经数周没有产出任何信号。这不是"不确定它还在不在跑"，是"它已经死了，只是没人发现"。

## 三、进度记录方式会让人（包括未来的自己）看不清真实状态

这个模式出现了至少三个独立实例：

1. **默认分支误导**：某个仓库的默认分支停留在一个容易被误解的提交上，而真正在生产运行的系统说明文档全在一个**没有发起过 PR、默认不可见**的分支上。任何人（包括第一次读这个仓库的自己）只看默认分支，得到的印象都是错的。

2. **重复命名的平行项目**：多个名字相近、定位相近的仓库同时存在，其中某一个号称"待办清单全部完成"，但它和其他几个是同一条线的不同阶段、还是独立的平行线，从仓库本身看不出来。

3. **结论散落在多个仓库**：同一个策略的正面证据在一个仓库、负面证据在另一个仓库，两者互相矛盾（例如某条腿在一个数据库上测出正、在样本量最大的数据库上测出负），而**没有任何地方记录过这个矛盾**，更没有解释。直到一次跨仓库整理才被发现——而矛盾的真实原因是一个成本方向算反的 bug。

**对应的纪律**：

- **真实在跑的东西必须在默认分支可见**，或者 README 第一段就说清楚"看哪个分支"。
- **一个方向一个仓库**。要开新仓库，先说明旧仓库的处置（归档 / 合并 / 明确的并行理由）。
- **结论必须有唯一权威位置**。同一个策略的结论散落在多处时，必须有一个总账，且矛盾要被显式记录为"未解决"，而不是让两个结论各自存在。

## 四、知识库的真实价值在"负面结论"和"矛盾"

一次跨仓库整理最有价值的三类产出，按价值排序：

1. **矛盾**：A 仓库说有效、B 仓库说无效，且没人解释过。这些是最高优先级的待办——它们意味着至少有一边是错的，而你不知道是哪边。
2. **悬而未决的线索**：接近通过验收但差一点、然后因为资源转向而被搁置的方向。这些比"再挖一个全新方向"性价比高得多。
3. **负面结论**：被证伪的东西，以及为什么。这决定了未来不要再浪费周期。

**"已验证有效"反而是最小的一块**，而且它还要被打上"历史验证 ≠ 当前有效"的折扣。

### 一条关于知识库自身的警告

用自动化手段（LLM/agent）批量生成知识条目时，会产生大量**看起来像结论、实际没有任何证据支撑**的页面。我们自己的知识图谱里就有一批标注为"低置信度、无来源、通用模式列表"的条目，它们和有真实来源的条目混在同一个目录下。

**纪律**：

- 每一条结论必须带 `来源` 和 `置信度` 字段，且这两个字段要被**强制校验**（缺失即视为无效条目）；
- 自动生成的内容默认低置信度，需要人工或独立复现才能升级；
- 定期跑一致性检查（孤立页面、缺失元数据、断链）；
- **不要用 LLM 生成的"具体数字"当证据**。我们核查过一批看起来很具体的业绩数字（某类新型交易的利润预估、某类套利模型的收益），全部没有回测依据，属于生成风格的产物，不采信。

## 五、多视角交叉验证：有用，但有边界

多个独立执行者（不同的 agent、不同的工具链）交叉验证同一个结论，确实抓出过好几个"看起来是神级、实际是统计幻觉"的假阳性。这套做法值得保留。

但有两个明确的边界：

1. **机械核对 ≠ 语义验证**。自动化审阅工具只能验证"数字对不对、代码跑不跑得通"，无法验证"这个断言是否成立"。它给出的"通过"不能当作结论正确的证据。
2. **必须自己复现**。子流程报告的结果，主流程必须独立复现一遍。我们有过子流程报告多年期优秀 Sharpe、主流程复现后完全失真的实例。

延伸出的一条更一般的原则：**"N 个独立来源都说有效"的说服力，取决于这 N 个来源是否真的独立。** 如果它们共用同一份数据、同一段 regime、同一套成本假设，那它们只是一个来源被复制了 N 次（这也正是 cluster-aware DSR 要解决的问题）。

## 六、资源约束下的工程经验

一些在长期运行自动化研究时踩到的具体问题：

- **配额管理**：LLM 额度是有窗口的。长任务要设计成**可中断、可恢复**（处理一批存一批），并在配额耗尽时自动安排在下一个窗口重启，而不是整批失败重来。
- **定时任务要自清理**：一次性的恢复任务在完成后要删除自己，否则会积累大量僵尸定时任务。
- **递归生成会无限发散**：自动生成知识条目时，每个新条目又会引用新的子概念，形成无穷回归。必须设明确的停止条件（频次阈值、深度上限），并接受"剩余的断链是噪声，不值得再花成本"。
- **知道什么时候停**：几次批量生成之后收益明显递减，剩下的工作本质上是输出质量问题（提示词约束）而不是生成量问题。**主动宣告停止**是一个需要被显式做出的决定。

## 七、给未来自己的几条硬规则

1. **同时只推进一条主线。** 新方向进入之前，旧方向必须有明确处置（毕业 / 证伪 / 归档）。
2. **每条线都要有"下一步是什么、什么条件下判死"。** 没有判死条件的研究线会永远活着并持续消耗注意力。
3. **定期问"现在什么东西真的在跑"，并且要能在五分钟内回答。** 回答不了就说明可观测性不够。
4. **先执行已验证的结论，再找新的。** 一条通过验收但没人跟进的线索，价值高于一个全新的探索方向。
5. **诊断要配强制机制。** 写下"我应该收敛"没有用，写下"开新项目前必须关掉一个旧项目"才有用。
6. **负面结论和矛盾优先入库。** 它们才是知识库的骨架。
