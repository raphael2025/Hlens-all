# 两条产品线：为什么它们分开长，又为什么互相借东西

这个项目从外面看像是一条 V1→V2→V3…… 的版本递进线。实际不是。它是**两条并行的产品线**，各自解决不同的问题、各自有一套不能妥协的正确性前提；它们在中途开始互相引用对方的实现与错误，最终一条线的重写大量吸收了另一条线的产出。

这份文档记的是：它们为什么分开、分开之后各自沉淀了什么、以及"把自己写过的旧仓库当作一等参考资料"这件事到底值多少。

---

## 一、两条线各自在解决什么

**A 线：通用多交易所长周期数据采集平台。**
目标是"五年之后我手上有一份别人买不到的原始数据"。多个交易所 × 多个焦点资产 × 行情/衍生品/链上，主节点 + 工作节点分布式采集。经历了：第一代实现 → 归档冻结 → 完全重写 → 生产采集线。

**B 线：针对单一永续合约交易所的交易员情报平台。**
目标是"谁值得跟、什么时候跟、跟多少、什么时候停"。抓排行榜、筛高绩效钱包、分布式采集它们的持仓与成交、做看板与告警；后来又加了一层离线研究平台专门回答"跟单到底有没有 edge"。

两条线用的语言、存储、拓扑都不一样，而且在相当长一段时间里同时在跑。

## 二、它们为什么不该合并

真正把它们分开的不是技术栈，是**两套互不兼容的正确性前提**：

| | A 线 | B 线 |
|---|---|---|
| 最怕的事 | 一段数据永久消失，而且没人知道 | 一个结论是假的，而且看起来很漂亮 |
| 由此推出的硬纪律 | 原始数据不可覆盖、内容寻址、出口唯一性、回执即"可以删原件" | 时点纪律（PIT）、摩擦必须内化、先验后建、负面结论照样入库 |
| 重复的代价 | 便宜（内容寻址天然幂等） | 昂贵（同一份数据被重复计入会直接污染统计） |
| 延迟的代价 | 致命（不可回补） | 可接受（离线批处理） |

把这两套纪律塞进同一个系统，结果一定是其中一套被稀释——通常是被稀释的那套先出事。**分成两条线不是资源浪费，是让每条线的"最怕的事"都能被当成第一优先级对待。**

## 三、一个被明确写下来的决定：新一代不杀死上一代

B 线的研究层上线时，文档第一段就写明：**它不取代在线采集器**。在线系统继续跑、继续出看板；研究层从它的数据库导出历史做冷启动，之后独立拉取、建立自己的 append-only 历史。

这个决定值得单独拎出来，因为默认冲动总是"新的一代要替换旧的一代"：

- 只有当新系统**承担同一份职责**时，替换才是替换；否则它只是多了一层职责不同的东西。
- 在线采集器的职责是"不断线"，研究层的职责是"结论可证伪"。让后者去承担前者，等于让一个还在被反复推翻的研究流程扛住生产可用性。
- 冷启动从旧系统导，但**之后不再依赖它**——这是"借用"和"耦合"的分界线。导入是一次性的，持续依赖不是。

反过来，A 线在重写时做的是另一种处理：上一代的全部分支与标签**整体冻结到一个独立的归档仓库**，主线只保留一条分支。归档而不是删除，主线而不是兼容。效果是：历史随时查得到，但不会有任何人（包括 AI 协作者）因为"仓库里还有这份代码"而去改它、引用它、或者试图保持兼容。

## 四、重写时的定位话术：不是第五个版本，是新一代的 V1

A 线重写的自我定位写得很清楚：**这一代不是"第五个版本"，而是新一代的 V1。** 上一代的价值是教训与已验证的实现思路，不是要兼容的存量。

这句话实际拆成了两条方向相反的纪律，而且必须同时成立：

1. **代码与设计不继承**。设计决策以新仓库自己的文档为准，**不因为"以前是那样做的"而沿用旧做法**。
2. **坑必须继承**。旧仓库踩过的每一个坑都要复用，不允许重付学费。

只有第 1 条是"推倒重来"，两条一起才是"重写"。绝大多数失败的重写，是只执行了第 1 条。

## 五、两条线是怎么互相喂养的

A 线重写前做的那次考古（见《重写之前先做一次代码考古》）把 B 线的仓库当成了一等资料。实际被采纳的东西：

**当成实现范本借过来的：**
- 单条 SQL 完成"领取任务 + 过期租约重入 + 失败重试"（行锁 + `SKIP LOCKED` + 条件更新），这是"工作拉取"这个拍板的已验证落地形态；
- 提交时校验租约归属 + 全链路按自然键幂等写入，这是围栏的最小可用形态；
- bronze / silver / gold 的数据契约约定（bronze 只追加、发现坏数据也不删而在下一层过滤并记录原因；分区键取事件时间不取采集时间；摩擦参数与规则阈值全部版本化；产物记录代码版本 + 参数 + 数据区间）；
- 展示层的"每源一个 adapter + 逐源优雅降级 + 离线全绿单测与显式 live 冒烟两层测试"组织方式；
- "诚实边界"的文档写法：每个接口一行写明主源 / 降级链 / **能力边界（加粗写死）**，失败返回 200 + 明确的不可用标记与真实原因，而不是 5xx。

**当成反例借过来的（价值同样高）：**
- 一个毫秒级排他游标的 bug 被直接写成了新一代测试里的反例 fixture；
- 一张缺少"采集保真度"维度的表，被用来反推新一代 schema 该长什么样；
- 一个大文件每轮全量重下、不做版本探测的下载器，被用来确立"下载纪律要借，版本锚不能丢"。

**真正跨线共享的资产其实是第三样东西：** 两条线的仓库里都有同一族的交易所 API 实测文档（限速形状、推送保真度、结算周期陷阱、静默忽略参数的端点清单）。代码全部重写过，这批文档一路继承。

> **实测得来的第三方行为事实，比任何一份实现活得久。** 它应该单独成层、不依赖任何一个代码库的生死。

## 六、可迁移的结论

1. **两条产品线如果"最怕的事"不同，就不要合并。** 合并的代价不是复杂度，是其中一套纪律被悄悄降级。
2. **新一代不必杀死上一代。** 只有职责相同才谈替换；职责不同就是加一层，并且说清楚冷启动依赖是一次性的。
3. **旧仓库归档冻结，不要留在主线。** 主线只有一条分支，历史另存。否则"还能改"就一定会被改。
4. **"不继承代码"和"必须继承教训"要一起说出口。** 只说前者的重写会把学费再交一遍。
5. **自己写过的旧系统是信噪比最高的参考资料**——实现是在生产里验证过的，bug 是可复现的，而且你知道当时为什么那么写。前提是你愿意把它当资料读，而不是当负担躲。
