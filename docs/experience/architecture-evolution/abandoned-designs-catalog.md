# 被放弃的设计清单：它们错在哪、以及由此得到的规则

这份文档是一个反面目录。每一条都是在这批仓库里真实写过、跑过、然后被明确放弃或推翻的设计；每条只记三样东西：**它是什么、为什么不行、由此得到的可迁移规则**。

把这些集中成册的理由很实际：**一个被否决的方案如果只存在于某次对话里，它一定会被重新提议。**

---

## 总览

| 被放弃的设计 | 为什么 |
|---|---|
| 把常驻推送流建模成有界的租约任务 | 一次租约抖动 = 所有交易所的流同时断，而这批数据不可回补 |
| 派生层摄入挂在原始数据接收的同步路径上 | 下游一个小 bug 把上游采集堵死 |
| 用"双路冗余订阅互比一致"证明数据完整 | 降采样发生在服务端扇出**之前**，冗余会稳定地误报"我们没丢" |
| 聚合表不带"采集保真度"维度 | 不同采样策略的行被当成等价行求和，结果没有定义 |
| 排他式游标（上次时间戳 + 1） | 同一时间戳内的后续事件永久静默丢失 |
| 大文件每轮全量重下、不做版本探测 | 浪费带宽只是小头，**永久丢失"数据截止于何时"这个锚**才是大头 |
| 逐仓位累加清算价、用"距离百分比"过滤垃圾值 | 跨仓位联合效应丢失；那条轴上根本不存在正确阈值 |
| 契约强制"记录数 > 0" | "正常为空"无法表达，于是每类数据各造一个特例类型 |
| 压缩被硬编码为"无" | 容量是前提不是优化；且哈希绑压缩前还是压缩后必须显式定义 |
| 一个字段承载多种语义 | 分片键直接吃这个字段，多来源下语义打架 |
| 单 JSON 文件控制面 + 无 GC 的审计/幂等表 | O(n) 写放大 + 无界增长；换数据库不是换后端那么简单 |
| 每个数据块一个目录 | 五年期事件级流会产生海量小目录与小文件 |
| 租约令牌明文随任务对象流出 | 只靠注释提醒调用方脱敏 |
| 任务状态机只有三态 | 没有失败 / 退避等待 / 死信 / 尝试次数，退避与告警无处安放 |
| 并发上限只降不升（棘轮） | 一次限速永久压低该出口，是一场慢性停摆 |
| 超时重传后重复入库、重复计费 | 先查后写跨网络不是幂等 |
| Kubernetes / 外部共识 / 消息队列 / 云托管 | 它们最值钱的三件事在这个项目里恰好都是要被禁止的行为 |
| 多代理合并请求 + 交叉复核控制面 | 三个数字：协调表 0 行、0 个提交、负责人介入 0 → 10+/天 |

下面按主题展开。

---

## 一、抽象错位

### 1. 常驻流被当成有界任务

已单独成篇，见《常驻流不是有界任务》。一句话版本：**租约只买两样东西——不超发限速预算、不重复推进有状态游标。常驻长连接两条都不沾边，所以对它上租约是纯亏。**

**规则**：套用任何协调原语之前，写下它买来了什么，再逐条确认这类负载真的需要。不需要的部分不会消失，它会变成一类你本不必有的故障。

### 2. 可重算的挡住了不可回补的

规范化 / 派生层的摄入被放在原始数据接收的同步路径上：派生层失败 → 整个上传返回 5xx → 上游认为传失败。

**规则**：**原始层不可回补，派生层随时可重算。让可重算的挡住不可回补的，方向是反的。** 接收层不得 import 任何派生层，回执不得依赖派生层成功，并用测试把依赖方向钉死——不要靠评审时的自觉。

### 3. 一个字段承载多种语义

同一个 `subject` 字段在一处表示"覆盖窗口 ID"、在另一处表示"账户地址"，而账本的分片键直接吃这个字段。多来源 × 多品类之后语义必然打架。

**规则**：语义不同就分字段（`subject_kind` + `subject_id`），不要靠上下文区分。被索引键或分片键直接消费的字段尤其不能多义。

## 二、把"测不出问题"当成"没有问题"

### 4. 双路冗余订阅被当成完整性证据（这条最值得读）

设计是：每个采集目标强制派两路独立订阅（主 / 影），由不同节点执行，互比一致即认为没有丢数据。计划器甚至把这条固化成了**结构约束**——校验函数强制要求恰好四个任务、四种（类型, 角色）组合齐全。

实测结果：

- 同一交易所两条独立连接跑 12 小时，事件**交集 100%、双向漏 0**；
- 另一家两条连接互比**分歧为 0**；
- 而**对照另一种取数模态（轮询接口）才发现丢了七成**。

原因：**降采样发生在服务端扇出之前。** 所有订阅者拿到的是同一份已经被砍过的流。于是：

> **"多点互比一致"会稳定地误报"我们没丢"。**

最讽刺的一点：这个实现自己的设计原则第 4 条就写对了——"质量不等于完整性：双节点和本地序号只能降低风险，不能证明来源无遗漏"。**但计划器把冗余固化成了结构约束，等于用架构语言说"冗余是必需的"。**

**规则**：

- 冗余可以保留，但**只能声明为连通性/断线冗余**，不得作为完整性证据；
- **只有换模态对照**（推送 vs 轮询）才能测保真度，这需要在质量事实体系里单列一类事实；
- 更通用的一条：**当文档里的原则和代码里的校验函数打架时，实际生效的是校验函数。** 定期审计你的 validator，看看里面偷偷固化了哪些未经检验的信念。

### 5. 接收端序号被用来声称"源端有缺口"

反面的正确做法，来自同一个被废弃的实现，也是它最值钱的一条设计：事件信封里的序号带 `sequence_scope ∈ {source, observation}`，**只有 source 作用域才允许产生"缺口"这条事实**，并且有一条测试专门钉死"接收端序号永远不会声称源端有缺口"。

**规则**：**把纪律做成类型，而不是约定。** 没有源序号时，"我漏了"这句话应该在类型层面根本说不出口。

### 6. 聚合表缺少"采集保真度"维度

一张跨交易所的强平事件表只有品种 / 方向 / 价格 / 数量 / 金额 / 来源 / 时间戳七列。它回答不了自己存在的理由：

- "这一小时全网爆了多少钱？"——不同来源的行分别来自"每秒最多推一条且取最大"、"实测只收到三成且越剧烈丢得越多"、"确定全量"三种策略，**在表里不可区分**，SUM 出来的数没有定义；
- "哪个来源占比最高？"——占比差异可能全部来自推送策略差异；
- "某次策略变更前后的数据可比吗？"——表里没有任何字段标记采集方法学变更，新旧数据无缝混在一起；
- "这一小时没有数据，是真的没有事件，还是断线了？"——没有连接 / 会话维度，静默断连与真实零事件不可区分。

**规则**：**如果不同的行可能来自不同的采集方法学，方法学就必须是一列**，取值是受控枚举，并且**聚合层被强制按它分组、禁止跨组求和**。同时：原生事件时间与本地接收时间必须分列、采集会话标识必须入库、原始报文指针必须保留。

### 7. "正常为空"无法表达

契约把"记录数 > 0"写成硬约束。后果是"这段时间什么都没发生"这件事没法用普通数据块表达，于是实现被迫为空窗口另造一个数据类型、为空结果页再造一个——**每类数据各造一个特例**。

**规则**：**"这段时间什么都没发生"必须是一条数据，不是没有数据。** 而且它应该是通用契约里的一个字段（为什么为空），不是每类数据一个新类型。与之配套：每个窗口型来源必须记录"最后一次成功拉完整窗口"的时刻，超时即告警——否则"一直没数据"和"一直没在采"长得一模一样。

## 三、游标与增量

### 8. 排他式游标

增量续采时把起点写成"上次见到的时间戳 + 1"。如果排序键是毫秒级且同一毫秒内可能有多条事件（在高频账户上是常态），**那一毫秒内还没见过的事件会永久静默丢失**。

同一处还叠了第二个错误：两个取数接口的排序方向相反（一个新→旧、一个旧→新），代码统一按"末元素是最旧"处理，于是增量路径拿到的"最旧"其实是最新，翻页方向算反，游标还会回退。

**规则**：**排序键不唯一时，游标必须是复合的**——（时间戳 + 该时间戳内已见 ID 集合），**含起点续采 + 按 ID 去重**。另外：**同族接口的排序方向必须逐个建模，不能假定一致**。

这个 bug 后来被直接指定为新一代的**反例 fixture**——不是写进"注意事项"，而是变成测试里的一个具体输入。

### 9. 大文件每轮全量重下、无版本探测

一个数十 MB 的榜单文件每个周期完整重下一次，不带任何条件请求或版本探测。浪费带宽只是表象，真正的损失是：**文件正文里没有时间戳，不记录版本标识就永久失去了"这份数据截止于何时"这个锚**。

值得借的是它做对的那半边：流式写临时文件 → 完成后原子改名 → 异常路径清理临时文件 → **下载后强制结构校验**（解析 + 行数 + 顶层键）才算成功。

**规则**：原子落盘与下载后结构校验缺一不可；**同时必须记录版本标识与抓取时刻**——对一份没有内嵌时间戳的数据，这是它唯一的时间锚。

## 四、数值与口径

### 10. 逐仓位累加清算价 + 用"距离百分比"过滤垃圾值

一个清算分布图的实现把每个仓位的清算价独立扔进直方图累加，循环体内没有任何账户维度——**全仓保证金账户的联合效应完全丢失**（在全仓模式下，"清算价"的语义本来就是"其他仓位不变时"，跨仓位独立累加没有意义）。

唯一的垃圾值防线是 `|距离百分比| > 50% 就跳过`。实测表明：那条轴上**根本不存在正确阈值**——一个低杠杆的大额真实仓位，距离百分比可以高达 88%；而一个名义金额极小的仓位会报出荒谬的清算价，它之所以被挡住，纯属距离恰好极端的**巧合**。

**规则**：

- **靠巧合生效的过滤器不是过滤器。** 换一条真的存在正确阈值的轴去过滤（这里是名义金额）。
- 在有账户级联合效应的模型里，**先按账户聚合再入桶**。
- 顺带一条术语纪律：**"统计"、"模型估算"、"真实持仓"是三件不同的事**，不能混在一张图里，展示层必须标注哪一种。

## 五、控制面与存储形态

### 11. 单 JSON 文件控制面

每次操作整份重写状态文件，审计日志与幂等表都在同一份文件里且**无限增长**。在长周期、多来源、大量目标的规模下是 O(n) 写放大 + 无界文件。

**规则（迁移时最容易出事的一处）**：换成关系数据库时，**不能只是把 JSON 换成表**。原实现的"领取任务"原子性来自**进程内互斥锁**；换库之后必须换成行锁 + 跳过已锁行的条件更新，否则并发领取会重复发牌。**存储后端的替换不等于并发模型的替换。**

附带两条：**幂等表和审计表五年期必须有保留策略**；且**幂等记录的过期时间必须长于任何客户端的最大重试窗口**，否则会出现"重试时幂等记录已被清掉 → 重复执行"。

### 12. 每个数据块一个目录

`<块ID>/{manifest, 载荷, 状态, 回执}` 的布局设计上很干净，但原实现只跑过有限窗口。**五年 × 多来源 × 事件级流会产生海量小目录与小文件**，inode、备份扫描、同步工具全会吃苦。

**规则**：保留"内容寻址 + 自证 manifest"的语义，但物理布局要按**实际块大小分布**重新设计（分层目录或打包容器）。语义和布局是两个决定，不要一起定死。

### 13. 压缩被硬编码为"无"

契约直接拒绝任何非"无压缩"的取值。而实测下事件级流的压缩比高达一个数量级——**压缩不是可选优化，是容量前提**。

**规则**：契约从第一天就要允许编解码器字段；并且**必须显式定义内容哈希绑的是压缩前还是压缩后的字节**。原实现因为不压缩而不存在这个歧义，一旦要压缩，这就是个必答题。正确答案是**绑未压缩流**：若绑压缩字节，换一次编解码器等于换一遍所有 ID，历史全部对不上（压缩后的哈希另存一列）。

### 14. 租约令牌明文随任务对象流出

状态快照接口会把含令牌的完整任务对象返回出去，**只靠一行注释提醒调用方脱敏**。

**规则**：**在结构上杜绝**——存令牌的哈希，或者让快照类型根本没有令牌字段。同族的正面做法：状态上报接口只接受**白名单枚举**（任务开始 / 成功 / 失败 + 有限的原因码），实现方绝不能收到目标、进度、令牌或原始错误串。

> **监控面板的输入面必须是白名单枚举，不是自由文本。** 既防泄密，也强迫你把失败分类想清楚。

### 15. 任务状态机太窄

只有"待领取 / 已租出 / 已完成"，没有失败、退避等待、死信、不早于某时刻、尝试次数、错误分类。结果是"单任务内部的指数退避"和"断言失败要标红等人处理"这两类需求在模型里**无处安放**。

**规则**：状态机在迁移之前**必须先扩再用**。一个缺少失败态的状态机会逼着调用方在外面私自实现重试，而那份实现不会被任何人审计。

## 六、生产中长出来的两个 bug

### 16. 并发上限只降不升（棘轮）

限速调节函数只在收到限速响应时把某出口的并发上限减一，**没有任何地方加回去**。一次偶发限速会**永久**压低该出口的并发，而且完全无声——它表现为"系统一直在工作，只是越来越慢"。

修法是 AIMD 式的"加得慢、砍得狠"，并额外引入三样东西：一个**操作员配置的天花板**（恢复只靠近它、不越过，也不下拉人工设的更高值）、一个**冻结期**、一个**恢复锚点时间戳**。

两个细节值得记：

- 判断逻辑做成**纯函数**（不碰数据库），于是可以直接测；
- **不要复用另一个调节器的时间戳字段**——两个 AIMD 共用一个 `updated_at` 会互相覆盖冻结期。

**规则**：**每一个自动降级都必须配一条定义清楚的恢复路径和一个上界。单向控制器是一场慢性停摆。** 上线后还要有一条对账查询："常年低于天花板"就是棘轮卡住了。

### 17. 超时重传导致重复入库、重复计费

上游在中心超时后原样重传，中心无条件再处理一次——同一页数据落两次盘，配额也被多扣一次。

修法是幂等键（任务 ID + 本次租约的尝试次数，重传时原样带上不变；任务被重新租出后尝试次数变，键跟着变）。**但第一版修法被评审抓出了先查后写的竞态**，最终升级成让数据库的唯一约束来承担判重。

**规则**：**跨网络的"先查后写"不是幂等**。把唯一性下沉到存储引擎的约束里。另外：判重不能只看"任务是否已完成"，因为那只覆盖成功路径——失败类的重复提交会把任务放回待领取态，单看状态会漏判。

## 七、被整体拒绝的外部组件与流程

### 18. 容器编排 / 外部共识 / 消息队列 / 云托管

完整论证另见开发定稿，这里只留骨架：

**编排系统最值钱的三件事，在这个项目里恰好全部买不到：**

1. **"我不在乎进程跑在哪台机器上"**——这正是本项目**正确性前提的反面**。限速额度按公网出口算、同一出口只准一台机器出网，正确性来源是"不存在第二个消费者"。调度器的天职是把负载搬来搬去，而这正是要禁的事。
2. **"副本数一改就扩容"**——出网采集器**永远只能 1 个副本**。值得注意的是：**连主张上编排的那份旧文档，自己都把采集器从自动扩容里剔除了**。主张方不得不把最核心的部分从价值主张里挖掉，这本身就是证据。
3. **"节点挂了自动迁走"**——采集节点不是无状态的，本地盘上压着 WAL 和未上传的不可回补数据，必然被钉死在特定机器上；在编排系统里就是有状态副本 + 本地卷，**又回到"钉死"**。

还有一条结构性的：**本设计的核心是"中心可以死、边缘继续录"；编排系统的模型是"节点向控制面对齐"。我们要的是"控制面失联属于一等公民的正常状态"，它那里这属于降级状态。方向相反。**

**而真正想要的四样东西成本全为 0**：声明式 → 一份角色参数配置；装哪台都一样 → 部署产物逐字节可复现；自愈 → 进程管理器的重启策略 + dead-man's switch；换机不重来 → 全部可变状态只在数据目录里。

**规则**：

- **要拒绝的是调度器，不是容器。** 容器化拿到环境可复现，成本近乎零，完全可以要。
- **区分"迁进程"和"迁出口身份"**：前者装一遍产物就行，不需要调度器；后者根本不该被自动做——换一个出口换掉的是限速预算、可达性资格、甚至对方认不认你（实测：某家的 CDN 会按主流云厂商的整段地址拒绝，与国家无关）。**"悄悄把负载搬到另一台机器"如果真生效了，那是 bug 不是 feature。**
- **这不是永久拒绝，是"等到有证据再上"**：推翻条件是节点数长到某个量级**且**运维负担有实证。届时**必须保留"每个出口只有一个出网消费者"的硬约束**——那时编排系统只能是**被约束的对象**，不能是解决方案。
- 不上的代价很低，也是拍板的一部分：将来真要上，那是**部署层**改动，原始数据、契约、数据库 schema、采集逻辑一律不动。

### 19. 多代理协作控制面

见《决策要带推翻条件》第六节。一句话：**它技术上能跑，但协调表 0 行、走它的任务 0 个提交、而绕过它的开发同期产出 11 个提交。**

## 八、一个反复出现的错误形状（不是设计，是分类）

最后一条不是被放弃的设计，而是同一轮里踩了三次的同一种错误：

> **把"会自己好的事"，归进了"不会自己好的那一类"。**

三次的具体形态不同（一次是响应里已经带着正确信息、跟随重传即可成功的冲突；一次是磁盘满这种会自愈的情况因为错误响应缺少身份标记而被误判成"打到了别的中心"；一次是网关抖动的 5xx 被判成身份不符），但后果完全一致：

> **一件几秒就自愈的事变成"停在那里等人"，而真正需要人看的告警淹没在里面。**

**规则**：**写任何分类表 / 状态码表 / 告警分级之前，先逐条问"这件事会不会自己好"，再决定它进哪一类。** 界面上同样成立——需要动手的与会自己好的必须分两块显示，混在一起人会对整块区域脱敏。

补充一条观察：这类错误**只跑单元测试看不出来**。三次里有一次是真起服务端到端跑一遍才发现的，另一次是独立红队评审指出的。
