# 决策要带推翻条件，延后要带挂载点

一个长期项目里的架构决策有两种死法：

- **被反复重提**——每隔几周就有人（或某个 AI 协作者）重新提议同一个替代方案，每次都要重新论证一遍；
- **在前提早已改变之后还被死守**——更糟，因为没人记得当初为什么这么定。

两种死法的根都一样：**只记录了结论。**

这个项目用两份文档解决它：一份管"已拍板的方向性决策**与它们的推翻条件**"，一份管"功能上必须有、但当前不实做"的模块。两份都不是清单，是带强制字段的登记册。

---

## 一、三份文档各管一样东西

| 文档 | 管什么 |
|---|---|
| 协作规则文件（给人与 AI 的入口） | **决定了什么** |
| 开发定稿 | **为什么** |
| 决策日志 | **什么情况下这个决定该被重新考虑** |

第三样是稀缺的。它不是"为什么"的补充，是一个独立的问题。

## 二、决策日志的条目长什么样

每条固定四段：**决策 / 为什么 / 推翻条件 / 不构成推翻条件**。最后一段常常是最有用的那段。

几个真实条目的形状（细节已做通用化处理）：

> **限速预算按公网出口计；同一出口只允许一个节点出网采集**
> **为什么**：正确性来源是「**不存在第二个消费者**」，**不是共享令牌桶**。令牌桶要求所有消费者都诚实上报，而崩溃 / 重启 / 时钟漂移都会破坏这个前提。
> **推翻条件**：交易所把限速改为按 API key 或按账号计（而非按出口）。届时要**重新建模，不是简单放宽**。
> **不构成推翻条件**："多台机器共用一个出口更省钱"。

> **禁止按分片键预分配任务；拓扑用中心辐射 + 工作拉取**
> **为什么**：**被采集对象之间的工作量差异是数量级的**（实测最活跃与较不活跃的对象之间可差三个数量级）。预分配会让一个分片跑完闲置、另一个永远追不上。
> **推翻条件**：工作量分布被实测证明已经均匀化——实际上不可能，**这是被观察对象的性质，不是系统的性质。这条基本不该翻。**

> **换实现语言**
> **推翻条件**：某个**具体热点**被实测证明达不到记录门槛（丢帧 / 延迟超标），**且瓶颈经 profiling 定位到语言运行时**，而不是 IO 或设计缺陷。届时**只针对那个热点**换运行时做窄范围对照，**不做全项目重写**。
> **不构成推翻条件**："某语言更快"这类一般性判断。

注意最后这条的结构：推翻条件不只说"什么时候可以重开这个话题"，还**预先限定了重开之后允许采取的动作范围**。这一句挡住的是"发现一个性能问题 → 提议整体重写"的经典滑坡。

## 三、几条写作纪律

**1. 新增方向性决策时必须同时写下推翻条件。写不出来的，说明这个决策还没想清楚。**

这条是整份文档的核心。一个没有推翻条件的"决定"通常是一个偏好。逼自己写下"什么会让我改主意"，会当场暴露出那些其实并没有想清楚的选择。

**2. "我觉得 X 更好"不是推翻条件。"大厂都这么做"也不是。**

推翻条件必须是可观测的事实：某个数字越过阈值、某个外部约定变更、某类故障**实际发生过**（不是"担心会发生"）。

**3. 有些决策的推翻条件就是"无"，而且要明说。**

比如"内容 ID 绑未压缩字节流"——若绑压缩字节，换一次编解码器等于换一遍所有 ID，历史全部对不上。这条是纯粹的技术正确性，**没有权衡空间**，推翻条件写"无"。

再比如"契约字段不改名"——**改名的收益永远低于契约变更的代价**。

明确写"无"，和没写，是两件不同的事。

**4. 当别处有措辞更松的同结论文档，在条目里点名，并说清以谁为准。**

真实例子：一份更早的研究报告把几个组件列为"暂缓、需触发指标才引入"的**开放候选**，措辞比决策日志松。条目里直接写：**两者结论一致（现阶段都不用），但以本文档为准**——那份报告成文于技术栈锁定之前。

不点名的话，下一个人会引用措辞更松的那份。

**5. 明确区分"已拍板"和"还没决定"。**

决策日志结尾单列一节"待拍板（还没有决定，不要当成已定）"，并指出这些待决事项的清单在别处。**别把"还没决定"误读成"已经决定"**——在一份全是拍板的文档里，这种误读几乎是默认的。

## 四、为什么和 AI 协作者一起工作时这件事更重要

文档自己给出的理由：

> **AI 每次对话从零开始。** 它能读到"已拍板，不要重新提议"，但读不到"当初否决的理由现在还成立吗"。

推翻条件正是把一个决定变成**对没有记忆的人也可审计**的东西。

还有一条配套的、很实用的做法：项目从一个被废弃的方案里单独挑出了一条规则保留——**"技术中立只在明确授权时适用"**。理由是它堵住了红队审查代理每一轮都重开语言选型 / 编排组件选型的口子。

> 对一个每次从零开始的评审者来说，"保持技术中立"会被执行成"每轮都把所有选项重新摊开一遍"。中立需要被限定范围，否则它会消耗掉评审的全部预算。

同一份规则文件里还留了一条硬约束：**给另一个评审工具读的入口文件必须软链到主规则文件，不能换成一份只有流程、不含实测硬事实的文件**。理由写得很直接：那样做等于让它瞎着做红队——它会丢失全部实测事实，然后给出**看起来合理、实则踩在已知坑上**的结论。

## 五、姊妹册：延后模块登记册

第二份文档管的是"功能上必须有、但当前不实做"的模块。它的立项理由是：

> 延后开发最大的风险不是"没做"，而是**做主线时没给它留位置**，等真要做的时候发现要改核心。

于是每条登记必须同时写清**四件事**，缺一不可：

1. **端口签名**（现在就要定死的接口）；
2. **挂载点**（它将来接在哪个模块上）；
3. **"主线现在必须为它做的"**——这是最重要的一栏。**如果这一栏是空的，说明还没想清楚，不要登记**；
4. **触发条件或恢复条件**（什么时候该做它）。

配套三条通用纪律：

- **端口先定，实现后补**；接口变更走契约流程（先改文档与契约文件，再改代码）。
- **每个端口的"空实现"必须是合法配置并跑通全部测试**（CI 门禁）。没有通知渠道、没有备份目标、没有智能层，系统都要能完整工作——**否则"延后"会变成"主线被半成品卡住"**。
- **延后不等于降级为可选。** 每一项都是功能上必须有的，只是时间上排后。

第 3 栏的实际产出很具体，而且都是"晚做就要回头改所有调用点"的那类：

- 告警必须是**结构化的意图对象**（severity / category / 事实列表 / 建议动作 / **去重键**），不能是格式化好的文本——否则将来换投递渠道要重写全部告警点，而去重键晚加要回头改每一个调用处；
- 备份回执必须存 **manifest 自身的哈希**（不只是载荷的）和**相对路径**（换挂载点不失效）；"能不能删本地"的四个条件必须在备份模块做完之前就完整实现，因为删除的正确性依赖备份，**不能等备份做完再补**；
- 可达性探测的粒度必须**细到主机名**——否则探针打首页会得出"某站点可达"的错误结论，而真正取数的那个主机名其实是不通的（这是一条实测教训）；
- 智能层只留接口，但主线现在就要做**断言失败的结构化记录**，因为那是将来诊断的唯一输入面，**缺了就只能让模型猜**——而且它本身对人也有用。

还有两条写法上的纪律值得单独记：

**登记册必须写下当前真实敞口，而不是"已规划所以已解决"。** 备份那一条明写：**在这个模块做完之前，系统是单副本的。一块盘坏掉，那段数据归零。**

**禁止把"还没想好怎么做"的东西登记成延后模块。** 延后的前提是**已经想清楚它长什么样**，只是不现在做。想不清楚的属于另一类，该留在"待实测收敛"的清单里。

## 六、附：怎么用数字杀掉一个技术上可行的设计

决策日志里最有教学价值的一条，是砍掉一套完整的多代理协作控制面（任务立项 → 独立工作区 → 合并请求 + CI → 交叉复核 → 人工合并，外加一个本地协调器做租约与围栏）。

它**技术上能跑**。三个数字否决了它：

| 数字 | 含义 |
|---|---|
| 协调器任务表 **0 行** | 从建库至今没有承载过任何一个真实任务；它要防的"多代理互相踩"从未真实发生 |
| 走该控制面的任务 **0 个提交** | 而同一时段绕过它的直接开发产出了 **11 个提交** |
| 负责人介入次数 **0 → 10+/天** | 每个合并请求都要他做工程判断，而他不是工程背景 |

补刀来自它自己的设计文档：同一台机器上的同一个用户可以直接改协调器的数据库，**所以它不是恶意代理之间的安全边界**——它只防正常客户端的误并发，而单人单机每次只跑一两个代理时，误并发本就基本不存在。

**但被砍掉的方案里仍然有三样东西被单独摘出来采纳**，且与它原本捆绑的流程完全解耦：

1. 一个基线校验：**声明的基线提交必须等于真实的合并基**——挡的是"用分支中途的提交伪装基线"。这是唯一一条防自动化代理自我美化的实质检查。
2. **额度准入四态**（运行 / 排空 / 暂停 / 未知），其中**未知必须 fail-closed**。
3. 前面提到的"技术中立只在明确授权时适用"。

> **砍掉一个设计不等于扔掉它。** 一个技术上跑得通的方案里，几乎总有一两个与它的流程无关的机制值得单独收编。把"整体否决"和"逐条收编"分成两个动作做。

## 七、可迁移的结论

1. **决策日志记的不是"为什么"，是"什么会让这个决定失效"。** 写不出推翻条件就是还没决定。
2. **同时写下"不构成推翻条件"的那几句**，它们挡住的是最常见的重提理由。
3. **推翻条件可以顺带限定重开之后允许的动作范围**，避免"发现一个小问题 → 提议整体重写"。
4. **推翻条件为"无"的决策要明说"无"。**
5. **延后一个模块，必须同时写下主线现在为它做什么；这一栏为空就不许登记。**
6. **空实现必须是合法配置且能跑通全部测试**，否则延后会变成阻塞。
7. **延后项要写清当前真实敞口**，不要用"已规划"掩盖"当前没有"。
8. **否决一个方案时，先把里面可独立收编的机制摘出来再扔。**
