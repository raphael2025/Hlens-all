# 常驻流不是有界任务：一个两万行实现被废弃的真正原因

一个约 2.2 万行的分布式采集器实现，可靠性骨架相当成熟——内容寻址的不可变原始数据闭环、带围栏的持久租约、主节点身份/纪元防脑裂、去重即证据的规范化账本、原子归档与四条件删本地。测试写得也好：全仓注入时钟、没有一处 `sleep`。

它被整体废弃了。**不是因为语言选错了，是因为它用一个为"有界任务"设计的抽象去管"常驻长连接"。**

这是这批仓库里最值得外传的一条分布式系统教训。

---

## 一、那个抽象本身是对的

它的 worker 生命周期是教科书级的：

```
① 先尽力上传本地盘上所有未确认的残留数据（best-effort，一块坏盘不能让整节点罢工）
② 有本地残留任务就先做，没有才去领新活
③ 同步心跳，确认租约还在自己手上
④ 若主节点侧的 checkpoint 已标记「数据已确认」→ 直接完成，绝不重采
⑤ 启动续租守护
⑥ 若本地 checkpoint 已标记「已封存」→ 跳过采集，直接进上传
⑦ 否则：采集 → 封存 → 写【仅本地】checkpoint
⑧ 上传 → 校验每一块都已被中心确认
⑨ 停续租守护 → 补一次同步心跳 → 写【中心】checkpoint → 完成
```

配套的几条纪律，换任何语言重写都该照抄：

- **续租周期 < TTL/2，单次续租请求超时 < 续租周期**。理由写在注释里：一次挂死的心跳不能吃掉整个租约窗口。
- **后台续租与前台提交绝不并发使用同一个租约**。收尾必须先确认后台协程已退出，再补一次同步心跳，才允许写 checkpoint / 完成。
- **失去租约必须先落盘、再抛错**。顺序反了，进程崩在两者之间，重启后旧 owner 会"复活"并继续写。
- **两级 checkpoint 语义必须分开**：本地那份只说"我已经把数据封成不可变块了"（含本地盘路径，用于重启后不重复调用外部 API）；中心那份只在中心已经出具回执之后才写，且必须剥掉本地路径。于是"中心有已确认 checkpoint" ⇒ 数据一定已在中心，接管者看到它可以直接完成，不必重采。
- **三元围栏**：owner + token + 单调 generation，三者缺一不可。只有 owner 会被节点 ID 复用击穿；只有 token 无法表达"第几代"；只有 generation 无法防伪造。

这一整套对一个"跑十分钟、有明确终点、会推进游标、会烧配额"的任务来说是正确的。

## 二、它被用错的地方

同一套 worker 也被用来管常驻 WebSocket 流。于是这条规则被一起继承了下来：

> **续租一旦失败（任何原因，包括一次网络超时）→ 立刻取消采集上下文。**

注释里写得很明白，而且对有界任务是对的：「在一次失败的续租之后继续采集，有产出一份过期租约下的结果的风险。」

但把它加在常驻流上，后果是：

> **主节点抖一下 = 所有交易所的爆仓流与增量流同时断。**

三个层面都错了：

1. **爆点相关**。一次中心侧的抖动不是影响一个任务，是影响全部常驻流。故障域被抽象本身放大到了整个机队。
2. **损失不可逆**。实时推送流没有回补接口——断线那一刻的数据就永久没了。有界任务停了可以重跑，常驻流停了没有"重跑"这回事。
3. **方向反了**。中心失联时，系统最该做的事是**继续录**，而不是停手。

这个线自己的架构文档其实承认了这点（"中心失联后连续流会在续租失败时停止"），也设计过替代方案，只是没来得及实现。

## 三、根因：没有问"租约到底买来了什么"

把租约当成一个通用的"所有权"原语，是这次失误的全部来源。正确的问法是：

> **租约买来的只有两样东西：① 不超发限速预算 ② 不让两个 owner 重复推进同一个有状态游标。**

拿这两条去对常驻 WS 连接：

- 长连接几乎不占请求配额 → 第 ① 条不沾边；
- 它没有游标，只有**连接代（connection epoch）** → 第 ② 条不沾边。

**两条都不沾边，那么对它上租约是纯亏**：所有的故障模式照单全收，一样好处都拿不到。

这个检查法可以直接外用：**在把任何协调原语（租约 / 锁 / 选主 / 事务）套到一类负载上之前，先写下它买来了什么，再逐条确认这类负载真的需要。** 不需要的那部分，代价不会消失——它会变成一类你本来不必有的故障。

## 四、同一个仓库里的第二个耦合错误

规范化账本（派生层）的摄入被放在了原始数据接收的**同步路径**上：派生层失败 → 整个上传返回 5xx → 工作节点认为传失败。

后果是同一个形状：**下游一个小 bug 把上游采集堵死。**

由此得到的规则被写进了新一代的模块依赖约束，并且用测试钉死：

> **原始层不可回补，派生层随时可重算。让可重算的挡住不可回补的，方向是反的。**

具体做法：接收层不 import 任何派生层；回执不依赖派生层是否成功；派生层改成可重放的异步消费者，按内容 ID 幂等，可以随时全量重算。这条用"子进程真 import 一次 + 静态扫描"两道验证守住，而不是靠代码评审时的自觉。

## 五、替代形态：双控制面

重写之后，系统被明确劈成两半——**这是压过其余所有决定的那个决定**：

| | 常驻流面 | 有界任务面 |
|---|---|---|
| 管什么 | 各所爆仓 WS、盘口增量、成交流 | 快照轮询、窗口重拉、到期前抢采、地址级回补 |
| 怎么分派 | **版本化 feed 指派**（声明式意图），中心下发、**工作节点持久化** | **工作拉取**：短事务行锁 + 三元围栏租约 |
| 中心失联 | **在宽限期与本地盘配额内继续采**，产出的数据块标记"控制态不确定" | 租约到期即停手，不再领新活 |
| 重复的代价 | **可接受** | **不可接受**（双倍烧出口限速预算） |
| 靠什么保证正确 | 不要求唯一，只要求**可归因**（节点标识 + 连接代进事件信封） | 三元围栏（owner + token + generation） |

中心恢复之后，由一个对账器接纳 / 去重 / 隔离离线期间产出的数据。

**这个形态是唯一能同时满足"主节点可以死"和"不能重复烧配额"的解**：主节点挂了，常驻流继续录（不丢不可回补的）；有界任务自然停摆（只丢可延后的）。

## 六、让这一切成立的那条不对称性

常驻流面敢于放弃唯一性，全靠一条底层性质：

> **原始数据块的 ID ≡ 其内容的 SHA-256。** 所以重复上传天然幂等——同内容 = 同 ID = 同路径，不需要任何去重表。

由此：

> **重复是免费的，缺口是永久的。**

这个不对称性决定了所有取舍的方向。一旦重复免费，"防止重复采集"就不再是需要用独占所有权去买的东西，常驻面才可以只要"可归因"而不要"唯一"。

配套还有一条实现细节值得记：**WAL 段与数据块一一对应，封存时读段文件而非读内存**。于是崩溃后重封会得到逐字节相同的载荷 → 同一个 ID → 幂等命中。"允许重复"在实践中反而不产生重复。

## 七、什么情况下才该把租约加回常驻流

这条拍板是带推翻条件的：

> 出现一类流，**既是常驻长连接，又会消耗请求配额或推进有状态游标**。届时该类流需要**单独建模**，而不是把整个常驻面改回租约。

注意后半句。抽象用错的修法是"给用错的那一类换建模"，不是"把整个面倒回去"。

## 八、可迁移的结论

1. **在套用任何协调原语之前，写下它买来了什么，逐条对照这类负载是否需要。** 不需要的部分会变成纯粹的故障面。
2. **有界任务与常驻连接是两类负载，不要用一个控制面管。** 它们对"中心失联"的正确反应方向相反：前者停手，后者继续。
3. **抽象用错的代价不是局部的，是相关失效。** 一个租约打嗝会同时掐断全部流——这个爆点半径是抽象本身给的。
4. **让可重算的挡住不可回补的，方向永远是错的。** 派生层不得出现在原始层的同步路径上，并用测试钉死依赖方向。
5. **内容寻址把"重复"变成免费之后，很多独占性需求会自己消失。** 先找能让重复变便宜的性质，再决定要不要买独占。
6. 一个成熟的可靠性骨架 + 一个错位的负载模型 = 整体报废。**骨架值得考古挖走，负载模型不值得。**
