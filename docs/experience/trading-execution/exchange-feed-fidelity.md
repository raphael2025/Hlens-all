# 交易所数据流保真度：你收到的不等于市场发生的

做行情采集的人有一个默认假设：**只要我连上了、没断线、没丢包，我拿到的就是全量。**

这个假设是错的，而且错得很系统、很难发现。下面是在七家交易所上逐条实测之后得到的结论，以及它们对下游研究口径的影响。

---

## 一、最核心的一条：降采样发生在交易所内部，多点冗余修不好它

以公开强平（爆仓）流为例。

某家头部永续交易所的官方文档明确写着：其强平订单流 **"不再推送实时订单数据，改为以每秒最多 1 单的频率推送快照数据"**。

这意味着：级联行情下一秒钟可能有上千笔强平，而 WebSocket 只给你 1 笔。**该交易所侧的爆仓额天然被严重低估，且低估倍数随行情烈度非线性放大**——平静期接近无损，踩踏期可能差一个数量级。

更狠的是方法学还会变：同一家交易所曾把这个"每秒一单"的选法从**取该秒最新一单**改成**取该秒最大的一单**。这一改，被扭曲的就不只是条数，**分布本身也失真了**——系统性偏向保留大单、吞掉小单。

另一家交易所的实测结果更糟：**只收到真实强平的 29.7%，整体低估 3.4 倍**，而且低估随烈度非线性恶化：

| 该秒真实笔数 | WS 捕获率 |
|---|---|
| 1 笔 | 99.0% |
| ≤ 3 笔 | 42.4% |
| ≤ 10 笔 | 16.9% |
| > 10 笔 | **6.3%** |

**正好在最需要数据的时刻丢得最狠。**

### 为什么多点冗余测不出来

直觉上，开两条独立连接互相比对，就能知道有没有丢。实测：

- 两条**完全独立**的连接、12 小时、1293 个事件，**交集 1293，两边各自漏 0 条**，连交易所时间戳都逐条一致；
- 另一家交易所两条连接互比，分歧同样为 **0**。

而真相是它丢了 70%。

> **原因很简单：降采样发生在交易所内部扇出之前，所有订阅者拿到的是同一份已经被砍过的流。**
>
> **⇒ 多点互比只能测「断没断线」（可用性），绝不能用来测「全不全」（保真度）。它会稳定地误报「我们没丢」。**

唯一能测保真度的手段是**换模态对照**：WebSocket 对 REST，或者对一家已确定全量的交易所。这两件事（可用性 vs 保真度）在设计和文档里必须彻底分开写。

### 下游口径要求

1. **禁止把各所数据直接跨所加总当"全市场总量"**——这是几乎所有第三方面板的通病，量级错误且随行情烈度漂移。
2. 每条事件必须带一个 **`feed_fidelity` 维度**，下游聚合按该维度分组，**不允许混算**。取值至少要能区分：全量 / 每秒取最大 / 每秒取最新 / 按比例丢弃 / 部分流 / 未知。三值或四值的取值域表达不了"方法学变更"和"丢弃比例随烈度变化"这两种情况。
3. **锚定一家确定全量的交易所**，用它反推其他家的低估系数（按波动/成交烈度分层）。这本身就是一个可发表的方法学结果。

顺带一提：查了六家商业数据商的文档，**无一说明其数据来自哪个流，也无一提及这个节流问题**。买数据同样绕不开这个坑。

## 二、去重键的碰撞会静默删除真数据

跨所归一化时，很自然会构造一个内容去重键：`来源 + 合约 + 时间 + 价 + 量`。

**这个做法在某些交易所上会静默删除真实记录。**

一家交易所的 REST 返回中时间戳只到**秒级**。同秒、同价、同量的多笔强平，在级联行情里是常态。实测：

- 平静行情下即已静默删除 **0.715%** 的真实记录；
- 按碰撞概率平方放大，**每合约每秒 50 笔时删掉 19.3%，100 笔时删掉 34%**；
- 又是"最需要数据的时刻删得最狠"，而且**事后完全无法察觉**。

全量实测五家交易所的结果：

| 交易所 | 样本量 | 该键静默删除率 | 同(合约,秒)最多 | 拥挤秒记录占比 |
|---|---|---|---|---|
| A | 62,834 | 0.0000% | 2 | 3.31% |
| B | 18,548 | 0.0000% | 13 | 2.85% |
| **C** | 3,955 | **0.0253%** | **78** | **73.12%** |
| D | 8,788 | 0.0000% | 2 | 3.14% |
| E | 小样本 | 样本不足 | 7 | — |

**必须读懂这张表的因果**：

> A 和 D 的碰撞率是 0，**不是因为键设计得好，而是因为它们的流被降采样了**（每秒最多 1~2 条，当然不碰撞）。
>
> **C 是唯一确定全量的一家，于是成了唯一实测出碰撞的一家。**
>
> ⇒ **碰撞率低是降采样的副产品，不是设计的胜利。** 绝不能拿 A 的 0% 去论证"内容去重是安全的"——那等于用"我们收到的数据本来就不全"来证明"我们的去重不会丢数据"。

还有一个反直觉的发现：原以为某家交易所的订单 ID 字段"天然唯一、可以直接当键"，实测 62,834 条事件里**含该字段的为 0 条**——文档里有的字段，推送里可以根本不出现。

**通用规则**：

> 凡去重键里出现"时间 + 价 + 量"而没有交易所原生唯一 ID 的，**必须先量化碰撞率再定稿**，不能想当然认为组合足够唯一。
>
> 没有原生 ID 时，必须引入**同键序号**（按该键分组后的批内序号），而不是直接去重。
>
> 碰撞造成的是**静默的真数据删除**，比重复入库危险得多——重复能事后发现并清理，删掉的永远找不回。

## 三、跨所字段语义不同构，禁止直接拷贝

这一条听起来很基础，但它是最常见的静默错误来源。

以"强平方向"为例，五家交易所的表达方式各不相同：

- 有的给的是**强平订单的买卖方向**（SELL ≈ 多头被强平）；
- 有的直接给**仓位方向**字段；
- 有的用 `Buy` 表示**多头**被强平（与第一种恰好相反）；
- 有的用**数量的正负号**表示方向。

> **normalize 时必须按"仓位方向"重新映射，禁止直接拷贝 `side` 字符串。**

数量单位同样互不相同：**币 / 张 / 报价名义**三种都有。用"张"的交易所必须乘各自的合约乘数才能得到币量，而**合约乘数每个合约不同，必须从 instruments 端点取，不能硬编码**。

还有一些只能靠实测发现的坑：

- 某家 REST 返回的数组里**只有第 0 个元素是真实记录**，后面十几个都是字面的 JSONPath 引用对象（`{"$ref": "$.data[0]"}`）。这是服务端序列化产物，不是客户端解析问题。真实明细藏在 `data[0]` 的子数组里。消费端必须先清洗。
- 同一条记录里 `time` 是 int 毫秒而 `ts` 是字符串毫秒，两者同值——但类型不同。
- 某家的 WebSocket 订阅**根本不是公开的**（无鉴权订阅返回 "authentication required"），而文档看不出来。
- 某家没有公开 REST 端点，请求返回的是**裸 404、没有 JSON 错误体**——fetcher 必须容忍非 JSON 响应，否则会在解析处崩溃而不是走错误分支。
- 某家的 404 会先被 CDN 的 WAF 拦成 403：**用默认的 curl UA 看到的是 403，换成浏览器 UA 才看到真实的 404**。用错误码判断"端点是否存在"时，先确认你看到的是源站的响应。
- 某些采样脚本会**截断长列表**再存盘。不能用截断样本推断"某资产未上市"——要看原始长度字段或查实时 API。

## 四、限流预算：记账单位是权重，不是请求数

### 4.1 串行吞吐远远打不满预算

一个典型的按权重计费的 REST 接口，理论上单 IP 每分钟 1200 权重、某个权重为 2 的端点就是 600 次/分。实测：

| 项 | 结果 |
|---|---|
| **串行实际吞吐** | 仅 153 次/分，**只用掉 25% 的预算**（p50 延迟 393 ms、p95 793 ms） |
| **打满所需并发** | 8~10 并发（8 线程实测 606 次/分，正好打满） |
| 再高 | 只会撞限速，换不到任何吞吐 |

**结论**：容量规划要按"权重预算 ÷ 单次权重"算理论上界，但必须用实测并发度校准，否则会把一个需要 2 个出口 IP 的任务排给 1 个。

### 4.2 "无条数上限"的历史端点是真正的成本大头

分页端点里，有上限的那些（例如单页 2000 条、总量 1 万条封顶）反而安全。**危险的是那些没有总量上限的历史端点**：一个持仓两年、二十个品种的活跃地址，光资金费记录就可能有三十多万条，相当于独占二十几个 IP-分钟。

这类端点通常不在任何人的预算表里，因为大家只统计"每分钟调多少次"，不统计"每次返回多少条"——而历史类接口**按返回条数加权**（例如每 20 条 +1 权重）。

> **记账单位必须是权重，不是请求数。**

### 4.3 只读查询可能没有"自己触发限流"的机制

在某些设计里，地址级/账户级的配额**只针对交易动作**（下单/撤单），只读查询完全不受地址级限制。后果是：一个数据量巨大的重地址不会"自己触发 429"，它会**吃光整个出口 IP 的权重预算，拖慢该 IP 上所有其他采集任务**。

这类跨任务的资源污染在监控上表现为"某些无关的采集任务莫名变慢"，很难定位。预算必须在出口 IP 这一层统一分配。

### 4.4 429 有两种，处置方向相反

这是最值得记住的一条：

| 响应体形态 | 是什么 | 正确处置 |
|---|---|---|
| 应用层的 JSON 响应（可能是 `null`） | **应用层权重限速器** | 退避权重 |
| 反向代理返回的 HTML 错误页 | **连接速率限速器** | **降并发**（退避权重毫无用处） |

实测：并发 64 时，一个权重只有 2 的轻端点**3.2 秒**就撞上后者，而权重预算还远远没花完。

这是"并发不要开太高"的**第二个独立理由**——超过某个并发度，多开的并发一点吞吐都换不到，只会换来一类你以为自己已经处理过、实际处理方向完全相反的错误。

### 4.5 当接口不返回限流头时，怎么测一个端点的权重

有些 API **根本不返回任何限流头**，"对比调用前后的用量头"这条路走不通。只能烧到 429 反推，并用一个**已知权重的端点做标定**：

| 端点 | 并发 | 首个 429 时的成功次数 | 用时 |
|---|---|---|---|
| 已知权重 = 2 的端点（标定） | 16 | 1,496 | 32.2 s |
| 待测端点 | 16 | **163** | 3.9 s |
| 待测端点（复现） | 64 | **164** | 2.3 s |

若待测端点权重也是 2，并发 16 下应跑到 1400 次以上才 429；实测只有 163 次，**差 9 倍** → 点估计权重约 16。

> **两条记账纪律：**
> 1. **点估计 16，记账按上界 20。** 预算估计的方向必须是**高估自己的消耗**。
> 2. 同一次实测里观察到该出口的实际容量比文档宽约 2 倍（约 2,350~2,990 权重/分 vs 文档 1,200）。**记账仍按 1,200**——单出口的单次观测不足以改写全局假设，而**高估自己的预算是最危险的方向**。

## 五、通过 CDN 分发的数据：你看到的版本已经旧了

有一类数据只能从 CDN 拿（POST 接口里根本没有对应的查询类型，**CDN 是唯一取数路径，没有备用通道**）。这类数据有几个特有的坑：

- **边缘缓存实测约 53~54 分钟才回源**。加随机参数、加 no-cache 头、直接钉不同的边缘节点**全部无效**，返回的是同一份缓存 → 单个出口一天最多只能看到约 27 个版本。
- **不返回 gzip**：即使带 `Accept-Encoding: gzip` 也没有 `Content-Encoding`，每次固定几十 MB 入站流量。支持 Range 请求。
- **正文里没有任何时间戳**——只有 ETag 和 Last-Modified 在响应头上。**必须把 ETag + Last-Modified + 抓取时刻三者一起入库**，否则快照永久失去时间锚点。
- 采集方式应该是：定期 HEAD + `If-None-Match` 探版本，**变了才整包下载**。

### 一个会把结论带偏半小时的测法陷阱

实测的 HEAD 响应里带着 `Age: 1720` —— 我们看到那个版本时，它**已经在边缘节点躺了 28.7 分钟**。

如果"版本变更日志"只记录"我们探到的时刻"，算出来的是**边缘缓存的刷新节奏**，而不是**源站的出版节奏**。两者能差半小时——而这个差距恰好就是"15 分钟一版"与"53 分钟一版"两种说法之间的量级。

> **版本变更日志必须同时记 `last_modified`（源站版本时刻）+ `observed_at`（观测时刻）+ `age_s`（缓存年龄）三者。只有基于 `last_modified` 的间隔才能用来下频率结论。**

## 六、"空结果"不一定是失败

采集地址级数据时实测存在这样的地址：排行榜显示日成交额数亿美元，但成交查询在 24/48 小时窗口内均返回**空数组**，账户价值接近零。

> **必须把它当作正常终态，不能当失败重试**——否则会在重试队列里无限烧配额。

相关的一条：分层依据不能用排行榜上那个大数字。实测某个榜首地址在排行榜上报的账户价值与它实际的合约权益**相差六个数量级**（其余是自发行代币）。分层必须用你真正关心的那个口径去取。

## 七、超时与未知执行状态：唯一不能重试的场景

这一条是从交易侧（而非行情侧）来的，但性质相同——**收到的响应不等于真实发生的事。**

`HTTP 200 不代表订单成交`；反过来，超时和 5XX 也**不代表订单没成交**。

正确处理顺序：

1. 记录完整的 client order ID、合约、方向、数量、时间戳；
2. 查询订单状态；
3. 查询用户数据流里是否出现了对应的成交事件；
4. 查询成交明细和账户余额；
5. **只有在明确确认未执行时**，才决定是否重试。

> **盲目重下是交易系统里代价最高的一类 bug。** 策略层永远不要直接依赖单一 REST 响应判断成交。

配套：至少持久化 `clientOrderId`、交易所订单 ID、成交 ID、产品类型、合约、订单状态、执行类型、手续费资产、时间戳、请求权重、错误码和**原始响应**。私钥、签名原文和 API 凭据**不得写入日志**。

## 八、采集器的验收门槛怎么写

数据质量不能靠"跑起来了"来判断。下面是一份真实用过的 16 小时验收门槛的结构，它的价值在于**每一行都是可以自动判定的**，而且**不达标就不许进入下一阶段**。

**稳定性**（必须全部满足）：

| 指标 | 门槛 |
|---|---|
| 进程崩溃 / 服务重启次数 | 0 |
| 内部队列丢弃计数 | 0 |
| healthcheck 失败次数 | 0（网络抖动导致的短暂 stale ≤ 2 次，**且能对应到 gap 记录**） |
| 内存 RSS | 末尾 vs 第 1 小时 < +50%，且无持续增长趋势 |
| 订单簿重同步收敛时间 | 每次 < 30s（网络抖动除外，**需有日志证据**） |
| 未解释的 gap | **0**——每条 gap 必须对应日志中的明确原因 |

**数据完整性**（必须全部满足）：

| 指标 | 门槛 |
|---|---|
| 逐笔成交 ID 跳号 | 0（gap 期间除外） |
| K 线连续性 | 无缺口，**且与 REST 抽样比对零误差** |
| 深度快照间隔 | ≥ 99.5% 恰为标称间隔；买价 < 卖价 100%；档位数 100% |
| 低频轮询流 | 无空洞（gap 期间除外）、无重复时间戳 |
| 各流每小时行数 | 无异常为零的小时 |

**分析能力**（验证数据真的支撑得起信号设计）：

| 指标 | 门槛 |
|---|---|
| 分钟级 CVD | 可计算；价格大幅波动的分钟内，CVD 方向与价格方向一致率 > 70% |
| 强平爆发 | 能识别出爆发事件，**并在逐笔成交和深度快照里看到对应的微观痕迹** |
| 深度失衡 | 可计算，分布合理（非常数、非全 null） |

这份门槛里有三个设计值得复用：

1. **"未解释的 gap = 0" 而不是 "gap = 0"。** 网络会抖，重点是每一次中断都有对应的记录和原因，而不是假装没发生过。
2. **交叉验证写进门槛**（K 线与 REST 抽样逐根比对、强平事件与逐笔/深度互相印证）。只测"有没有数据"不够，要测"数据之间自洽不自洽"。
3. **"分析能力"独立成节。** 稳定性和完整性全绿，并不意味着这份数据支撑得起你打算做的研究。CVD 一致率这种指标回答的是"这份数据里真的有信号吗"。

最后是不达标的处理流程，它必须提前写好：**定位原因 → 修复 → 补测试 → 重跑（轻微问题跑短周期，严重问题跑完整周期）→ 重新评估。** 不许"这次差一点，下次注意"。

## 九、一句话

> 采集系统的默认假设应该是"我收到的是不全的、语义是不同构的、时间锚点是丢失的"。
> 把这三件事**各自设计一套可以被实测证伪的检验**，比把采集器写得更快更稳重要得多。
