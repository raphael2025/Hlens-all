# 多 Agent 编码工作流的编排设计

当一个项目同时用上好几种 AI 编码 Agent（不同厂商的 CLI、不同的模型档位），最先失控的不是代码质量，而是**谁能干什么、谁说了算、谁来验收**。

常见的失败形态有三种：

- **万能 Agent**：一个会话既做需求分析又做架构又写代码又自己宣布验收通过——于是没有任何一步是被独立检查过的；
- **按领域分角色**："前端 Agent"、"后端 Agent"——但这是**项目领域**的划分，不是**能力**的划分，于是同一个 Agent 被派去做它不擅长的事；
- **项目经理被代码细节淹没**：负责统筹的那个会话为了"搞清楚情况"读了几万行 diff，上下文爆掉，之后它的判断就开始漂。

下面这套结构是为了同时解决这三个问题。

---

## 一、四层结构，每层只做一件事

```text
用户（产品经理）
  ↓  只提需求、做产品决策
接口层 CLI（只转发需求与反馈）
  ↓  不直接调用执行 Agent
控制层（项目经理）
  ├─ 需求入口 / 阶段闸门 / 最终汇报
  └─ 独立的需求分析者（范围、验收标准、任务包）
  ↓
运行时层（动态会话、队列、工作区、生命周期）
  ↓  按任务能力创建
执行 Agent（架构 / 研究 / 实现 / 操作 / 验证 / 审核）
```

关键的两条边界：

1. **接口层不在运行时拓扑里**，它不直接调用任何执行 Agent。它只向控制层转发需求，然后等待澄清问题、阶段结果或最终结果。
2. **控制层不写代码**。这不是洁癖，是为了**保护它的上下文**——项目经理一旦开始读实现细节，它的判断质量就开始下降。

---

## 二、按能力选 Provider，不按领域分角色

这是整套设计里最重要的一条：

> **角色不是固定的"前端 Agent"或"后端 Agent"。先判断这个工作项需要什么能力，再选择一个明确的 Profile；Profile 同时固定 Provider、基础角色、模型、权限边界和工作区模式。**

一份典型的 Profile 表长这样：

| Profile | 默认用途 | 工作区 | 硬约束 |
|---|---|---|---|
| `clarification_broker` | 把阻塞问题压缩成最少的几个问题 | 主工作区，只读 | 不执行项目任务 |
| `plan_reviewer` | 独立审查任务包是否可执行 | 主工作区，只读 | **不代替 planner 重写整个计划** |
| `*_architecture` | 架构、模块边界、接口契约、技术文档 | 独立 worktree | **只做文档，不写代码** |
| `*_review` | 独立的代码 / 方案 / 证据审核 | 主工作区，只读 | **不修改代码** |
| `*_research` | 技术栈、实现可行性、深度技术研究 | 独立 worktree | 按任务包限定范围 |
| `*_implementation` | 复杂逻辑与代码实现 | 独立 worktree | **必须先通过计划闸门** |
| `*_operations` | 搜索、批处理、迁移、格式化、环境操作 | 独立 worktree | **不自行改变设计** |
| `*_verification` | 测试执行、运行检查、机械验证 | 独立 worktree | **只按验证合同执行** |
| `round_checker` | 汇总整轮证据并判定通过 / 返工 | 主工作区，只读 | **不修复问题** |

注意每一行的"硬约束"列。它们之所以重要，是因为**Agent 的默认倾向就是越权**：审核者会顺手改代码，架构者会顺手写实现，验证者会顺手"帮你修一下"。越权本身不算坏事，坏在**它同时销毁了这一步的独立性**——一个改过代码的审核者，不再是一个独立审核者。

> **规则：如果一个工作项同时含架构和编码，必须拆成两个会话，不得让同一个会话既定契约又写实现。**

Profile 是**能力模板**，不是项目领域清单。同一个项目阶段可以创建多个不同 Provider 的会话，但**每次创建都必须写明选择理由**。

---

## 三、能力 → Provider 的映射

不同 Provider 的默认能力边界是可以（也应该）写死的。一份示例：

- **偏规划与审查的 Provider**：适合架构、模块边界、接口契约、任务拆解、技术文档、计划审核、代码审核、证据审核。硬约束：**可以读代码，但不编写或修改代码**。
- **偏实现的 Provider**：适合技术栈深挖、复杂逻辑、跨文件实现、代码修复、实现风险分析。约束：**编码前必须有已批准的任务包**，不得自行扩大产品范围。
- **偏机械操作的 Provider**：适合资料搜索、批量编辑、迁移、格式化、环境检查、测试运行。约束：**不得自行改变核心设计**；搜索结果必须附来源，操作结果必须附命令和输出。

选择算法就七步：

1. 把需求拆成**可独立验收**的工作项；
2. 给每个工作项标记主要能力：规划 / 架构 / 研究 / 实现 / 操作 / 验证 / 审核；
3. 在配置里选匹配的 Profile；
4. 记录 **Provider 选择理由、文件权限、工作区模式**；
5. 一个工作项同时含架构和编码 → **拆成两个会话**；
6. 结果会影响下一阶段 → **必须增加独立 reviewer/checker**，不能由执行者自证完成；
7. 创建后**验证实际生效的 Profile / Provider / 模型 / 工作区**——不要相信你以为你创建了什么。

第 7 步不是多余的。用别名、角色名或临时模型参数绕过 Profile，是这类系统里最常见的静默错误：你以为派了一个只读审核会话，实际拿到的是一个有写权限的通用会话。**创建命令必须只有一种合法形态（显式指定 Profile），其他形态一律禁止。**

---

## 四、派工必填字段

任何动态会话在创建时必须同时指定这些，缺一项就不许放行：

- `task_id` 与所处阶段；
- 工作项内容和所需能力；
- **Profile、Provider 和选择理由**；
- **是否允许写项目文件**；
- 工作区、**文件所有权**和**禁止修改的范围**；
- 交付物、验收标准和**验证命令**；
- 失败 / 阻塞时应该返回给谁；
- 完成后的**释放策略**。

这张清单的作用类似于函数签名：它强迫派工者在派工**之前**就把"这件事算做完了没有"想清楚。实践中，写不出"验证命令"的工作项，通常意味着这个工作项本身没拆干净。

---

## 五、标准工作流与闸门

```
需求 → 需求分析（独立会话）→ 计划审查（独立会话）
     → 派工（控制层是唯一派工者）→ 执行（多个并行会话）
     → 逐项 checker/reviewer → 整轮 round_checker → 控制层决策
```

几个细节：

- **需求分析和计划审查是两个不同的会话。** 审查者的职责是判断"这个计划可不可执行"，**不是重写计划**——否则它就变成了第二个 planner，独立性消失。
- **控制层是唯一派工者**，不额外套一层 orchestrator。多一层转发就多一层信息损耗。
- **执行 Agent 只完成自己的工作项**，返回文件、命令、测试结果、风险和状态，**不宣称整个项目完成**。这句要明确写进 Profile 约束里，因为 Agent 天然倾向于给出一个圆满的总结。
- 阶段闸门要有**明确的失败路线**（修订 / 澄清 / 返工 / 换 Provider / 重规划），而不是只有"通过"这一条出路。

一份需求分析单模板里最该有的几节：**明确非目标**、**需要用户决定的事项**、**已执行的只读检查**、**时变事实及其来源日期**、**权限和凭据边界**、**失败与降级行为**。其中"明确非目标"和"需要用户决定的事项"是最容易被省略、也最容易导致返工的两节。

---

## 六、上下文与幻觉控制

这一节是整套设计真正的目的。

1. **控制层不承担深度实现**——避免项目经理的上下文被代码细节淹没。
2. **需求分析、执行、审核使用独立会话；执行者不能审核自己的结论。** 这是唯一能防住"我做完了，我检查过了，没问题"这种自证的结构性手段。
3. **每轮必须以文件、命令、测试或来源作为证据，不接受只有总结的"完成"。** 这一条的反面案例很具体：有子 Agent 报告过多年期的优秀回测结果，主流程独立复现之后发现结果完全失真。**任何来自另一个执行者（人或 Agent）的结论，在进入结论库之前必须由主流程独立复现。**
4. **长任务按阶段释放动态 Agent**：需要保留上下文时 park，不需要时 unload。一直挂着的会话既烧配额又会带着过期的上下文做判断。
5. **中断的会话不要原地恢复**：某些 Provider 的会话被中断后无法可靠恢复，正确做法是**从最近一次的任务包和证据重新提交**，而不是试图接上一个状态不明的会话。

---

## 七、一份统一的交接格式

所有 Agent 用同一个结构回报，这样控制层不需要为每个 Provider 写一套解析逻辑：

```text
状态：done | blocked | needs_rework
完成：...
证据/文件：...
执行命令与结果：...
风险与未决问题：...
建议下一步：...
```

在一个更轻量的项目里，同样的思路可以退化成写进项目约定文件（`CLAUDE.md` / `AGENTS.md`）的四条报告要求：

1. 做了什么（文件列表 + 一句话说明）；
2. 如何验证的（跑了哪些命令、结果如何）；
3. **未完成 / 存疑 / 偏离规格的地方，以及原因**；
4. 对规格本身的改进建议。

第 3 条是最有价值的一条。没有它，你收到的永远是"已完成"。

---

## 八、轻量版：不需要运行时框架也能用的分工

不是每个项目都需要一套动态会话运行时。同样的原则可以用最朴素的方式落地：

| 角色 | 职责 |
|---|---|
| 统筹（主会话） | 写规格、拆任务、派发、审核代码、汇总汇报 |
| 框架构建者（高能力模型） | 按规格构建底层框架、核心逻辑、关键算法 |
| 基础代码填充者（快模型） | 按规格填充边缘模块、样板代码、运维脚本 |
| 测试者（快模型） | 写单元/属性测试，跑测试，**报告失败与规格歧义** |

```
统筹写 SPEC ──▶ 建框架 ──▶ 填基础代码 ──▶ 测试 ──▶ 统筹审核 ──▶ 汇报
                  ▲                            │
                  └────── 失败 / 歧义 反馈 ─────┘
```

配套一个明确的 **Definition of Done**：lint 通过、类型检查通过、测试全绿且**不访问网络**、规格里的验收标准逐条满足（或在报告中说明未满足的原因）、关键路径有日志。

核心原则和重型版本完全一样：**写规格的、写代码的、验收的，不是同一个会话。**

---

## 九、一条安全纪律

多 Agent 系统有一个独有的泄露面：**Agent 沙箱的 home 目录**。

各家 CLI 工具把登录凭据（OAuth token、refresh token、账号标识）存在用户 home 目录下的配置文件里。当你为每个动态会话准备一个隔离的工作区，并且把 `$HOME` 指向工作区内的某个目录时，那些凭据就**落在了仓库目录里**。之后任何一次 `git add -A` 都会把它们提交上去。

同类的还有：会话回放日志、事件流、队列状态、provider 侧的本地数据库——它们体积巨大、无法检索、而且是**风险最高的一类文件**。

> **规则：**
> 1. **运行时状态目录从第一次提交开始就进 `.gitignore`**，而不是等到它长到几百兆才想起来。`.gitignore` 要写在创建这个目录**之前**。
> 2. 这条规则**必须跨仓库传播**。同一个人的多个仓库里，往往只有一部分写了这条排除规则——而漏掉的那个就是会出事的那个。
> 3. **运行时状态不是文档，不能作为经验提取的来源**。要沉淀的是"读完之后重写的结论"，不是原始会话流水。
> 4. 事后补 `.gitignore` **不能清除历史**。已经进过仓库的凭据，唯一正确的处理是**先轮换/吊销，再重写历史**。

---

## 十、一句话

> 多 Agent 编排的价值不在于"并行干得更快"，而在于**把"谁说了算"和"谁来证明"拆成了两个不同的会话**。
> 一个能自己宣布自己完成的 Agent 系统，再多的并行度也只是在更快地生产未经检验的结论。
