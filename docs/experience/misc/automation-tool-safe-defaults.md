# 自动化工具的安全默认值：会造成不可撤销后果的工具怎么设计

有两类小工具的失败代价远高于它们的代码量：

- **会对外产生不可撤销动作的**（发消息、下单、发布）——发错对象没有撤回键；
- **需要接触本机敏感状态的**（凭据、token 缓存）——泄漏一次就永久有效。

下面是这两类工具在实践中固化下来的设计习惯，以及一个"官方接口不存在时该怎么办"的具体案例。

---

## 一、当目标应用没有可用的自动化接口

### 1.1 背景：一个被版本升级打掉的常见方案

需求很简单：让脚本/agent 给桌面聊天客户端的某个联系人或群发一条通知。

过去的标准做法是用系统的 UI 自动化框架去遍历控件树，社区也有成熟的库。但目标应用的新版本是一次**完整的 Qt 重写，整个界面被绘制到单张画布上**，几乎不向 UI 自动化框架暴露任何控件——为旧版写的那个流行库在新版上直接不工作，而能工作的替代品是收费的。

> 这是一类值得单独记下来的坑：**"这个方案不行"的真正原因经常不是方案本身，而是目标应用换了渲染架构。** 判断依据应当是"控件树里还剩什么"，而不是"这个库最近有没有更新"。查清楚这一点，才知道是该换库还是该换路线。

### 1.2 换路线：像人一样操作

既然拿不到控件，就退到**模拟输入 + 屏幕 OCR**这一层：

```
找到窗口（含最小化到托盘）并强制置顶
  → 点击搜索框 → 粘贴名称（让应用自己做模糊匹配）
  → 截图结果区 → OCR 读出每一行的文字和坐标
  → 挑出正确目标 → 点击打开会话
  → 再 OCR 一次会话标题做复核
  → 粘贴消息 + 回车
```

两个降低依赖的选择：

- OCR 用**操作系统自带的离线识别能力**，不引第三方 OCR 服务——离线、免费、无网络出网面；
- 主程序只用标准库（通过 `ctypes` 调系统 API）+ 一个用于"感知"的系统脚本，**零第三方依赖**。

分工很清晰：系统脚本只负责"截图 + OCR，返回带**绝对屏幕坐标**的文本行"，主程序负责决策和操作。感知层和决策层分开之后，替换 OCR 实现不影响主流程。

### 1.3 防误发：三层，而不是一层

发错人是这个工具唯一真正严重的失败模式，所以防护叠了三层：

1. **区段过滤**——搜索结果里应用自己会分组（常用 / 联系人 / 群聊 / 聊天记录 / 文件 / 功能…），只匹配前三类。跳过"聊天记录/文件"避免把一条历史消息当成目标；跳过"功能"避免触发特殊弹窗。
2. **长度感知的模糊打分**——一个短的精确名称，应当胜过一句只是"包含了关键词"的长文本；整块"N 条相关记录"之类的聚合行直接跳过。
3. **打开之后再 OCR 标题复核**——会话标题字号更大、识别更可靠；**不匹配就直接中止，不发送**。

关掉第三层的开关存在，但在文档里明确标注"不推荐"。

> 通用形态：**用"先定位 → 再独立确认"两段式，而不是把匹配分数当成唯一凭据。** 第二次确认最好走一条和第一次不同的信息通道（这里是不同区域、不同字号的文本），否则两次确认会一起错。

### 1.4 默认值：dry-run 优先

- CLI **默认只预演**，必须显式加发送参数才会真的发出；预演会一路走到第三层复核并打印"将要发给谁、发什么"，只是不按回车。
- 作为 MCP 工具暴露给 AI 使用时，**预演参数默认为真**，调用方必须显式传参才会真的发送。文档里写明了理由：**当多个 agent 都能调用这个工具时，安全默认值比任何说明文字都重要。**
- 失败时返回结构化结果（失败原因 + 原始 OCR 文本行），让人能据此标定参数，而不是只给一个退出码。
- 退出码区分成功与失败，方便被脚本消费。

### 1.5 环境适配与踩过的坑

- **DPI 感知**：不同缩放比例下，固定像素常量会全部错位。做法是分类处理——列表区（搜索框、结果行）用"固定逻辑像素 × 缩放比例"，因为列宽是固定的；结果行**直接点 OCR 返回的实际坐标**，天然自适应；会话区和输入框按窗口尺寸比例定位。
- **前台锁**：系统会限制后台进程抢占前台，所以需要专门的唤醒 + 强制置顶逻辑（包括从托盘唤醒）。
- **脚本编码**：那个系统脚本包含非 ASCII 字符时，**必须存成带 BOM 的 UTF-8**，否则旧版 shell 会按本地代码页解析而报错。
- **频控风险**：UI 自动化比协议层机器人安全得多（它字面意义上就是在替你点击），但**高频批量发送仍可能触发风控**。工具定位因此写死为"低频告警/通知"，不是群发。
- **脆弱性要写在 README 里**：依赖屏幕坐标 + OCR，本质上比官方 API 脆弱；对方界面改版或布局异常就需要重新标定。把这句话写进"已知限制"，比事后解释便宜。

## 二、需要接触本机凭据的工具

另一类工具的需求是读取本机上其它应用保存的登录态，用来查询配额之类的只读信息。这类工具天生敏感——它要做的事，和凭据窃取在技术上只差一个意图。

固化下来的几条自律，全部写进 README 并在代码里执行：

1. **只读，不刷新，不落盘。** 读到的凭据只在进程内使用，既不触发刷新流程（避免影响原应用的登录态），也绝不写入任何文件或日志。
2. **绝不提交任何凭据文件。** `.env`、各类 `auth.json` / `credentials` 文件、以及任何解密结果，全部进 `.gitignore`，并额外加上通配安全网模式（`*api_key*`、`*.pem` 之类），**不是因为它们曾经被提交过，而是为了让它们不可能被提交**。
3. **README 必须显著标明"非官方 + 风险自负"。** 依赖的是未公开的本地存储格式和接口，随时可能变；使用者需要知道这一点。
4. **文档里只写"做了什么"，不写"怎么复刻"。** 研究笔记对自己有价值，但**具体的凭据存放位置、加密方案和解密步骤，不适合作为公开文档发布**——即便工具本身只读取使用者自己的凭据，这类细节的可复用方向是单向的。整理对外文档时，这部分整段略去。

> 判断标准可以很简单：**如果一段文档被一个心怀恶意的人读到，他能省下多少工作？** 省得越多，越不该公开。

## 三、通用小结

| 原则 | 具体表现 |
|---|---|
| 危险动作默认关闭 | 默认 dry-run；暴露给 AI 的接口默认预演 |
| 确认要走不同通道 | 匹配用搜索结果区，复核用会话标题 |
| 失败要可诊断 | 返回原始感知数据（OCR 行），不只返回错误码 |
| 脆弱点写进文档 | "依赖坐标+OCR，改版需重新标定"要主动写 |
| 敏感数据只读不留痕 | 进程内使用，不刷新、不落盘、不入日志 |
| 安全网先于事故 | `.gitignore` 通配模式是预防，不是补救 |
| 不发布可复刻的攻击细节 | 只写结论与自律，不写路径与解法 |
