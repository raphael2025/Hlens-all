# 按规格书实现一个系统：解读判定、边界清单与机器化的架构铁律

当输入是一份几十节、带条款编号的正式规格书，而不是一段口头需求时，实现过程中真正消耗精力的不是写代码，是**回答规格没说清楚的地方**。

这份文档记录一套已经跑通的做法：怎么组织"实现侧文档"、怎么处理规格的歧义、怎么把架构约束从"文档里的规矩"变成"CI 里的断言"，以及怎么诚实地交付一个部分完成的系统。

---

## 一、第一条规矩：实现文档不新增规则

实现侧文档的开头写死两句：

> 规格是唯一事实来源。本文件不新增任何规则；凡本文件与规格冲突，以规格为准。

这两句话决定了这份文档的定位——它记录的是**关键数据流设计、边界条件处理，以及实现过程中对规格的解读判定**，不是第二份规格。

为什么重要：一旦实现文档开始自带规则，系统就有了两个事实来源，而它们一定会在某次修改后分叉。分叉之后没人知道该信哪个。

配套的一条铁律是"**规则在文档不在注释**"：每个核心模块必须引用它所实现的条款号，行为的定义留在规格里。这条后面会变成一个可执行的测试。

---

## 二、把分散在多处的规定，收敛成一条规则

规格在三个不同章节分别规定了三种情况下的成交时点：信号产生后在哪根 K 线执行、日线收盘后在哪个小时成交、熔断确认后在哪根 K 线平仓。三处措辞不同、示例不同，其中一处还特别强调"不得使用与决策 K 线收盘同时间戳的那根开盘价"。

实现时的判断是：**这三条是同一条规则的三个实例**：

```
执行时刻 = 决策 K 线的 close_time + 一个固定延迟
```

因为一根 K 线的 close_time 等于下一根的 open_time，而"同时间戳开盘价"被明令禁止，顺延一根自然就得到规格里写的那个结果；日线那条代入之后得到的具体小时，与规格字面值精确吻合——**三处字面值同时被一条公式复现，就是这条归纳正确的证据。**

于是实现只留一个常量和一处计算，被多个调用方共用，四个出口分别被四个测试锁住。

> 通用做法：**当规格在多处给出看起来不同的规定时，先假设它们是同一条规则的不同实例，并尝试构造一个能同时复现所有字面值的统一表达。** 能构造出来，实现就少了三份可能分叉的逻辑；构造不出来，说明规格真的有内部冲突，应该回去提问而不是各写各的。

同一段推演还带出一个配套推论：**处理时刻的定义会影响哪些数据在同一个处理槽内可用**。把处理时刻定义成"K 线 close_time + 最小数据延迟"，才能让同时闭合的两个周期落在同一个槽里；若定义成"close_time"，较慢的那个周期要推迟一个槽才可用，成交时点就会比规格晚一格。**这种"定义差一点点、结果差一整格"的地方，值得在文档里单独写清推导，而不是只写结论。**

## 三、阶段次序：为什么某些顺序不能颠倒

核心决策管线被拆成编号阶段（接收交易所事实 → 摄入新可用数据 → 开盘排队订单 → 保护止损 → 持仓极值更新 → 移动止损重算 → 收盘估值与熔断判定 → 窗口重置 → 退出意图 → 入场意图）。

文档里对"为什么不能换顺序"给出机制级理由，而不是"按规格这么写"。两个例子：

- **数据摄入必须早于订单执行**：否则一个已经失效的意图会先被执行掉。
- **熔断判定必须早于窗口重置**：close_time 恰好等于周期边界的那根 K 线归属**旧窗口**。若先重置再判定，旧窗口的最后一根 K 线永远不会参与熔断判定——**而那恰恰是最可能击穿限额的一根。**

第二条还被做成了一个直接断言事件顺序的测试（审计日志里"熔断"事件必须早于"窗口重置"事件）。

> 只要某个顺序的理由是"否则会漏掉最危险的那个样本"，它就值得一个专门的测试，而不是一句注释。

## 四、防止"混源"这类硬约束，要在写法层面堵死

系统里有一张价源矩阵：信号用哪个价、权益估值用哪个价、止损触发判定用哪个价、移动止损丈量用哪个价、强平用哪个价，在不同产品形态下各不相同。规格的硬约束是：**用哪个价源触发止损，就必须用哪个价源丈量移动距离，禁止混源。**

实现上的处理不是"在每个地方都记得用对"，而是：**用一个变量承载这个选择，相关的几个阶段全部只读它**，不给"这里用成交价、那里用标记价"留下写法上的可能。

再配一个专门构造分歧数据的测试（两个价源的最高价刻意不同），把正确答案钉死。

> 一条容易违反的约束，最好的防御不是纪律，是**让违反它的写法根本写不出来**。

## 五、边界条件清单的写法

实现文档里有一张十几行的边界清单，三列：**边界 / 处理 / 依据**。依据一列要么是规格条款号，要么标一个醒目符号表示"**规格未逐字规定，由实现作出的解读**"。

这个"⚠ 标记"是整套做法里最有价值的一笔：它把"我猜的"和"规格说的"在同一张表里区分开，并在文档末尾明确建议——**把这几条解读回填进规格，消除歧义**。项目计划里本来就有一条"发现规格推不出唯一的预期结果就停下来修文档"，这几条正属于此类。

三个被标记的解读，每个都单独展开了理由：

### 5.1 两个网格量相减，必须四舍五入而不是向下取整

规格写的是一个纯减法：`减仓数量 = 已成交量 − 上限量`。两个操作数都已经落在步长网格上，看起来不会有问题。但**二进制浮点会让 `0.118 − 0.117` 得到 `0.0009999999999999975`**；如果对它再做"向下取整到步长"，结果是 **0**——减仓单不会发出，仓位会带着超限的风险敞口继续存在。

处理：新增一个专用的"四舍五入到步长"函数（用十进制、ROUND_HALF_UP），只用于这类"两个网格量相减"的场景；原来的向下取整仍严格用于"取整下限"语义的地方。

> **同一个"对齐到步长"的动作，在"求上限"和"求差值"两种语义下，取整方向必须不同。** 混用一个工具函数是这类系统里最常见的静默错误之一。

### 5.2 过期判定的时间基准

规格写"意图的过期时刻 = 计划执行时刻 + 一个周期"。若过期判定用处理槽的时刻，那么计划在某个整点成交的意图，会在处理对应那根 K 线时**先被判过期、再轮到执行**——结果是所有入场都无法成交。

处理：过期判定以 `bar.open_time` 为基准。计划成交的那根、以及其后一根宽限 K 线仍可执行，再往后才过期——这正是"+1 个周期"的语义。

> 时间语义的 bug 往往不是"算错了几分钟"，而是**同一个时刻在两条代码路径上用了不同的基准**，表现为"某个功能完全不工作"。

### 5.3 预热期：未定义 ≠ 反转

规格规定持仓在"趋势条件失效"时退出，同时规定预热期不生成信号。若指标尚未就绪，趋势对象的初值（中性）会被"是否需要因反转退出"的判断读成"已反转"并触发平仓。

处理：退出分支加一个"指标已就绪"的前置条件。**未定义不等于反转。**

> 任何"枚举初值 + 语义判断"的组合都要检查这一点：初值往往不是任何一种真实状态，而判断函数通常没考虑过它。

## 六、把架构铁律变成测试

三条铁律，三个对应的自动化检查，全部在 CI 里跑：

| 铁律 | 机器化检查 |
|---|---|
| 核心层零 wall-clock、零随机、零网络、零 IO（时间只能来自事件时间戳） | AST 静态扫描核心模块的 import 与调用，禁止读系统时钟、禁止导入 IO/随机/外层包 |
| 回测与实盘共享同一个决策核心 | 断言全仓库只存在一个决策管线类，且两层都 import 它 |
| 规则在文档不在注释 | 断言每个核心模块都引用了条款号 |

依赖方向是单向的：`核心 ← 回测`、`核心 ← 实盘`；核心反向 import 或 import IO 库，由测试直接拦截。

第二条铁律还有一个直接推论体现在文件组织上：回测层的成交模块**只做再导出，不重写规则**——因为同一套价格链和成交规则实盘内核也要用。**规则只有一份拷贝，是铁律 2 的直接结果，不是风格偏好。**

### 还有一个守卫测试：防止重构静默丢测试

规格附了一张编号测试矩阵。项目里有一个专门的覆盖率守卫测试，**扫描所有测试文件的函数名编号，断言规定的每一项都在、且没有编号落在矩阵之外**。

> 没有这个守卫，一次重构删掉两个测试函数，套件依然全绿，没有人会发现。

冻结数值的处理也值得抄：规格给出的数值锚点**直接照抄为 expected**（含多位小数的精确值），而不是让实现"自己算一遍再比"。expected 来自规格，才能验出实现的错；expected 来自实现，只能验出重构的改动。

## 七、诚实交付：显式写下"未实现"

文档单列一节"明确未实现的部分"，逐条列出属于规格/计划范围内但本次没有落地的模块，并写明原因（例如：当前环境无凭证与网络访问，因此数据基座未实现，全部回测在合成数据上运行）。

最关键的两句：

> 全部回测均在合成数据上运行。演示脚本的输出是管线连通性演示，不是研究结论——**合成数据上的收益、Sharpe、盈亏比没有任何策略含义。**

以及关卡状态的明确表述：

> 当前状态为"编码完成 → 单元测试全数通过"；确定性回放已在合成数据上验证，但"可严格回测"需在真实数据接入后重跑。**不得进入模拟盘，更不得进入实盘。**

另外还有一类"已声明的系统性近似"值得学：某个随时间变化的交易所参数表在实现中用的是一份**离线快照**，快照日期被写进常量、并被要求打印进回测报告。历史值不可考这件事，被显式声明成一个已知近似，而不是留给读者自己发现。

> 一份交付文档里最容易被省略、也最能体现可信度的，就是"我没做什么"和"我近似了什么"这两节。

## 八、可以直接抄走的清单

1. 实现文档开头写死"规格是唯一事实来源，本文件不新增规则"。
2. 多处规定先尝试归纳成一条公式，用"能同时复现所有字面值"作为归纳正确的证据。
3. 阶段顺序的理由写机制（"否则会漏掉最危险的那根"），并为它写测试。
4. 硬约束用"单一变量承载选择"堵死写法，而不是靠纪律。
5. 边界清单三列：边界 / 处理 / 依据；自己的解读打醒目标记，并建议回填规格。
6. 区分"取整下限"和"求差值"两种步长对齐语义，用两个不同的函数。
7. 架构铁律写成 CI 测试（依赖方向、唯一决策核心、条款引用）。
8. 加一个测试覆盖守卫，防止重构静默丢测试。
9. 规格给的数值锚点直接照抄为 expected。
10. 单列"未实现"和"已声明的近似"两节，并写明当前不得进入哪一档运行环境。
