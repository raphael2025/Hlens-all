# 行情数据层的坑与服务间契约

信号研究和回测引擎的问题容易被讨论，数据层的问题容易被当成"配置没弄好"。但数据层的错误有个共性：**它们不报错，只是让结果悄悄变得不对。**

下面是几类已经踩过的具体问题，以及一套把数据依赖显式写成契约的做法。

---

## 一、SDK 封装层的静默截断

下载历史 K 线时，统一封装的 `fetch_ohlcv` 方法**即使请求 1500 根也只会静默返回 1000 根**——不报错，不警告，只是少给。直接调用交易所的原始端点才能拿满。

这类问题的通用形态是：**统一封装层为了兼容最小公分母，会把参数悄悄夹到某个上限**。表现不是异常，而是"数据好像有点少"或"某段时间的回测结果和上次不一样"。

处理方式两条：

1. 大批量下载时，**核对实际返回条数与请求条数**，不一致就查封装层默认值，必要时降级到原始端点；
2. 把这个选择**写进项目说明的命令小节**（"这里用的是原始端点而不是统一方法，原因是…"），否则下一个人会"顺手改回标准写法"。

## 二、类型比较在某个依赖版本上抛错

在一段判断"两个时间点之间有多少根 K 线"的代码里，用 `np.searchsorted` 拿一个 `datetime64` 数组去和一个**裸的 `datetime` / `Timestamp` 标量**比较，在当时的 numpy 版本下直接抛 `TypeError`。

修复很简单——比较前**显式转换成 `np.datetime64`**。值得记的是两件别的事：

- **这个 bug 是新增测试触发暴露的**，不是运行中发现的。原有代码路径上恰好没有这个组合的调用。
- 修复被写进了功能提交的说明里（"顺带修复 X，原因是 Y，做法是 Z"），而不是单独一个无说明的小提交。**顺手修的 bug 更需要解释，因为它出现在一个和它无关的改动里。**

> 通用提醒：涉及 numpy / pandas 时间类型的比较、排序、搜索，**先显式统一类型再比较**，不要依赖隐式转换——它在不同版本之间的行为并不稳定。

## 三、不要把一个市场的概念硬套到另一个市场

给一个原本面向股票市场的分析系统增加加密货币数据层时，做的第一个判断是**范围判断**，不是代码判断：

- K 线级别**直接映射交易所原生的 interval**，不做股票市场那套"分钟数据降级合成"和"交易日对齐"——因为标的是 7×24 连续交易的，那些机制存在的前提不成立；
- 选股、板块、涨跌停这些**市场专属功能不迁移**，并在提交说明里写明"本次范围：仅数据层 + K 线级别接口"。

分析引擎本身被原样复用——**可复用的是计算，不可复用的是围绕交易日历和监管规则长出来的那一圈概念。**

另外一个小但真实的可用性问题：某个在该市场里最常用的中周期级别（交易所原生支持）一开始没有被映射进去，用户想看就没有选项。**"常用级别缺失"是功能缺陷，不是配置问题**，值得一个单独的提交和一句理由。

---

## 四、微观结构信号的已知限制，要写进 README

一个订单簿 + 成交数据的分析工具，README 里专门有一节"已知限制"。这一节的价值高于它旁边的架构图：

1. **价差可能为 0**——深度行情下买一卖一可以相等，任何拿价差做分母或做归一化的公式都要有防护。
2. **桶大小需要按品种标定**——成交量分桶类指标（如 VPIN）的桶大小取"平均成交规模 × 常数"，这个常数在不同交易所、不同品种之间并不通用，**照抄论文默认值会得到无意义的数**。
3. **有些形态需要订单簿历史，而手上只有 K 线**——诱多/诱空这类依赖"挂单堆积后突然撤单"的判断，用 K 线只能粗略近似。近似就写明是近似。
4. **K 线粒度回测没有逐笔成交**——用主动买量占比之类的代理变量替代真实订单流方向时，要显式标注这是代理变量。
5. **某个交易所的公开接口不可用**——适配器已经写好，但备用路径返回 404。**把"写好了但没跑通"如实写出来**，比让使用者自己发现好。

> 这一节的通用写法：每条 = **现象 + 当前的处理 + 它还欠什么**。三样都写，读者才能判断这个工具能不能用在自己的场景里。

同一份 README 里的"下一步建议"也值得保留同样的诚实度：把"实时流比轮询精度高一个量级""逐笔数据落成列式文件供回测复用"这类**设计理由**写出来，而不是只列待办项。

## 五、把服务之间的数据依赖写成契约

当"行情采集"和"撮合/钱包"是两个独立服务时，最容易出问题的不是任何一方的实现，而是**双方对"需要什么数据"的理解不一致**。做法是单独写一份数据契约文档，包含四块：

### 5.1 分档的字段需求

不是给一张平铺的字段表，而是分成三档：

| 档位 | 含义 |
|---|---|
| **必须** | 缺了就有功能完全不可用（例如没有买一卖一就无法成交市价单） |
| **推荐** | 缺了会降级（例如没有盘口深度就只能用简化滑点） |
| **可选** | 锦上添花 |

分档之后，上游可以**分阶段接入**，而不是"全部做完才能联调"。

### 5.2 最小可用样本

文档里直接给出一份"如果暂时没有深度数据，至少提供这些字段"的最小 JSON 样本。**一个能直接复制粘贴的最小样本，胜过一页字段说明。**

### 5.3 价源优先级，让同一个服务同时服务回测和实盘

价格来源按固定优先级解析：**主动注入 > 缓存 > 从上游拉取**。

这条设计的直接收益是：回测时按历史时间戳**批量注入** tick 即可覆盖外部源，实盘时什么都不用改。**"回测和实盘走同一条代码路径"不是靠两套分支实现的，是靠一个优先级规则实现的。**

同一思路在别处也成立：把决策核心做成唯一的一份，回测层和实盘层都 import 它，用依赖方向的检查把"核心不许 import IO"钉死（详见《按规格书实现一个系统》）。

### 5.4 新鲜度策略要精确到场景

"数据是否过期"不是一个全局开关：

- **立即成交的市价单**检查盘口新鲜度——否则会按一个已经作废的价格成交；
- **条件单挂单**不检查——它本来就要等未来的行情；
- 标记价的新鲜度不阻断成交，只影响估值类计算。

> 通用原则：新鲜度检查的粒度应当对齐**"这个动作是否立刻产生不可撤销的后果"**，一刀切地检查或不检查都会出问题。

### 5.5 命名统一

Symbol 命名在整个链路里**只允许一种写法**，并在契约文档里写死。跨交易所聚合时，转换发生在适配器层，不允许往上层漏。

## 六、采集与核心分离部署

采集器和核心服务分开部署时的两条理由，值得写进部署文档：

- **采集节点放在靠近交易所撮合机房的区域**，核心服务放在另一处——采集对延迟敏感，核心服务对延迟不敏感但对稳定性和存储敏感，两者的最优位置本来就不一样。
- **对外只暴露一个入口端口**，其余服务只在内网或受限来源之间互通。容器编排内部用服务名互相寻址，配置里不出现任何公网地址。

配置方面：**所有凭据与口令一律走环境变量，示例文件里只保留空占位**，并对实际配置文件收紧权限。示例文件的作用是说明"需要哪些变量"，不是"填好给你抄"。
