# 会自我纠正的研究日志：一个被主动记录的引用错误

大部分研究记录的问题不是写得少，而是**只记成功、不记推翻**。时间一长，日志变成了一份自我吹捧的合集，后来人（包括半年后的自己，包括接手的 AI agent）读完得到的是一个被美化过的世界模型。

下面是一个把"我引用错了一个数字"完整写进日志的真实案例，以及围绕它固化下来的日志格式和规则。

---

## 一、日志的形态

这类研究项目的交付物不是软件，而是**"哪些配置真的有效"的经验证据**。所以工程结构服务于记录，而不是反过来：

- `research_log.md`：按时间倒序（最新在最上面）的研究日志，每条带日期与序号，记清楚"做了什么 / 结果是什么 / 结论 / 下一步"。
- `methods_catalog.json`：结构化的方法目录，每个方法带状态 `pending / testing / adopted / rejected`，以及一个存放"最重要的那条警告"的字段。
- `results_*.json`：每一轮实验的原始输出落盘，**不用重跑就能查历史结果**。
- 项目常驻说明文件：开头就写"动手之前先读日志最新几条"。

关键的细节是那份常驻说明文件里的一句话：

> 不要把旧日志条目当作仍然成立的结论——这份日志内部有一段"一个错误结论被发现并纠正"的历史。

**主动告诉读者"这里面有过错"**，比假装日志一贯正确更有用。它把"检查是否被后续条目取代"变成了读者的默认动作。

## 二、那次引用错误

### 2.1 发生了什么

在整理另一个仓库里的既有研究时，看到一份结论很漂亮的报告，其中有一个头条数字：给某类策略加上一个状态过滤闸门，样本外风险调整收益从负值提升到正值，提升幅度接近 0.8。这个数字被拿到与用户的讨论中引用了。

后来**完整通读原始文档**才发现：**这个数字被原作者自己在同一天的后续验证里推翻了**。用滚动窗口重测，只有六个窗口中的两个显示"加闸门更好"；作者原话认定那个大幅提升是"近期单段的偶然结果"；扣除交易成本后诚实的数字，提升幅度只有原先宣称的七分之一左右。

也就是说：**一个已经被原作者撤回的数字，差点被当作真结论继续向下游传递。**

### 2.2 日志里是怎么写的

不是删掉了事，而是新开一条，标题里直接写明"发现并纠正了一处引用错误"，正文用醒目标记单列一段：

- 我引用了什么数字，在什么场合；
- 原始文档里它后来被怎么推翻的，诚实的数字是多少；
- 这属于哪一类错误：**只信了报告的结论，没有自己复核到底**；
- 对应到哪一条既有规则上（"子 agent / 外部报告的结果，主 agent 必须自己复现，不能直接采信"）。

**把错误写成一条独立日志条目，而不是悄悄修正正文**，是这件事最值钱的部分。它让这个错误变成了可被后来人检索到的资产。

### 2.3 由此固化的规则

> **任何外部引用的数字，必须找到原始文档通读全文，尤其要看有没有"后续验证 / 自我推翻"的部分，不能只看摘要或者它第一次出现的位置就采信。**

推论：

1. **好文档的作者会推翻自己，而且往往写在后面。** 摘要、开头、第一次提及的位置，通常是作者最乐观的时刻。
2. **越漂亮的数字越要往后翻。** 一个"从负到正"的戏剧性提升，本身就是"作者后来可能加了 walk-forward"的强信号。
3. **引用链每多一跳，可信度就掉一档。** 自己没读过原文的数字，在对外表述时要标明来源层级。

## 三、配套的几条日志纪律

### 3.1 外部结论不能直接接进自己的系统

后续遇到同一类情况时的处理方式变成了两步走：

1. 先开一条日志**记录**外部研究的结论，明确写"这不是本项目跑出来的，不能直接采信"；
2. 再开一条日志记录**自己独立实现并验证**的结果。

实际做完之后，独立验证的结论是"方向对、但没强到能过本项目自己的显著性门槛"——于是方法状态从 `pending` 改为 `testing`，既不是 `adopted` 也不是 `rejected`。**"方向对但不够格"是一个需要被表达出来的状态**，只有二元的采纳/否决会逼着人把它凑到某一边。

顺带记下一条有价值的方法论差异：外部那份研究用了对小样本、抗自相关更稳健的统计方法，而本次独立验证只用了简单 t 检验——**显著性偏弱可能部分来自检验方法更保守，而不是效应不存在**。把这种"我知道自己这里还不够好"的自评写进日志，比只写结论有用得多。

### 3.2 不利结果照记

引擎修 bug 之后重跑，大部分配置变好、有一个变差。变差的那个照样写进表格，并注明"说明修复对不同配置的影响方向不一致，不能假设'修复=万能提升'"。

同理，一个曾被诊断为"策略结构性弱点"的现象，在 bug 修复后基本消失——日志里明确写下"**这是一个重要的自我纠正，之前的结论被过度解读了**"。

### 3.3 结论会过期，要显式标注

- 结果文件被覆盖重写时，在日志里写清"以这次为准，第一版的结果是错的"。
- 一个数字如果是在某个已知 bug 存在时跑出来的，要写明"这些历史数字已过期"。
- "下一步"章节被后续条目推翻时，标题里直接写"推翻 XX 的排序，重新定优先级"，而不是默默改掉。

### 3.4 未完成的东西要标成未完成

日志里明确写：某个 walk-forward 优化脚本"已写好但从未成功跑完，按草稿对待，不是已验证的结果"。**半成品被当成成品引用，是另一种形式的引用错误。**

## 四、几条工具层的小经验

这些和研究方法无关，但同属"日志值得记下来的东西"：

- **写长文档时先写入、再读回确认**，避免中途截断产生一份看起来完整、实际缺尾的文件。
- **记忆/日志目录不会自动创建**，工具链里该有的目录要显式建好，否则写入会静默失败或落到别处。
- 网络检索被某个搜索入口拦截时，**直接抓取目标页面**往往比换搜索词有效。

## 五、一页纸小结

| 做法 | 为什么 |
|---|---|
| 最新条目在最上面 | 读者第一眼看到的是当前状态，不是历史起点 |
| 方法目录带状态机 | 容纳"方向对但不够格"这种中间态 |
| 原始结果落盘 | 查历史不用重跑，也防止口径漂移 |
| 常驻说明文件写明"日志里有过错" | 把"检查是否被推翻"变成读者的默认动作 |
| 错误单独成条，不悄悄改正文 | 错误变成可检索的资产 |
| 不利结果、方法局限照记 | 日志的价值来自它敢说自己不行 |
| 旧结论过期时显式标注 | 防止别人（和未来的自己）引用僵尸结论 |

> 一句话：**研究日志的可信度，不来自它记了多少成功，而来自它是否记录过自己被推翻。**
