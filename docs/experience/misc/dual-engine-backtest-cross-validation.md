# 双引擎交叉验证：一次把"Sharpe≈1.0"打回"Sharpe≈0"的复盘

这是一个具体的事故复盘：一套跑了几个月、已经被标记为"已采纳"的配置，在换一个独立回测引擎重测之后，全部优势消失。下面记录事故本身、排查路径、最后保留了什么、撤回了什么，以及从中固化下来的两条工程机制。

---

## 一、为什么要同时养两套回测引擎

项目里故意并存两套实现：

| 引擎 | 定位 | 特点 |
|---|---|---|
| 自建轻量引擎 | 快速探索 | 逐 bar 事件循环，纯 Python 每秒上百次回测，适合大批量扫参数/过滤器组合 |
| 工业级开源框架 | 可信裁决 | 慢，但成交模型更接近真实（基于 OHLC 撮合），指标用标准 TA 库而不是 pandas 近似 |

一开始的理由只是"快"。事故之后，理由变成了硬规则：

> 自建引擎只用来**排除**明显不好的想法；任何"这个配置看起来不错"的结论，必须在独立引擎里复现出来才算数。

这条规则写进了项目的常驻说明文件，任何后来的人（或 agent）接手时第一眼就能看到。

## 二、事故经过

### 2.1 现象

自建引擎上，某组"趋势信号 + 趋势强度过滤 + 波动率目标仓位 + 跟踪止损"的配置，长期稳定给出 Sharpe 接近 1.0 的结果，并据此被写进推荐配置。

把同一套逻辑逐条翻译到工业框架、用同一段历史、同一份数据源重测：**所有过滤器/仓位/多空组合，Sharpe 全部落在 0 附近或为负，没有一个明显为正。**

### 2.2 排除法，先排掉最容易甩锅的解释

排查顺序很重要——先排除"两边算得不一样"这类低级差异，才有资格谈"哪边是对的"：

1. **指标实现差异**：把两边的趋势强度指标和波动率指标逐 bar 比对，相关性 >99.99%，阈值判定一致率 99.9%。**排除**。
2. **仓位记账差异**：核对框架的盈亏公式在美元层面是否精确成立，以及第一笔交易的盈亏量级。两边接近，不是离谱错位。**排除**。
3. **手续费假设**：核对两边的单边费率一致。**排除**。

排除之后，剩下的嫌疑集中在**成交与时序假设**上：自建引擎把"止损一定能在止损价成交"这类简化当成了默认，信号到成交之间的时序约定也比真实情况更有利。

### 2.3 一个反直觉但正确的决策：不再逐笔对齐

自然的下一步是"逐笔比对两边的交易记录，找出到底差在哪"。实际判断是**不值得**：两个独立实现在成交价、止损触发时点、时序约定上必然有大量微小差异，穷举对齐几乎不可能完成，而且不是最有价值的时间投入。

改成：**不再纠结"为什么两边不一样"，而是把研究阶段测过的主要组合全部在更可信的引擎里重跑一遍，横向对比它自己内部是否自洽。**

结果是自洽的——过滤器越多回撤确实越小、固定风险仓位的回撤确实低于波动率目标仓位，方向全对，只是整体水平上不去。一个内部自洽、但整体结论相反的结果，比"两边差异的逐笔清单"更有裁决力。

### 2.4 结论：保留什么，撤回什么

- **保留**：模块之间的**相对优劣排序**大概率仍然成立（"加趋势强度过滤能降低回撤"这类方向性结论，在两个引擎里都成立）。
- **撤回**：**绝对收益和绝对 Sharpe 全部作废**，之前写下的"验证有效、可以推荐"必须改口。所有基于自建引擎做出的"已采纳"判断，重新定性为"仅供参考，未经过更真实的执行环境验证"。
- **连带决定**：原计划的下一步（启动模拟盘）取消。不是"分歧没查清不敢上"，而是有实质证据表明这个策略本身可能就没有优势，去模拟一个大概率没有 edge 的东西没有意义。

## 三、顺带抓出的两个真实 bug

交叉验证的额外收益是：它是一台 bug 探测器。这一轮抓到两个。

### 3.1 "止损后同根 K 线立刻重入"——持续型信号的通病

**怎么发现的**：在给一个组合级回撤熔断做功能测试时，把触发阈值设得比历史最大回撤还宽松（理论上永远不会触发），结果回测数字居然和不加熔断时不一样。顺着这个**本不该存在的差异**往下查，才发现根因不在熔断，而在引擎更底层的地方。

**根因**：当目标仓位信号是**持续型**的（条件满足期间一直非零，而不是只在某根 K 线上触发一次），止损平仓后，只要信号还没变，引擎会在同一根 K 线立刻按同一根的收盘价重新开仓、重算一个新的止损位。这不是"止损离场后等下一根再决定"，而是"止损从来没让你真正离场，只是把止损位挪到了当前价格附近"。

**修复**：在引擎层加通用的 `止损后冷静期` 参数——止损触发后 N 根 K 线内禁止同方向重新开仓（信号翻转导致的正常换向不受影响）。冷静期为 0 时的语义也从"允许同根重入"改成"至少隔 1 根"。

**同一个 bug 在两套引擎里各犯了一次**：在工业框架里它表现为"没有开启冷静期保护机制"，默认配置下同样会连环重入。**任何持续型信号的策略，从第一天起就需要这个机制。**

**影响面才是真正的教训**：这个 bug 静默存在了几个月，此前记录下来的全部历史结果都是在它存在的前提下跑出来的。修复后重跑：

- 大部分配置**变好了**（说明"止损后至少歇一根"本身是更保守、更正确的处理，减少了无意义的止损—重入震荡）；
- 但有一个配置**变差了**（Sharpe 反而下降）——如实记下来，不能选择性只强调对自己有利的变化；
- 此前被诊断为"策略结构性弱点"的某个年份负收益，修复后基本消失——也就是说，**之前那个"结构性弱点"的结论，相当一部分其实是 bug 的副作用，被过度解读了。**

由此固化三条：

1. 改动引擎核心逻辑（哪怕只是为了某个新场景修 bug），都可能悄悄改变**所有依赖同一份引擎的历史结果的含义**，必须主动回去重跑旧的对比组，而不是默认"旧结果还作数"。
2. 一个看似局部的修复，如果修在共享核心组件上，影响面比预期大得多。发现"通用机制"级别的问题时，第一反应应该是"这会不会影响其他已经跑过的实验"。
3. 修复不总是让数字变好看。两个方向的变化都要如实记录。

### 3.2 框架自定义止损回调与杠杆的除法陷阱

在工业框架里第一次跑移植版策略，结果灾难性（年化深度负值，九成以上交易是止损离场，平均持仓极短）。翻框架源码才找到根因：

> 框架内部会把自定义止损回调函数的返回值**先除以杠杆倍数**再换算成实际止损价格距离。也就是说它的返回值语义是"**杠杆后的名义比例**"，不是"纯价格移动比例"。

策略里直接返回了基于 ATR 算出的**纯价格距离**，而策略用了 2 倍杠杆，于是实际止损距离被腰斩成预期的一半——止损比预期紧一倍，几乎任何正常波动都会打到。

**修复**：返回值乘以杠杆倍数，抵消掉框架内部的除法。

**这是一个通用坑**：任何在杠杆/合约模式下用自定义止损回调、并且止损距离是按价格算出来的策略，不做这个换算，止损都会比预期紧 `leverage` 倍。写完策略后专门检查这一点，比事后从回测数字倒查便宜得多。

## 四、可以直接抄走的几条

1. **两套引擎不是冗余，是制度**。快的那套负责枚举，慢的那套负责裁决；谁有最终解释权必须事先写死，否则事后一定会挑对自己有利的那个。
2. **排查顺序**：先逐条排除"算得不一样"（指标、记账、费率），再谈"谁的假设更接近现实"。跳过这一步的结论没有说服力。
3. **内部自洽性是廉价的裁决依据**。与其对齐两套实现，不如看更可信的那套在自己内部是否给出方向一致的排序。
4. **"本不该出现的差异"是最好的 bug 线索**。一个理论上不会触发的开关改变了结果，就一定有东西错了——不要放过它。
5. **改核心必须重跑旧结论**，并在日志里明确写"旧数字已过期"。
6. **交叉验证只解决"引擎乐观偏差"这一个问题**，不解决"过拟合到这段历史"。两者是完全不同的检验，少一个都不够。
