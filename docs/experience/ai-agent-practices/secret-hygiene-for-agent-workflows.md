# Agent 工作流里的脱敏纪律

AI agent 天然是**泄密放大器**：它读你的环境变量、读你的配置文件、把命令输出原样贴回对话，然后你（或它自己）把这段对话提交进 Git。
传统"不要把密钥写进代码"的直觉在这里不够用，因为泄漏面已经从源码转移到了**日志、记忆文件和对话记录**。

这份文档是多次实际泄漏之后反推出来的纪律。

---

## 1. 泄漏点排序：真正出事的地方

按实际发生频率从高到低：

1. **原始会话 / 对话日志**。用户直接把 token 粘进对话框，agent 把它原样写进 transcript，transcript 随记忆仓一起推到远端。这是最大的一类，而且最隐蔽——没人会去 review 一个三千行的 JSONL。
2. **Agent 自动写入的记忆文件**。agent 在总结"我做了什么"时，顺手把主机地址、账号、连接串写进了结论。
3. **基础设施描述文档**。`*-infrastructure.md` / `*-deployment.md` / `cloud-servers-*.md` 这类文件天然就是 IP、主机名、账号的聚集地。
4. **配置样例**。`.env.sanitized`、`auth.json.sanitized` —— 名字里带 "sanitized" 不等于真的干净。
5. **源码**。排最后。这里反而是防护最完善的。

**结论：把脱敏预算投在日志和记忆文件上，不是投在源码扫描上。**

---

## 2. 必须扫描的模式清单

一份可以直接抄的正则类别表：

| 类别 | 说明 |
|---|---|
| GitHub PAT | `ghp_` / `gho_` / `ghu_` / `ghs_` / `ghr_` / `github_pat_` 前缀 |
| OpenAI 类 key | `sk-` / `sk-proj-` 前缀 |
| Anthropic key | `sk-ant-` 前缀 |
| Telegram bot token | `<纯数字>:<定长字母数字串>` 形态 |
| Slack token | `xox[bpars]-` 前缀 |
| AWS access key | `AKIA` 前缀 |
| VPN / 网格网络 auth key | 厂商固定前缀形态 |
| PEM / OpenSSH 私钥 | `-----BEGIN ... PRIVATE KEY-----` |
| Bearer token | `Authorization: Bearer ...` |
| 赋值型 | `password=` / `api_key=` / `secret=` / `token=` |
| 连接串 | `<scheme>://<user>:<pass>@host` |
| 助记词 | 连续 12 / 24 个词表单词 |

命中后统一替换为 `[REDACTED:<kind>]` 这类**带类别标记**的占位符——比单纯 `***` 好，因为事后能知道漏的是什么类型，从而决定轮换哪个凭据。

**不要擅自改 PATTERNS。** 新增规则的流程固定为：记一条规则变更决策 → 往自测用例里加一条 → 跑通自测 → 提交。自测用例用假值（`password=hunter2hunter` 这类），永远不用真值做测试夹具。

## 3. 三层防御

单点防御一定会被绕过（忘了跑、脚本坏了、换了台机器）。

| 层 | 触发点 | 作用 |
|---|---|---|
| L1 | 本地 `git commit` 前的 pre-commit hook | 主防线，拦在进入历史之前 |
| L2 | 远端 CI / 服务端扫描 | 兜底复扫，防 L1 被跳过 |
| L3 | 写入前作者手动跑 `--check` | 心智层，让人意识到自己在写什么 |

关键在 L1：**必须拦在 commit 之前**。一旦进了 Git 历史，`git rm` 是无效的——凭据已经存在于对象库和所有克隆里，只能按"已泄露"处理。

另外，扫描强度应该按内容的持久化等级分档：永久保留的文件用全量规则 + 强制人工复核；短期文件用降噪后的高危规则集（只查 token / 私钥 / PEM，跳过 `password=` 这类高误报规则），否则误报太多会导致所有人开始习惯性 `--no-verify`。

---

## 4. 泄漏台账：记录"什么该轮换"，而不是"什么泄漏了"

发现历史泄漏后，正确的产出不是一份"泄漏内容清单"（那等于又抄了一份），而是一张**轮换台账**：

| 什么类型的凭据 | 大致出现在哪个仓 / 哪类文件 | 状态 |
|---|---|---|
| 代码托管平台 PAT | 某记忆仓的索引文件 | 已撤销 |
| 某模型厂商 API key | 某 agent 配置文档 | 待轮换 |
| 服务器登录口令 | 某日志文件 | 视为泄露，已轮换 |
| OAuth client id | 某产品仓的待办清单 | 待撤销重建 |

三条规则：

1. **台账里只写类别和位置，不写值。** 否则台账本身成了新的泄漏源。
2. **状态只有三种**：待轮换 / 已轮换 / 已撤销。不存在"应该没事吧"。
3. **凭据一旦出现在任何提交历史或任何 transcript 里，一律按已泄露处理**，不管仓库是不是私有。私有仓不是保险箱——它会被克隆、被归档、被当作素材喂给下一个 agent。

## 5. 反模式清单

从真实事故里抽出来的：

- **多台主机共用同一口令**。一台泄漏 = 全部沦陷。台账里出现"同密码"三个字就是 P0。
- **把凭据粘进对话框**。人类为了让 agent"能用上"直接粘贴，是泄漏第一大来源。正确做法是让 agent 读环境变量或本地 secrets 目录，**只传变量名，不传值**。
- **密码认证的 SSH 长期开着**，公钥明明早就配好了。
- **把 "sanitized" 当成 "clean"**。sanitized 文件往往只替换了 value，保留了完整的主机名、用户名、端口、路径结构——这些合在一起就是可用的攻击面。
- **在 commit message 里写"绕过脱敏检查"**之类的措辞。这等于给扫描器和审计者留一个指路牌。
- **把脱敏结果长期缓存**。降级 / 失败的结果只短缓存，不要把一次误判固化下来。

## 6. 哪些东西不算密钥但同样不能发

密钥有明确形态，容易扫。真正难的是这些"**不是密钥但同样识别身份 / 暴露攻击面**"的内容：

- 内网 / 公网服务器 IP、主机名、端口拓扑
- 账号名、用户名、UID、邮箱、手机号、即时通讯数字 ID
- 真实姓名（包括出现在 agent 花名册、团队成员描述里的）
- 家庭 / 办公网段的私有 IP、设备名
- 路径中的用户名（`/home/<user>/...`、`/mnt/c/Users/<user>/...`）
- 实盘资金量、绝对盈亏金额、持仓明细、订单 ID
- 别人的私人对话内容

**处理方式是改写而不是打码**：把"主节点 `<某个 IP>` 上的 PostgreSQL 临时表空间被写满"改写成"共享生产数据库的临时表空间被写满"。技术教训一个字没丢，指纹全部消失。

需要保留数量级时用区间或比率替代绝对值。

## 7. 对外发布 / 提炼公开文档时的流程

把私有记忆整理成可公开材料时，这套流程实测有效：

1. **先做仓级判定，再做文件级判定。**
   如果一个仓里真实姓名、主机地址、原始聊天记录是**贯穿性**的（出现在索引文件和多数正文里），那就整仓跳过——不要为了抢救其中一两个"看起来干净"的片段而去逐行摘录。摘录动作本身就是高风险操作，而且你无法证明剩下的部分真的干净。
2. **敏感内容集中在可枚举的少数文件时，才做选择性提取。**
   典型可预测命名：`*-infrastructure.md`、`*-deployment.md`、`cloud-servers-*.md`、顶层索引文件。把这些整体排除，剩下的纯经验文件基本可以直接用。
3. **永远不把原始会话 / 对话日志当素材来源。** 只用已经写好的反思类、总结类文档。
4. **重写，不复制。** 复制会把源文档的措辞、路径、上下文一起带过去；重写会强迫你判断每一句话是不是真的通用。
5. **不确定就丢掉。** 一条边缘有用的洞见，不值得一次泄漏。

---

## 8. 最后：默认设定要正确

所有纪律都会在赶工时被跳过，所以真正起作用的是**默认值**：

- 凭据默认放在本地 secrets 目录，`.gitignore` 默认覆盖它
- pre-commit hook 默认安装（通过符号链接进 `.git/hooks/`，换机器时可复现）
- 新文件默认最保守的持久化等级 → 默认最严的扫描规则
- 脱敏脚本默认 `--check`（只报不改），`--in-place` 需要显式指定
- agent 的授权策略里，**触碰 secrets 目录永远需要人类确认**，不管当前授权级别多高
