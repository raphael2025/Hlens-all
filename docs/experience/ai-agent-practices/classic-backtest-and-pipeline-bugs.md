# 经典回测与数据管道 Bug 目录

上一份文档讲的是统计纪律——即使代码全对，也会因为多重比较而得出假结论。
这一份讲的是**代码本身就错了**的情况。它们的共同特征是：

- **不报错、不崩溃**，测试全绿
- 产出的数字**看起来非常合理**，甚至漂亮得让人兴奋
- 往往要靠一次独立审计才会被发现

真正危险的不是"测出无效"，而是"**测出有效但其实是 bug**"。后者会让你投入几周去优化一个不存在的东西，甚至真的上真钱。

---

## 1. 成本方向算反

**最贵的一个。**

做空的交易成本被记在了对自己有利的一侧，而不是不利的一侧。回测因此显示 100% 胜率。
一次独立审计把成本符号改正之后，同一份数据、同一套规则从大幅盈利直接翻成净亏损，表观收益差了几百个百分点。

单笔层面的体感：毛利 +0.12，成本 −1.40。**成本项比信号本身大一个数量级**——这类策略的全部结论都由成本模型决定，成本写错等于结论随机。

**自检**：
- 分别构造一笔纯多、一笔纯空的手工算例，人工核对最终 PnL 的符号和量级
- 打印单笔的 `gross` / `fee` / `slippage` / `net` 四列，看 `net = gross - |cost|` 是否恒成立
- 看到"胜率 100%"或"几乎无回撤"，先假设是 bug，不要先假设是天才

## 2. Expanding z-score（前视泄漏的最常见形态）

用截至目前**全样本**的均值/标准差做标准化，等于让每个历史时点都知道未来的分布。

这个 bug 曾把一个真实的负信号做成 Sharpe +51。

**规则：任何标准化、归一化、分位数映射，必须用滚动窗口（≥1 天），expanding 永久禁止。**

同类泄漏还有：
- 用全样本的极值做 min-max 归一化
- 用全样本统计量做异常值裁剪
- 用未来数据填补缺失值（前向填充是安全的，插值不是）
- 标签用了 `t+1` 的数据，特征却包含了 `t+1` 时刻才能知道的量

## 3. 合成数据 / 自制 generator 的假成果

自己写的订单簿 / 行情 generator 会无意中把信号"造"进数据里，因为你按自己对市场的假设生成它。

实测对比：七个在合成数据上 100% 胜率的信号，放到真实数据回放上，最好的那个胜率只有三成多，十二组参数全亏。

**规则：合成数据只能用于验证代码路径是否跑通，绝不能用于验证假设是否成立。**

工程上的推论：真实数据回放才算数。用低频数据当高频代理会再低估一些，但结论方向通常不变——"用代理数据算出来是 fail"基本可以直接判死。

## 4. 数据对齐 bug 伪装成"没有信号"

一条轨道的回测输出 0 个事件 / 0 笔交易。

直觉反应是"这个假设不成立"。实际原因是数据框的索引对齐把整条轨道的行数干成了 0——两个时间序列的时区、频率或索引类型不一致，join 之后全是 NaN。

**规则：看到"0 事件 / 0 信号"先查数据管道，不要先下假设不成立的结论。**

自检：在每个 join / merge / reindex 之后断言行数与非空率，而不是只在最后看结果。

---

## 5. 一行多余的赋值

复现脚本里一行冗余的赋值，把 −88% 的结果算成了 +39504%。

**规则：复现脚本本身也要逐行审计。**"这是别人/上一轮写的、跑通了就行"是最危险的心态——复现脚本的 bug 和主代码的 bug 一样致命，而且没人审它。

## 6. "指标好" ≠ "能赚钱"

一个分类器 precision 0.74，看起来相当不错。做成策略后 Sharpe −2.46。

原因通常是三类之一：
- 预测对的那些事件**幅度太小**，覆盖不了成本
- 预测错的那些事件**幅度巨大**（尾部不对称）
- 信号触发时机与可成交时机之间有**无法消除的延迟**

**规则：分类指标（precision / recall / AUC / IC）只是中间量。最终验收必须是扣费后的 PnL 分布，不是分类指标。**

## 7. 真信号但不可交易

一个反直觉但极其重要的类别：**信号是真的，钱是假的。**

实测案例：订单簿顶档失衡对未来中价的 RankIC 在 1 秒尺度能到 0.286——这是一个非常强的真实信号，不是噪声。
但是：

- decile 之间的价差 1.4–2bp
- 盘口价差 1.48bp
- maker 往返成本约 4bp

**信号的幅度小于交易成本。** 净结果：taker 每笔 −8bp，maker 每笔 −2bp。

信号强度峰值出现在 0.5–1 秒，30 秒后衰减到 0.077，两分钟后归零。这意味着唯一能捕获它的位置是亚秒级的 maker 队列——一个散户在延迟上结构性必输的战场。

**规则：任何信号研究必须同时报告"信号幅度"和"交易成本"，且在同一个单位下比较。** 只报 IC / RankIC 不报可捕获幅度，是没有意义的。

## 8. 上真钱之前的清单（从一次真实亏损里抽出来）

一次真实的实盘失败，根因全部在对接层，与策略无关：

1. 持仓查询**没有区分双向持仓模式**下的多头仓和空头仓，把两个方向的仓位相减了
2. 持仓同步用错了字段名
3. 开仓计划构造时**缺少方向参数**，导致有符号数量算错
4. 平仓没有按方向分别调用对应的平多 / 平空接口
5. 下单前**没有检查是否已有持仓**

还有一条纯粹的单位陷阱：**永续合约的 size 单位是"合约张数"，不是标的数量**（一张可能等于 0.0001 个标的）。这类单位换算错误在每个交易所都不一样，且文档里往往一笔带过。

### 上真钱前的强制清单

- [ ] 测试网连续运行满一段时间（比如 7 天）零故障
- [ ] 确认账户的持仓模式（单向 / 双向），代码对应处理
- [ ] 每次下单前的 preflight 检查都过：已有持仓 → 不开新仓
- [ ] 本地持仓文件与交易所实际持仓**手工核对一致**
- [ ] 止损阈值已在下单前的环节实施（注意杠杆下的保证金比例换算）
- [ ] 单日最大亏损上限已实施
- [ ] 人工 review 前几笔真实成交
- [ ] 开关默认 `LIVE_TRADING = False`，且默认值写死在代码里，不靠环境变量

### 资金层面的硬约束

低杠杆、逐仓、同时最多一个持仓、日/周止损、**无马丁格尔、无金字塔加仓**、数据过期守卫（行情超过 N 秒未更新则拒绝下单）。

## 9. 记录层的前视泄漏：用序号，不用墙钟

这个 bug 不在回测代码里，在**数据采集层**，但它会污染此后所有的回测。

**错误做法**：用本地接收时的墙钟时间（wall clock）作为"这条记录在时刻 T 是否可见"的判据。直觉上很合理——晚到的数据应该有更晚的时间戳。

**失效模式**：

| 情况 | 后果 |
|---|---|
| NTP 时间回拨（step） | 晚到的记录拿到更早的时间戳 → 回放中**提前可见** |
| 容器 / 虚拟机迁移导致墙钟跳变 | 同上，顺序与真实获知时刻脱钩 |
| 毫秒级碰撞 | 同一时间戳内多条记录的全序未定义 |
| 某些虚拟化环境 | 实测过高频、规律性的时钟阶跃回拨，单日发生次数可达数千次 |

**核心问题：墙钟可见性创造了一条真实的未来数据泄漏通道**——消费者在"过去"的某一时刻能看到本不该看到的记录。而且更糟的是，常规的"特征无未来数据"测试**测不出它**，因为那些测试验证的是特征计算，不是存储顺序与可见性语义。

**正确做法**：

- 每个数据源一条独立 journal，分配**严格递增的序号 `seq`**（持久化成功之后才确认）
- 跨 journal 只有偏序，用一个显式的**向量游标** `{journal_id → seq}` 表达"我读到哪了"
- 可见性定义：记录 `r` 在游标 `C` 下可见 ⟺ `r.seq ≤ C[r.journal_id]`
- 回放 = 用记录下来的游标重建状态 → **按构造与实时逐位一致**
- 所有时间字段（交易所事件时间、本地接收墙钟、单调时钟）都降级为**元数据**，不参与可见性判定
- **永远不用墙钟做减法**——算时长 / 延迟用单调时钟
- 回补的历史数据按**实际写入时的 seq** 排序，在回放中于其真实获知时刻才可见。不要为了"时间顺序好看"重排 append-only 记录

代价是概念负担：下游不能偷懒写 `WHERE ingest_time <= T`，必须理解游标；跨数据源分析要显式维护向量游标；回补数据在 seq 轴上会晚于断线后的实时数据（这违反直觉，但它是正确的）。游标的序列化格式一旦开始录制就不可再改——要在第一天冻结。

## 10. 一个更一般的教训：静默错误比崩溃更糟

订单簿重建是这个原则的典型：它需要快照 + 增量缓冲 + 序号链校验 + 边界拼接。**重建错了不会崩溃，只会产出看起来完全合理的错误深度数据。**

因此在一个只做中低频决策、且没有任何假设会消费深度数据的阶段，正确的决定是**完全不采集深度流**，而不是采集一个"完整性不可证的降级版本"。降级版本严格劣于不采集——它引入了一整类你无法检测的静默错误。

推而广之：

> 当一类数据你还没有明确的消费假设，而它的正确性又难以验证时，**不采集**优于"先存着反正以后要用"。

反向的例外也要认：**某些数据事后无法重建**（行情快照、持仓量、资金费率、交易所状态）。这类数据是时间敏感投资——每推迟一天就永久损失一天。所以真正的判断是二维的：

|  | 事后可重建 | 事后不可重建 |
|---|---|---|
| 正确性可证 | 不急，按需采 | **优先采，第一天就开始** |
| 正确性不可证 | 不采 | 谨慎采，并在契约里显式标注保证等级低于其他流 |

把"保证等级"写进数据契约，比事后争论"这份数据能不能信"便宜得多。
