# 个人 AI Agent 记忆系统怎么搭

长期和多个 AI agent 一起工作，最先崩掉的不是模型能力，而是**跨会话的连续性**。
每开一个新会话，agent 都从零开始；于是同一条死路被反复走，同一个结论被反复推导，同一份额度被反复烧掉。

下面是反复试错后沉淀下来的一套结构。核心只有一句：
**记忆仓库存的是"沉淀的认知"，不是"发生的事"。**

---

## 1. 最重要的一条：结论 > 过程

会话日志（JSONL / 聊天记录 / 工具调用流水）**不是记忆**，是原材料。

它们有三个致命问题：

- **体量失控**：一个活跃使用半年的 agent，原始会话可以轻松占到整个仓库 99% 的体积，把真正有用的几百行结论淹掉。
- **不可检索**：没人会去读三千行对话找一个结论；agent 也不会。
- **风险最高**：密钥、IP、账号、别人的隐私对话，全部是从原始日志里漏出去的，不是从结论文档里。

所以：**原始日志留在本地或原仓，不进知识树**。进知识树的是"读完之后重写的结论"。

一个可操作的判据——写下一条记忆前问自己：

> 三年后的我（或任何一个接手的 agent）只读这一段，能不能直接用？

能，就是认知；不能，只是事件。

---

## 2. 三档记忆分级

把所有内容强制分成三档，并在文件 frontmatter 里显式标注。没有标注的默认取**最保守**的一档。

| 档位 | 典型内容 | 生命周期 | 清理方式 |
|---|---|---|---|
| `short-term` | 日报、inbox 通知、临时状态、调试输出 | 30 天内正常读写 | 30 天归档到 `archive/short-term/YYYY-MM/`，90 天后可物理删除 |
| `long-term` | 主题文档、工具栈约定、偏好、活跃目标 | 永久保留 | 每 6 个月 review 一次，不自动删 |
| `permanent` | 核心决策、关键教训、里程碑、身份约定 | 永久 + 永不进入任何自动删除路径 | 修改必须走 PR + 人类确认 |

分级不只是为了清理，它还驱动两件事：

1. **脱敏强度**：`permanent` 用最激进的扫描规则 + 强制人工复核；`short-term` 用降噪后的高危规则集（只查 token / 私钥 / PEM，跳过 `password=` 这类高误报规则）。
2. **归档自动化**：一个每周跑一次的定时任务按 `permanence` 字段决定移动还是删除，逻辑可以简单到十行伪代码。

**踩过的坑**：把身份类、决策类信息误标成 `short-term`，等于把它丢进了 90 天删除队列。所以"不确定就默认 long-term"这条兜底规则必须写进 onboarding 文档，而不是靠自觉。

---

## 3. 注入层 / 索引层 / 细节层的三段式

不要指望把所有记忆塞进上下文。分三层：

```
MEMORY.md         ← 每次会话开头强制注入，硬上限 ~2000 字符
INDEX / 目录树    ← agent 按需决定读哪个主题
topics/*.md       ← 细节，按需 read_file
```

**`MEMORY.md` 的字符硬上限是真约束，不是建议。**
它每次会话都要付注入成本，一旦放任它膨胀，每个会话的有效上下文都被挤掉一块。
细节全部下沉到主题文件，`MEMORY.md` 只留"我是谁、当前授权、去哪找东西"。

同理：运行时召回出来的相关经验**只做运行时注入，绝不回写 `MEMORY.md`**。

## 4. Onboarding 接口：让任意 agent 三十秒内会用

仓库要能被"任何一个未来的 agent"接手，就必须有一份显式的入口协议，而不是靠读者自己摸索目录。

一套可用的五步流程：

1. 读 `AGENTS.md` — 这是什么仓库、核心约束、目录地图、怎么贡献
2. 读 `INTERFACE.md` — 本流程本身 + 写入决策树 + 出错怎么办
3. 读 `MEMORY.md` — 身份、当前授权级别、时区与静默窗口
4. 读 `archive-policy.md` — 你写下的东西会不会被删
5. 按当前任务相关度，**选择性**读主题文件（不要一次读完）

配一个自检清单收尾（"我知道当前授权级别""我知道一键降权的命令""我知道脱敏脚本怎么用"）。

**硬规则：没读过归档策略之前，不允许写入新内容。** 否则第 2 节的分级形同虚设。

再配一棵写入决策树，消除"该写哪"的犹豫：

```
临时日报 / 调试输出 / 通知？        → short-term
工具约定 / 偏好 / 活跃目标？        → long-term（默认）
身份 / 核心决策 / 里程碑 / 教训？   → permanent
不确定？                            → long-term
```

## 5. 十年视角带来的格式约束

如果目标寿命是 5～10 年，很多"现在很方便"的选择会变成负债：

- **纯文本**：只用 Markdown + YAML + JSON。禁止 SQLite dump、protobuf、二进制 blob、模型权重、视频。二进制文件十年后未必还能打开，也无法 diff、无法 review。
- **零云端依赖**：不依赖任何 SaaS CI、托管数据库、平台专属功能。自动化一律走本地 pre-commit hook + 仓库内的纯脚本。平台会变，纯文本不会。
- **稳健命名**：全小写 ASCII kebab-case，日期前缀统一 `YYYY-MM-DD`；不用驼峰、不用中文目录名、**文件名里不带版本号**（`v2-xxx.md` 是反模式——版本属于 git，不属于文件名）。中文标题放 frontmatter。
- **大文件走指针**：超过体积阈值的数据集用对象存储 + 一份 manifest 指针文件，仓库里只存"去哪找"。
- **第二 remote**：单一代码托管平台是单点故障（账号、政策、可达性）。建仓当天就配一个异地 mirror，并且每年真做一次恢复演练——没演练过的备份等于没有备份。

## 6. 统一 frontmatter

每个 `.md` 头部一段 YAML，字段少而稳定：

```yaml
---
id: <稳定 slug，永不修改>
title: "一句话标题"
created: YYYY-MM-DD
updated: YYYY-MM-DD
type: note|decision|journal|reference|project|convention
source: human|<agent 名>
permanence: short-term|long-term|permanent
confidence: low|medium|high
status: draft|reviewed|archived
---
```

两个字段值得单独说：

- **`id` 永不修改**。文件可以改名、可以移动，引用靠 `id`。
- **`confidence` 必须诚实**。AI 推测出来的内容标 `low`，实测验证过的标 `high`。把推测标成 `high` 会污染整棵树——后来的 agent 无法判断哪条可信，最终只能全部不信。

---

## 7. 多仓库并存与收敛

现实往往是：每个 agent（不同 CLI、不同厂商）各自建了一个记忆仓，内容大量重叠、互相矛盾。

处理原则：

- **合并时"读完后重写"，不是 `cp -r`。** 重复内容只保留结论，不保留第二份拷贝。
- **冲突时取更严格、更新、可复现的那一份判决**，并在结论里写明"历史上曾经是 X，现在是 Y"。
- **做一份显式的来源映射表**（旧仓 → 新仓的哪个主题文件 / 为什么跳过），否则半年后没人知道某条结论是哪来的、有没有被吸收干净。
- **合并不等于删除**。旧仓保持原样，不删除、不改名、不 force-push；归档与否留给人类拍板。

## 8. 让记忆产生闭环：预测 → 到期 → 复盘

纯"写下来"的记忆是被动的。要让它真正改变 agent 的行为，需要一个数据驱动的闭环，而不是指望模型"自己反思"。

一个轻量实现（单用户级别数据量，SQLite 三张表足够，不需要向量库）：

- `episodes`：经验条目，`kind ∈ {learned, mistake, prompt_pattern, preference}`，带 `salience`（1–5）、`use_count`、`superseded` 标记
- `predictions`：可验证的判断，带 `confidence` 和 `horizon`（到期时间）
- `recall_log`：召回记录，用于事后评估召回质量

闭环怎么转：

1. agent 对某事做出**可验证**判断 → 登记一条 prediction（必须带置信度和时间窗）
2. 到期 → 定时任务列出待验证项 → agent 去找真实结果 → resolve
3. 判错 且 给出了调整方案 → **自动**插入一条 `kind=mistake` 且 `salience` 拉满的 episode
4. 下次同领域冷启动时，会话开头的注入块把这条 "别再犯" 捞出来

关键在第 3 步的"自动"：它不依赖模型自觉复盘，所以模型不会"漂移性地忘掉自己判错过"。

召回打分可以非常朴素，全表扫 + 内存排序即可：

```
score = 0.40 × 关键词重叠
      + 0.25 × salience/5
      + 0.25 × 时间衰减（半衰期 ~21 天）
      + 0.10 × (1 - e^(-use_count/3))    # 命中越多越可信，但饱和
mistake 类额外 +0.15
```

**首次部署踩到的四个坑**（都属于"设计时想不到、上线两周内必然遇到"）：

1. **自动收割重复**：高频出现的运维类事件会被反复写成近似重复的 episode。对策：去重哈希 + 低 salience，并且**首次不要回填历史**（先跑 1 天窗口观察两周，不要一上来 `--days 90`）。
2. **宽话题召回漂移**：用一个宽泛关键词做召回，会把所有沾边的条目全捞出来。对策：加 `kind` 限定；在没加之前，接受"宁滥勿空"以避免冷启动空跑。
3. **CLI 参数与文档对不齐**：由 agent 生成的 README 与实际 argparse 常有出入（参数名、未实现的选项）。对策：文档以 `--help` 实际输出为准，并把自测命令写进文档。
4. **字节 vs 字符**：注入预算按字符数截断时，UTF-8 中文一个字符三字节，实际字节数会超预算。明确按字符算，并接受这个偏差。

## 9. 明确写下"不放这里"

一份 negative list 的价值不低于目录结构本身。建议逐条写死：

- 任何密钥 / API key / cookie / 账号凭证 —— 哪怕只是"测试一下"
- 原始会话 JSONL、工具结果 dump、模型缓存
- 实盘资金量、绝对盈亏金额、持仓明细（需要时用区间或比率替代）
- 内网地址、主机名、账号名等基础设施指纹
- 他人的私人对话
- 半成品代码产品（代码归代码仓；记忆仓只存决策和教训）
- 超过体积阈值的二进制

并配一组可量化的健康指标，每月自查：每月提交次数、inbox 积压篇数、是否有密钥泄露、是否有超大文件误提交、每年至少一篇年度总结。

---

## 10. 一页纸小结

| 主张 | 反面案例 |
|---|---|
| 存结论，不存流水 | 记忆仓 99% 体积是会话日志，没人读 |
| 三档分级 + frontmatter 标注 | 身份信息被自动清理任务删掉 |
| 注入层有硬字符上限 | `MEMORY.md` 膨胀，每会话都在付税 |
| 显式 onboarding 协议 + 写入决策树 | 每个新 agent 自己摸索，写得乱七八糟 |
| 纯文本 + 零云端 + 异地 mirror | 平台变更 / 账号问题导致十年资产归零 |
| `confidence` 诚实标注 | 推测被当成结论，整棵树不可信 |
| 预测-到期-复盘闭环 | agent 靠"自己反思"，结果漂移性遗忘 |
| 明写 negative list | 密钥和隐私从原始日志里漏出去 |
