# Agent 授权、委派与"别碰生产"

让 agent 更自主，收益是真的；风险也是真的。
把"要不要放权"当成一个 yes/no 问题会两头受损：要么每一步都问、失去自主的意义；要么全放开、迟早出事。

正确的形态是**分级 + 兜底 + 少数永远需要确认的动作**。

---

## 1. 授权阶梯 L0–L3

| Level | 含义 | 何时进入 |
|---|---|---|
| L0 | 只读 / 只回答 | 默认起点 |
| L1 | 读 + 写本地，不进版本库 | 显式授权 |
| L2 | L1 + 可 commit，不 push | 显式授权 |
| L3 | L2 + 自动 push + 自动跑定时任务 | 显式授权，且四项兜底全部就位 |

阶梯的价值在于它**分离了"写"和"发布"**。L1/L2 让 agent 可以充分工作、留下可审的 diff，但错误不会扩散出本机。绝大多数提效来自 L1→L2，而不是 L2→L3。

### 四项必备兜底（L3 的前提）

1. **一键降权**：一条命令 / 一句指令把授权文件立刻改回 L0。这个开关必须简单到在慌乱中也能用对。
2. **熔断器**：单日自动动作失败次数超过阈值（比如 5 次）自动暂停到次日零点。防的是"错误的自动化以高频重复犯错"。
3. **审计日志**：所有自动动作按天写入结构化日志，保留固定周期（比如 90 天）。没有审计日志的自主等于没有自主。
4. **静默时段**：约定时段内不主动推送（critical 除外）。不做这条，自主 agent 会变成 24 小时骚扰源，然后你会把它整个关掉——这是"全有或全无"陷阱的另一种死法。

### 始终需要人类确认的动作

不管当前在哪一级：

- 删文件 / 删分支 / 删定时任务
- 修改授权配置文件本身
- 触碰 secrets 目录
- `git push --force`
- 关闭任何一项兜底机制

这份清单的共同点是**不可逆或会破坏防护本身**。

## 2. "无限自主研究"是个陷阱

一种很诱人的配置：给 agent 一套"永不停止"的硬约束（禁止说"任务已完成"、强制 OBSERVE → HYPOTHESIZE → EXPERIMENT 无限循环），让它自己一直研究下去。

**实测结果是它制造停滞感，而不是产出。**

机制很清楚：无限循环没有验收点，所以永远不会进入"执行"阶段。agent 会不断产生新假设、新方向、新框架，每一个看起来都比"把上一条线做完"更有吸引力。几个月后你会有几十份研究报告和零条上线的结论。

替代方案：**用有限的、带验收闸门的协议**（例如"必须通过 N 个独立视角的交叉验证才能标记为已验证"），跑完就停、出结论、进入下一阶段。自主性体现在"不打断地跑完一个协议"，而不是"永远不停"。

## 3. "你决定"是显式委派，不是"随便"

当人类说"你决定"时，它的含义是**把决策权交出来**，不是"给我列选项"。

- **正确**：给出推荐 + 理由（一两句）+ 立即执行 + 事后简短报告
- **错误**：收到"你决定"之后列三个选项让对方选 —— 这直接违背了委派意图

同理，"自主研究，不要打断"意味着：

- 遇到错误先自己尝试解决；解决不了就记录，跳到下一项，不要停下来问
- 一个阶段结束后自动进入下一阶段
- 不问"要继续吗""下一步做什么""要保存结果吗"

**只有这几种情况才停下来问**：需要人类授权的危险/不可逆操作、彻底卡死无法继续、人类明确要求停止。

## 4. 绝不修改用户的"活"环境

这是从一次真实事故里抽出来的铁律，而且随着 MCP / 外部工具接入变多，它只会越来越重要。

**场景**：用户装了一个第三方工具的 MCP，说"你写个策略，看看回测结果来调整"。
当前打开的那个工作区，是用户的**实盘环境**——有真实仓位、真实告警、他信任并依赖的自定义指标布局。
agent 直接在上面加策略、画线、切周期。用户不得不打断："那是我的实盘，你重开一个窗口自己研究。"

**为什么严重**：对活环境的任何修改都可能打乱用户的分析、与他挂着的告警/订单冲突、或者搞乱一套他依赖的视图。恢复成本远高于你节省的那点时间。

**如何应用**（可推广到任何第三方工具集成）：

- 任何**会改变状态**的调用之前，先确认目标环境：这是生产/实盘，还是专门给我的研究环境？
- 默认动作是**先切到一个明确命名的研究环境**，再开始工作。很多用户愿意专门建一个给 agent 用的沙箱——但你必须先问，不能假设默认标签页是安全的。
- **把工具报错当成信号**：某些受保护的目标在被改动时会返回特定错误。这不是"重试就能过"的瞬时故障，是"你碰错地方了"。**不要重试，换环境**。
- **不要相信布尔返回值**。"已添加"返回 `true` 不等于真的生效在你以为的那个目标上。用状态查询接口核对实际结果（例如按名称校验当前加载的是哪个布局），再继续。
- **用提交进仓库的脚本，不用一次性内联命令**。超长内联代码难以复现、难以审计，超时中断后也说不清做到哪一步了。
- 任务结束后把结果更新进该集成的操作记录文件，下次不用重新摸索。

## 5. 把大体量编码委派给另一个 agent

当规划/架构能力和编码额度不在同一个模型上时，分工是划算的：**主 agent 负责规划、架构、接口契约、任务拆分、验收；把实现交给一个可无头运行的编码 agent。**

实测可行的形态：

- 主 agent 产出文档（架构、API 契约、开发指南）+ 一批**任务卡**。每张卡是一个可独立完成的小目标，写清楚目标 / 范围 / 验收标准 / 可移植的参考实现。
- 一个包装脚本：给每张卡的 prompt 注入"必读文档 + 铁律"前缀，再调用编码 agent（无头模式，自动批准命令，指定工作区）。
- 一个队列脚本：按编号依次跑任务卡，成功则自动提交并移入 done 目录，失败即停。

**最关键的那个坑：不要用 exit code 判断成功。**

无头编码 agent 撞到账号会话额度上限时，会**退出码 0 但什么都没做**。如果按 exit code 判定，队列会一路"成功"跑完，实际零产出。

正确判据是 **git 是否检测到真实文件改动**。没有改动就判失败并停止；额度恢复后重跑即可。

其他经验：

- 让任务卡引用"**已验证过的可移植实现**"能大幅提升质量和速度——比任何 prompt 技巧都有效。
- 队列用后台运行，完成后通知；然后**逐卡人工验收**（跑测试 / build / 冒烟），不要相信"全绿"就交付。
- 不同 agent 共存时注意别互相覆盖各自的配置目录。
- 不要假设另一个 agent 写过什么，先列目录 / 看提交历史确认。

## 6. 不要直接采信子 agent 的报告

这条值得单列，因为它反直觉：派出去的 subagent 会给你一份自信、结构完整、看起来很专业的报告，而其中一部分结论是错的。

纪律：

- **子 agent 的结论必须由主 agent 自己复现**，尤其是任何"我验证通过了"。
- 并行派多个 subagent 做代码审查时，汇总后要**甄别**：剔除 agent 自己后来撤回的、被代码里的不变量本来就保护住的、以及纯风格性的。剩下的才由主 agent 亲自修。
- 报告里给出的数字（测试通过数、性能提升、命中率）默认当作**待验证**，不是事实。

## 7. 工具选择的成本心智

和多个订阅制 agent 工具并用时，成本结构直接影响工作方式，值得写进记忆：

- 不同工具的"默认/自动"模式通常路由到厂商自家的便宜池，额度宽松；显式指定高端模型会走另一个计费池，消耗极快。
- 把**大体量、低创造性**的任务放在便宜池（批量整理、索引重建、格式迁移、压缩总结）。
- 把**需要判断力**的任务留给强模型（架构、验收、取舍、写结论）。
- 某些 CLI 在特定订阅模式下不接受显式指定模型参数——但订阅本身已经覆盖了目标模型，直接用默认即可。遇到参数被拒先查订阅模式，别去改代码。
- 云端委派经常撞超时。超过一分钟的任务自己做，只把短任务外包。

这些具体数值会过期，但**"把额度当成一种要主动调度的资源"**这个心智不会。
