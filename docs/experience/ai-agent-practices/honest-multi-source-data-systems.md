# 多源数据系统的诚实性工程

把一堆可用性参差的数据源聚合成一个面板 / 控制台，是 AI 辅助开发下最常见的项目形态之一：
每个源都是某次研究留下的半成品，有的在线、有的挂了、有的口径完全不同。

这类系统里，**崩溃类 bug 很好修；真正的隐患是语义层面的静默撒谎**——不同口径的数据被同一个 UI 标签渲染成"看起来是同一个指标"，悄悄误导使用者。这类 bug 不报错、测试测不出来，而且恰恰最损害一个"诚实数据产品"的可信度。

---

## 1. 架构骨架：BFF + adapter + 优雅降级

对"聚合多个本地/远程数据源"类项目，这套结构实测有效：

### 同源 BFF 代理

前端只和自己的后端 `/api` 同源对话，后端再去调上游。

好处有三个，第三个最容易被忽略：
1. 彻底绕开上游的 CORS（服务端到服务端没有 CORS）
2. 统一鉴权、限流、缓存的落点
3. **凭据和内网地址留在服务端，不下发到浏览器**

### 每个数据源一个 adapter，且必须带 `health()`

统一接口，互不耦合。**先给每个源写探活，再写功能**——顺序反过来的话，你会在功能开发到一半时才发现某个源根本连不上，而那时已经有一堆代码假设它可用。

### 优雅降级是第一原则

上游挂了 / 超时 / 返回空，一律返回：

```
200 + { data: null | [], meta: { available: false, note, source, fresh_at } }
```

**绝不返回 5xx。** 5xx 只保留给 BFF 自己的 bug。

前端根据 `meta.available` 渲染"未就绪"占位，单个源挂掉不拖垮整页。

这条设计的真正回报在后面：**当上游陆续起来时，面板零改动自动点亮。**

### 统一响应外壳

```
{ data | items, meta }
```

`meta` 必带 `source` / `available` / `note` / `fresh_at`。前端永远先看 `meta` 再决定怎么渲染。

后面第 2 节会说明，`meta` 里还要带 `window` / `basis` 这类口径字段。

### 主源 + 兜底 + 单飞缓存

主源（远程 API）为空时回退到本地副本（例如列式文件）。缓存要合并并发请求（single-flight），但——

**降级结果只做很短的缓存（数秒级），绝不长缓存失败状态。** 否则上游恢复了，你的面板还要黑好几分钟。

### 实时流要去重

上游 WebSocket 订阅的首帧常常是历史快照。每次重连都会重放一遍。
必须按唯一键（成交哈希、事件 id）去重，否则**陈旧数据会被当成实时数据刷屏**——而且看起来一切正常。

## 2. 跨源语义诚实：真正的隐患在这里

以下几类问题都**不报错**，但都是真 bug。它们来自一次对真实面板的深度审查：

### 同名指标，两套口径

同一个"多空比"指标：主源算的是"近 4 小时高评级持仓倾向"，兜底源算的是"近 14 天开仓名义额之比"。
主源挂掉切到兜底时，UI 上这个数字**无声地跳变**，标题一个字没变。

**修法**：响应里带 `window` / `basis`，UI 标题动态拼出当前口径（"多空比（近 4h · 持仓倾向）"）。

### 两个不同的"宇宙"被同一个榜单展示

排行榜主源是实时追踪的一批对象，兜底源是历史打分库里另一批对象。
如果有"精选 / 关注"逻辑取 `leaderboard[0]`，切源时会**整批换人**，而用户以为是排名变化。

**修法**：切源时前端必须显式提示，不能只靠一个小圆点。

### 评分口径不一致，且与文案不符

同一个"评分"，一处用线性归一（被极值/异常大值挤压，大部分样本挤在低分区），一处用排名百分位，而免责声明里写的是"百分位"——**文案是假的**。

**修法**：统一成排名百分位，让文案变真。文案和实现必须对齐，不对齐时改实现或改文案，不能留着。

### 陈旧数据当实时

状态面板读取一份列式文件的最后一行当"当前状态"，但那份文件由外部离线批量任务生成，实测已经陈旧 37 小时，UI 上不显示任何时间。

**修法**：后端计算 `stale` / `age` 并暴露 `fresh_at`；前端显示数据时间 + 陈旧角标。
**而且——承诺了"显示 fresh_at"，就要每个面板都真落地**，不能只做一半。

### 诚实性不是一次性声明，要每次渲染强制

如果系统有一个"总体判定"（例如某个策略是否达到可交易门槛），那么当判定为否时，**逐行的绿色 ✅ 必须被否决、降级为"仅供参考"**。

一个绿色 ✅ 比一整条免责横幅更有暗示力。横幅是一次性声明，✅ 是每行都在重复的隐含承诺。

## 3. 语义审查：把它做成一道独立工序

**评审这类项目时，专门跑一遍"语义审查"，不只找崩溃。**

对每一个展示出来的指标，强制问三个问题：

1. **口径 / 窗口是什么？**
2. **数据多新？**
3. **跨源切换时含义变不变？**

后端的责任：忠实带上 `source` / `window` / `basis` / `fresh_at` / `verdict`。
前端的责任：**绝不**把不同口径渲染成视觉上同一个指标。

## 4. Mock 全绿 ≠ 正确

一个实测数据点：**57 个 mock 测试全绿，但只有真实数据探测才暴露出真问题**——评分分布被异常大值挤压（第二名只有 71 分）、状态数据陈旧 37 小时、WebSocket 混进了不该有的市场噪声、重连快照重灌。

原因很直接：**mock 测的是"代码按我的假设运行"，测不出"假设本身是错的"** —— 上游真实的数据形状不同、语义不对、有 NaN / 空值 / 噪声泄漏。

### 纪律

1. **mock 单测 / 集成测负责契约与降级路径**（离线可全绿、CI 友好）。
2. **另外跑一轮真实数据探测**，核验四件事：
   - 关键计算值合不合理（亲手对比，比如评分分布本该均匀就不该被极值挤压）
   - 数据多新（`fresh_at` vs `now`）
   - 跨源语义对不对
   - 有没有 NaN / 空值 / 噪声泄漏到前端

   探测方式可以很土：直接 `curl` 打 BFF + 脚本解析，看真值。

3. **代码审查分两遍**：
   - 第一遍找崩溃 / 资源泄漏 / 并发（行级 bug）
   - **第二遍专门找架构与功能逻辑**：设计是否自洽、功能是否真的实现了它声称的、跨源语义是否一致、新鲜度与口径有没有误导

   两遍可以派并行 subagent 各管一块（后端核心 / 路由服务 / 前端），主 agent 汇总后甄别（剔除 agent 自己撤回的、被不变量本就保护住的），再亲自修。

4. **修完要实测对比修复前后的真值**，确认生效（评分从 71 变 98、`fresh_at` 从空变成显示时间）。

### 能力边界要诚实告知

环境里没有无头浏览器时，前端只能做"语法检查 + 逐页数据形状对照真实 API + 静态审查"，**做不了真正的浏览器回归**。
这件事必须主动告诉使用者，而不是让"审查通过"四个字暗示比实际更强的保证。

## 5. 证据优先：给决策系统的一层额外约束

如果这套数据系统要喂给一个自动/半自动决策流程（尤其是有 LLM 参与的），还需要几条更硬的约束：

- **任何观点必须建立在可记录、可回放、可验证的证据上。** 不允许仅凭自然语言直觉产生决策。
- **证据管道优先于智能管道**：数据 → 特征 → 证据 → 状态 → 触发 → 分析 → 论点 → 挑战者 → 风控 → 执行 → 复盘。确定性的层（特征 / 状态 / 触发 / 风控）要能严格回测；LLM 只是"分析师"，输出论点而非指令。
- **论点不能直接触发动作**，必须经过一个独立的挑战环节、入场前重校验、和一个**确定性的**风控层。风控层拥有最终权限，LLM 无权绕过。
- **证据要分级标注来源**：直接观察 / 派生 / 模型估算 / 不可得。由模型推断出来的东西不得伪装成一手观测数据。
- **按信息源分组，而不是堆叠指标。** 十个指标如果都是同一条价格序列的单调变换，它们不是十个证据，是一个。要显式给出"有效独立信息源数量"，否则会在趋势末端产生**虚假共识**。
- **对 LLM 层来说，历史回放不构成有效证据。** 模型的训练数据里包含了未来路径，让它"回测"过去的行情本质上是在测记忆力。有效结论只能前向积累。
- **PnL ≠ 决策质量。** 要测量被拒绝的决策的反事实结果，否则无法区分"风控起作用了"和"风控挡住了赚钱机会"。
- **系统必须赢得行动权**：数据可靠 → 证据有信息价值 → 模型正确使用证据 → 挑战环节提高质量 → 风控限制尾部 → 执行无灾难性错误，逐级解锁，每级都有验收。

这套范式的代价要摊开讲清楚：工程成本前置（日志、哈希链、异地 checkpoint、恢复演练都要先于任何"策略"代码）、时间成本高（前向积累可能需要一两年才有弱统计结论）、而且**最可能的结论是"LLM 层没有可测量的边际贡献"**。所以架构必须保证：即使 LLM 层被证明无用，确定性层本身仍有独立价值。

## 6. 共享基础设施上的操作纪律

多个项目共用一套生产设施时（共享数据库、共享节点），有几条纪律是用故障换来的：

- **给了访问权 ≠ 可以随意改别人的项目。** 接口或数据缺失，优先**在自己这一侧降级处理**，不要去重构别人的管道。
- **但自己触发或加剧的故障必须负责恢复。** 因为自己的操作间接让共享数据库进入僵死状态，就应该把它救回来（取消僵死查询、修根因），而不是放着不管。
- **重型只读分析查询会拖垮共享库。** 动手前评估负载；必要时只取轻量数据，不要触发全量加载。

一个具体且极易重犯的技术坑：**大表排序把临时空间写爆**。
对一张上亿行的表做多遍扫描 + 排序，数据库的临时文件默认写在系统盘，盘满 → 任务永久挂起 → 拖垮整库。
修法是建一个临时表空间指向空闲的冷盘，并且用**全局级别**的设置（`ALTER SYSTEM` + reload）——按角色或按库设置的参数对连接池里的常驻连接**不生效**，这是最容易踩空的一步。
救僵死则是取消那些 `state='active'` 且已运行超过数分钟的查询（正常查询是亚秒级的）。
