# 多站点汇聚看板的设计取舍

当你有 N 个物理站点，每个站点里都跑着一套自己的本地监控系统，而你想在一块屏上看到全局——这就是"汇聚看板"这类系统要解决的问题。它看起来很简单（不就是把数字加起来吗），但几乎每一个默认选择都是错的。

下面是从一套真实的多站点汇聚看板里提炼出来的设计结论，全部与具体业务无关。

---

## 一、先划清楚边界：云端只做总览

第一条也是最重要的一条决策，是**明确云端不做什么**：

- **云端只是总览**：每个站点的运行概况（在线数、总产能、功耗、告警计数、归属方汇总），分钟级粒度。
- **运维操作、完整历史、对账原始数据都留在站点本地。**

这条边界一旦模糊，汇聚层会迅速膨胀成"第二套监控系统"，然后你要同时维护两套口径不一致的东西。

### 推论：云端对站点**只读，无反向通道**

写进设计原则并且明确禁止未来扩展：

> 推送模式下云端连站点的地址都不知道；即使云端被攻破也无法触碰任何现场设备。**永远不要往这个项目里加"下发命令"类功能**——那属于站点本地系统。

这是一条安全属性，但它是**靠架构保证的，不是靠权限配置保证的**：云端根本没有到站点的网络路径，所以"云端被攻破"这个事件的爆炸半径被物理地限制在了"数据被看到"。

---

## 二、推送优于拉取

| 模式 | 方向 | 站点要求 | 配置在哪 |
|---|---|---|---|
| **推送（推荐，默认）** | 站点 → 云端 | 无：NAT 后面即可，不需要端口映射 | 站点本地 |
| 拉取 | 云端 → 站点 | 云端必须能访问站点（公网 / 端口映射 / 内网穿透） | 云端 |

现场站点通常在 NAT 后面、网络条件不稳定、由非技术人员运维。**要求现场做端口映射是一条会在每次新站点接入时都卡住的路径。**

推送模式下，站点只需要在自己的配置里填云端地址和一个令牌，**第一次上报就自动出现在云端面板上，云端不用改任何配置**。这让"接入一个新站点"从一次运维协作退化成一次本地配置修改。

三条配套设计：

1. **两种模式产出同一张表的行，查询层不区分来源。** 否则你会写出两套查询逻辑，然后它们慢慢分叉。
2. **上报线程完全独立**，失败只打日志，绝不影响站点本地的扫描和告警。汇聚层挂掉不能拖垮现场。
3. **断网期间上报自动中断，恢复后自动续传**，站点侧不需要人工干预。

---

## 三、身份：稳定 ID 是主键，显示名只是标签

这是最容易在上线半年后才付出代价的一条。

- **数据主键是站点 ID**（站点本地首次运行时自动生成并持久化到一个文件，或显式指定）。
- **站点名只是显示标签，随时可改、改名不丢历史数据。**

如果拿名字当主键，任何一次"某某一场改叫某某基地"都会把它的历史切成两半，而且你没有办法把它们接回去。

两个配套细节：

- **克隆目录部署新站点时必须删掉那个 ID 文件重新生成**，否则两个站点会共用同一个身份，数据互相覆盖。这一条要写进部署 SOP 的显眼位置。
- 兼容旧版本上报（没有 ID 字段）时回退用名字当 ID，并在数据库连接时做一次性自动迁移。

---

## 四、不信任站点的时钟

**入库时间戳一律用汇聚端的时间**，不用上报里携带的站点时间。

现场机器的时钟漂移是常态（有的从来没配过 NTP，有的时区设错）。一旦用站点时钟做趋势图的横轴，你会看到未来的数据点、重叠的数据点，和无法解释的空洞。

代价是失去了"这个读数在站点侧是什么时候采的"这个信息——所以**站点侧的采集龄期要作为一个独立字段上报**（见下一节）。

---

## 五、状态语义必须分清四种，不能只有"在线/离线"

| 状态 | 条件 | 含义 |
|---|---|---|
| ● 正常 | 数据正常且无告警 | |
| ⚠ 告警 | 站点本地活跃告警 > 0 | 站点在工作，但现场有问题 |
| ⏸ **监控停滞** | 站点本地上次采集龄期超过阈值 | **站点在上报，但它自己的采集进程可能死了** |
| ✖ 不可达 | 超过 N 个上报周期没收到上报 | 断网 / 断电 / 服务挂了 |

第三种状态是这套设计里最有价值的部分。**"站点还在上报"和"站点的数据是新的"是两件完全不同的事。** 一个采集线程死掉但上报线程还活着的站点，会持续推送一份永远不变的旧数据上来，在只有两态的设计里它会一直显示绿色。

而这正是《监控系统的运维陷阱》里"屏幕绿油油其实早瞎了"那一条在汇聚层的对应版本——**汇聚层的存在让这个问题变得更严重，因为它多了一层可以独立存活的传输**。

### 不可达期间显示"最后已知数据 + 数据龄期"

不是空白（丢失信息），也不是照常显示（撒谎），而是**灰显 + 标注数据龄期**。恢复后自动回归正常。

### 汇聚层能发现本地发现不了的事

站点断电时，站点本地的监控系统也死了——**本地告警根本发不出来**。只有汇聚端能发现"整场失联"这件事。这是汇聚层除了"看全局"之外的第二个存在理由，值得单独作为一类告警对待。

---

## 六、令牌分权：写入与读取分开，一站一把钥匙

三类令牌，职责严格分开：

| 令牌 | 权限 | 泄漏后果 |
|---|---|---|
| 上报令牌 | **只写**（POST 上报接口） | 攻击者能往里灌假数据，但读不到任何东西 |
| 查询令牌 | **只读**（给自动化/Agent 取数） | 能读，但改不了任何东西 |
| 管理会话 | 读 + 管理操作 | 人工登录，短会话 |

两条关键推论：

1. **上报令牌和查询令牌必须是不同的值。** 合成一个"API token"是最常见的偷懒，代价是任何一方泄漏都同时丢掉读和写。
2. **每个站点发一把专属上报钥匙**（映射表：站点 ID → 令牌）。一个站点的钥匙被攻破，只作废那一把，不影响其他站点，**而且攻击者也无法冒充别的站点上报**。用一把全局钥匙的话，一台现场机器被拿下等于所有站点的数据都可以被伪造。

配套的接口纪律：

- 上报接口**只进数据且数值做钳制**（越界值直接夹到合理范围或拒绝），令牌错一律 401。
- 秘密字段在任何查询接口的响应里**一律掩码成布尔值**（"已配置 / 未配置"），永远不返回明文。异常文本在打印前也要过一遍掩码，否则会绕过接口层的掩码。
- 另提供一个**免登录的健康端点**给外部看门狗探活，**不含任何业务数据**。

---

## 七、配置分层：出厂默认 + 运行期覆盖层

主配置文件只在进程启动时读一次——改它必须登服务器改文件 + 重启。但有一类参数（通知渠道设置之类）管理员希望"在浏览器里改完立即生效、且重启后还在"。

做法是加一层覆盖：

```
主配置(出厂默认，改需重启) ──启动时合并──▶ 运行期配置
                                              ▲
覆盖文件(网页保存，覆盖同名字段) ──每次保存落盘──┘
```

四条必须注意的实现细节，每一条都对应一个真实的坑：

1. **覆盖文件不入版本库**（和主配置、数据库同一条忽略规则）。代码更新永远不会碰它。
2. **原子写**：加锁做"读-改-写"，先写临时文件再 `os.replace()`。两个管理员并发保存不会互相覆盖，进程崩在写一半也不会留下半截 JSON。
3. **深合并进原字典，不要整体替换。** 如果后台线程持有的是同一个字典对象的引用，`cfg["x"] = 新dict` 会让它继续读到旧对象——这个 bug 的症状是"网页上显示改成功了，但实际行为没变"，极难排查。
4. **首次运行没有这个文件是正常的**，读不到就返回空字典，全部按出厂默认走。不要因为文件不存在就报错或崩溃。

---

## 八、存储与查询：明细短保留，汇总永久保留

数据量本身很小（N 个站点 × 每天 1440 行），所以架构可以简单（单进程 + 嵌入式数据库 + 原生前端就够，十年内不需要更重的东西）。但保留策略必须从第一天就想清楚：

- **分钟级明细**按保留期（例如 30 天）定期清理。清理用**分批 DELETE + LIMIT**，短锁，不卡住正在进来的上报。给时间列单独建索引，否则删除会全表扫。
- **日级汇总永久保留**。体积极小，而所有"长周期报表"都从它累加出来。

> 这条是《监控系统的运维陷阱》里"月底拿不到整月数据"那个坑的正解：**不要试图靠延长明细保留期来支持长周期报表，要靠归档汇总。** 明细保留期是运维参数，汇总表是业务需求，两者不应该耦合。

### 趋势查询在服务端分桶

按"时间范围 / 目标点数"计算桶宽，`GROUP BY` 取均值，**任意时间范围都返回固定数量（约 300）的点**。前端不做降采样。

好处是前端逻辑极简、网络传输恒定、切换时间范围的响应时间恒定。

### 断报时段留空，不要连线

趋势图在没有数据的时段**留空不连线**。用一条直线把空洞两端连起来，是在编造从来不存在的数据点——而这张图的读者会拿它做判断。

### 并发模型

单连接跨线程共享时，**所有写操作串行化**（一把模块级锁），读不加锁（WAL 模式下读写不互斥）。在这个数据量级上，简单和正确比并发度重要得多。

---

## 九、给自动化留一个只读接口

除了给人看的面板，单独开一组**只读 + 限速**的接口，用查询令牌鉴权，专门给自动化程序或 AI agent 取数做情况汇报。

把它和面板接口分开的理由：

- 权限模型不同（面板要登录会话，自动化要长期令牌）；
- 限速策略不同；
- 字段稳定性承诺不同——面板接口可以随 UI 改，自动化接口是契约。

---

## 十、上线前必改清单要放在 README 里，不是藏在部署文档里

任何自带默认口令和示例令牌的系统，都必须在**最显眼的地方**列出"上线前必须改的 N 件事"：

1. 改掉默认口令；
2. 换掉仓库自带的示例令牌（上报的和查询的都要换），并给每个站点发专属钥匙；
3. 公网部署必须 TLS + 安全 Cookie + 正确的反向代理信任配置。

并且——**示例配置里不要放任何可计算的真实哈希值**，哪怕它对应的是一个文档里公开写明的弱默认口令。那只是在给攻击者省一步。

---

## 一句话总结

> 汇聚层的价值不在于"把数字加起来"，而在于它是**唯一能发现站点整体失联的观察者**。所以它的每一个设计决定，都应该围绕"不要让它自己也变成一个会安静死掉的组件"。
