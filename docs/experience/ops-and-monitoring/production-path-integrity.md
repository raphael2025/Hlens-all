# 生产链路完整性：测试全绿，功能全死

一个数据处理系统跑了几个月，327 个测试全绿，面板上数字在动，没有任何报错。然后一次专项审计发现：**整整四类观测项从来没有被触发过一次**，两个状态在生产代码路径上根本不可能到达，预览功能的返回值永远是 `null`。

这份文档整理的是那次审计（以及后续几轮）找到的缺陷形态、它们为什么能躲过测试，以及后来加上的几道结构性防线。每一条都是真实发生过的。

---

## 一、最贵的那一类：测试验证的是 mock，不是现实

### 案例：生产者和消费者的字段名完全不重叠

上游模块发出的字段是：

```
cross_side / crossed_above / bars_since_cross / close_above_level_count / ...
```

下游模块读取的字段是：

```
side / accepted / rejected / bars_beyond / excursion_atr
```

**没有任何一个键是重合的。** 四个观测项全部永久为空，依赖它们的三个状态永远无法触发。

测试套件为什么是绿的？因为下游的单元测试**手写了一个用消费者字段名构造的字典**——一个生产环境从来不会产出的形状。测试验证的是"如果给我正确形状的数据，我能正确处理"，而真正出错的是"没有人给我正确形状的数据"。

> 这是"测试验证的是 mock，不是现实"的教科书形态。它的特征是：**消费侧的测试自己构造输入**。只要这个模式存在，生产者改名、改结构、改语义，消费者的测试都不会红。

### 三道结构性防线

1. **给跨模块契约一个显式的、带版本号的类型。** 上游只发"事实"，用一个带 `schema_version` 的具名结构承载；下游从事实**推断**结论。两边不再各自定义字段名。
2. **维护一张权威的"消费清单"。** 下游模块里有一个常量，列出它读取的所有上游输出项（本例是 30 项）。它的作用不是运行时用，而是让 schema 漂移**可检测**而不是静默。
3. **消费侧测试的输入必须由生产侧真实产出。** 哪怕代价是测试跑得慢一点。任何一个"测试里手写上游输出"的地方，都是一颗定时炸弹。

## 二、只在某条分支上到达的数据

### 案例：第二次调用才带上的那一半数据

两个数据源的定稿顺序是固定的（一个总是先于另一个），协调层因此对同一个时间片调用了引擎两次。第二次调用发现时间戳已处理过，于是以"不持久化"模式运行。

**而其中一个数据源的值，只会在那第二次调用里到达。**

结果：它的滚动基线永远是空的，衍生指标永远返回"历史不足"。而这个指标是两个状态的**硬性前置条件**，候选筛选会丢弃前置条件不满足的候选——于是这两个状态在生产上永远不可达。

实测 50 个时间片：一侧历史 50 条，另一侧 **0 条**。

> **通用检查项**：任何"第二次/重复调用走不同分支"的设计，都要问一句——**有没有数据只走那条分支？** 如果有，那条分支就不是"重复调用的优化路径"，而是主路径的一部分。

### 案例：预览路径结构性死亡

引擎的工作周期是 5 分钟，而运行时喂给它的是 1 分钟粒度的流，于是评估函数在第一行就返回了。预览字段永远是 `null`。

更值得记的是**它背后藏着的东西**：评估函数会把未定稿的快照送进选择与定稿逻辑，而那些逻辑会修改计数器、进入时间和冷却状态。

> **如果有人"天真地把周期改对"让它跑起来，每一次预览都会污染已定稿的状态。** 死代码被修活之前，必须先确认它修活之后是安全的——"它本来就该工作"不是安全性论证。

正确的做法是让预览跑在状态的**克隆**上，并且检查点只复制那些非持久化构建真正会修改的递归量。验收标准很具体：**在两个定稿点之间跑 100 次预览，内存指纹和状态历史与跑 0 次预览逐字节相同。**

## 三、语义反转与"打分对了、状态机丢弃了"

### 案例：符号方向弄反

某个距离指标的定义是 `(当前值 - 参考位) / 波动尺度`。**负值**意味着参考位在上方（即阻力）。代码里写的是 `> 0 → 阻力`，正好反了。

后果是两个：某个需要"阻力位上下文"的状态永远无法满足条件；而另外两个对称的条件项之间，加成被互换了。

> 这类 bug 不会让任何测试变红，因为测试通常用的是和实现同一套（错误的）理解写出来的。**防线是在定义处写下符号的含义并让它可执行**——例如在类型层面区分"有向距离"和"绝对距离"。

### 案例：打分器是对的，状态机把赢家丢掉了

诊断输出长这样：

```
当前状态=A   原因='状态维持'
  BLOCKED  状态X  score=91.8  entry=78  reqs=[]
  BLOCKED  状态Y  score=88.9  entry=64  reqs=[]
```

分数远超门槛，前置条件全部满足，却仍然 BLOCKED——因为**状态迁移图里从 A 到 X 根本没有这条边**。

这里值得学的是**分类纪律**：这被归类为"迁移粘滞"，而**不是**"打分语义错误"。两者的修法完全不同（一个改图，一个改打分），混为一谈会让人去修一个没坏的东西。

> 在一个有多层的判定系统里，**每一个"为什么没触发"都必须能归因到具体的某一层**。做不到这一点，调优就变成了撞运气。

### 案例：方向盲的指标被当成有方向的反证据

有一个"响应效率"指标的定义是 `abs(收益) / abs(流量占比)`——**它不携带方向**。但打分器把它当成某个状态的**反证据**使用，标签写的是"价格仍在强劲向上响应"。

于是在一次决定性的**向下**行情里，价格响应得很有效率，这个指标以 0.95 的强度触发，**从它本该支持的那个状态身上扣分**：

```
实际:  50 + 50×(2.14/3.7) − 40×(0.95/1.0) = 40.92   (门槛 72，不通过)
去掉方向盲的反证据: 50 + 28.92            = 78.92   (通过)
```

**修法里最值得抄的部分是它没有做什么**：没有随手找一个"看起来有方向"的替代指标。实际验证过两个候选替代：

```
买方流量 + 价格上涨  →  有向响应 +40, 对齐度 +1
卖方流量 + 价格下跌  →  有向响应 +40, 对齐度 +1
```

**两者在这两个指标上完全不可区分**——天真的替换会原样复现同一个缺陷。

最终的新观测项要求**四个事实同时成立**：流量方向、价格方向、两者对齐、幅度达标（复用既有阈值，不新增任何可调参数）。并且**镜像出一个反向观测项**，使得"上行读数"可以被报成"被反驳"而不是仅仅"缺失"。可用性是四个输入的合取——所以某个数据源缺失时它是"不可用"，永远不会被伪造成一个"否"。

### 剩下的同类用法：登记，但不动

同一个方向盲指标在另外 5 处也带着有方向的标签在用。审计的处理是**列成一张表登记下来，标注"未证实是缺陷，未改动"**，并说明为什么被修的那一处是唯一有害的：

> 它是一个**反证据**项，而它守护的那个状态，恰恰是在市场朝着标签所述的相反方向运动时才会进入的。

> **这是一条重要的审计纪律**：在一次以正确性为目标的改动里，只修被证明有害的，把可疑但未证实的登记成后续审计的候选。一次改太多，就再也说不清是哪一处修复起了作用。

## 四、两个结构性工具

### 可达性矩阵

把"每一个被声明的状态，是否真的能在生产代码路径上到达"当成一项验收，用合成输入驱动**真实的**聚合器、汇总、拼接、特征引擎、观测层、打分器和状态机走一遍。

结果表里三列：状态、是否可达、**它需要哪个修复才变得可达**。最后一列是这张表的价值所在——它把"我修了个 bug"翻译成了"这个功能从此存在"。

### 证据的四态模型

把"证据存在/不存在"这个二值模型换成四态：

| 状态 | 含义 | 是否降低覆盖度 |
|---|---|---|
| SATISFIED | 达到阈值 | 否 |
| NOT_SATISFIED | 指标健康，但没到阈值 | **否** |
| CONTRADICTED | 相反的读数触发了 | **否** |
| UNAVAILABLE | 指标缺失或过期 | **是** |

于是覆盖度的定义变成 `可评估的权重 / 总权重`——**"我能评估多少证据"，而不是"多少证据恰好触发了"**。

> 这个改动的意义一句话就能说清：**在二值模型里，"平静的市场"和"死掉的数据源"长得一模一样。** 四态模型把它们分开了。

配套的是快照要把"支持证据 / 反对证据 / 未满足 / 被反驳 / 缺失 / 不可用的前置条件"分开暴露，而不是合成一个数字。

而且要明确：**这次改动没有动任何打分数学**，只改了覆盖度（因而是置信度）和报告方式。把"改了什么"和"没改什么"都写清楚，是这类审计报告可信的前提。

## 五、崩溃与重启：默认它会在最坏的时刻发生

### 案例：重建窗口取整到了错误的粒度

初始化时把重建窗口的终点取整到**分钟**，但汇总引擎把每个父级桶锚定到它自己的周期边界。于是在 14:31 重启，读到的是 14:31 起的分钟级数据，却仍然产出锚定在 14:30 的 5/15/30 分钟桶——**用一个缺了第一分钟的子集构建，然后覆盖掉了原本正确的完整桶**。

实测：三个周期的某个桶各自恰好丢失了那一分钟的全部记录。源数据是完整的——**这是一次有损的重建，不是丢失的输入**。

第二条路径由崩溃测试本身发现：重启后，实时引擎用它**内存里仅有的那几个子项**定稿了一个桶。实测某个桶从 4833 条被重写成 1425 条（恰好是内存里那两个子项），而磁盘上它的子项加起来是 5450 条。两个版本都标着"不完整"，所以一道只保护"完整"数据的守卫放行了它。

### 防线 1：把重建窗口对齐到公共边界，并在启动时验证

起点取整到**所有已配置周期共享的边界**。这个周期是所有周期的**最小公倍数**推导出来的，不是硬编码的：

```
已配置周期  ('5m','15m','30m','1h','4h')  →  推导周期 14400s
只配 ('5m','15m')                        →  推导周期 900s
```

关键在于**这个推理在 import 时对真实的取整函数做验证**，用几个刻意刁钻的探针（包括闰日和年份边界）。如果某个周期组合没有公共边界，或者有人改了锚定方式使这个论证失效，**直接抛异常，import 失败**。

> **把一个数学论证变成一个启动期断言**，是防止"某天有人加了个 45 分钟周期"这类事故最便宜的办法。实测：加 45m 会把周期撑到 12 小时而不是静默失效；未知周期抛错；把取整锚点挪 7 分钟抛错。

### 防线 2：派生数据的覆盖度只允许增加

存储层拒绝任何会丢失信息的写入：

| 已存 | 写入 | 结果 |
|---|---|---|
| 任意 | 完整 | 接受 |
| 完整 | 部分 | **拒绝** |
| 部分 | 更少的部分 | **拒绝** |
| 部分 | 更多的部分 | 接受 |
| **规范来源数据** | 任意 | 接受 |

论证很干净：**汇总是对子项的纯求和，所以它变小只可能是因为看到的子项变少了。**

最后一行是必须的例外：规范来源数据不是由子项算出来的，它有合法的修复路径（用权威来源替换一条"完整但错误"的记录）。对它套用同一道守卫会静默阻止真实的修正——这一点是被回归测试抓到的。

### 防线 3：崩溃矩阵

确定性构造，无市场噪声：**9 个崩溃偏移 × 5 个时间位置 × 日界 × 6 个周期**。连续运行与重启运行的历史**逐字段比对**（开、高、低、收、各类成交量、计数、方向量、完整标志、时间戳……）。

> **把两道防线都关掉，59 个测试里 47 个失败。** 这个数字才是这套矩阵的价值证明——一个永远全绿的测试矩阵，和没有这个矩阵是一样的。

真实的 `kill -9`（在三个数据库都有 4MB 热 WAL 的情况下）验收标准是**刻意不对称**的：

```
没有记录丢失
没有已完成的记录被重写
没有记录丢失信息 → 部分覆盖损坏 = 0
崩溃中断的部分记录被恢复补全：4      （允许）
增长但仍不完整：2                    （允许）
没有汇总在完整状态下被重写，也没有缩小
```

崩溃会中断写到一半的记录，恢复过程**合法地**把它们补全。必须永不发生的是**反方向**。

## 六、延迟问题要测量，不要推断

用采样分析器（而不是猜测）确认：**一条调用链占掉了 19.3% 的进程时间**。

消费者是面板上的一个图表系列：两小时的时间序列，在每秒刷新的循环里**同步地从磁盘读取**。直接测量：每次调用中位数 292 毫秒。

### 修法是改数据流，不是降轮询频率

选了"进程内增量状态"而不是"把刷新间隔调长"。理由是**数据本来就已经在进程里了**：每一条定稿记录都会经过运行时的完成回调，而那个字段恰好在那一刻被写入且之后永不改变。

于是维护一个有界（窗口 + 少量余量）的内存序列，启动时用后台线程播种一次，**之后再也不读磁盘**。

三个值得抄的实现细节：

- 启动阶段的回填不经过回调，所以空播种要**每 30 秒重试一次直到有数据，然后永不再试**。实测：启动期 8 次空尝试，然后 119 个样本，然后彻底安静。
- **无语义漂移**：缓存与磁盘来源**逐字段断言相等**——在多个时刻、增量喂入时、追加实时读数后、以及重启重新播种后。
- 缓存保留了空值，因为原实现是**先截断再丢弃空值**的；提前丢弃会改变哪些样本能活下来。**性能优化不得移动任何一个数字**，这类顺序差异是最容易被忽略的一种移动。

### A/B 对照要只有一个变量

同一个墙钟窗口、同一份实时数据、同一套埋点，唯一变量是把那一个函数回退到旧实现（通过 `PYTHONPATH` 加载）。

| 指标 | 之前 | 之后 |
|---|---|---|
| 事件循环 p50 | 355 ms | **17 ms** |
| 事件循环 p99 | 419 ms | **21 ms** |
| 被判"循环降级"的采样 | **100%** | **0%** |
| CPU | 31% | **3.4%** |
| 启动期队列滞后峰值 | **314 秒** | 0.0002 秒 |

那个 314 秒的启动期队列滞后是**意外发现**：同步读盘不只是在阻塞事件循环，它还在**饿死消费者**。

同样重要的是明确**没有**修好什么：某个一次性的历史归档摄入在两个构建里都是 36 秒左右——它在对照组里同样存在，与本次改动无关，**不被声称为已修复**。

## 七、几条贯穿的纪律

### 门槛不能为了让灯变绿而调高

修好阻塞之后，进程不再每秒被卡住 350 毫秒，于是它跟得上了，有界结构填到了真实工作集，内存达到 1679MB，超过了配置的 1500MB 降级阈值。

**这个阈值是在一个被阻塞到跑不满的进程上标定的。** 审计的处理是：

> 这是绝对上限**正确地报告了一个真实事实**，不是内存增长的误报。**阈值没有被调高**——为了让灯变绿而调阈值，正是任务纪律明令禁止的。1500MB 是不是合适的上限，是所有者的容量决策。

### 越权发现的缺陷：记录、复现、根因、建议，但不修

最后一轮审计在自己的崩溃测试里发现了**第三个**缺陷（当天的派生数据在补数之后从不重新推导，因为重建窗口止于当天零点，而且整段逻辑被一个"本次是否写入了历史数据"的条件挡着）。

处理方式：

- 给出**测量证据**（某条链的偏移量精确到小数点后两位，跨两次重启仍然存在）；
- 给出**根因**（两行代码）；
- 给出**建议修法**，并标注"未应用"；
- 明确标注**这是既有行为，不是本次改动引入的**——它此前被更大的那个损坏掩盖着，现在损坏没了才显形；
- 最终裁定：**阻塞，不通过**。

> 在自己的测试里发现一个超出任务范围的真实缺陷，既不顺手改掉（会污染本次改动的因果关系），也不假装没看见（会让它永远埋着）。**记录 + 复现 + 根因 + 停手 + 如实裁定**，是这里唯一正确的动作。

### 冻结指纹

每一轮改动前后，逐一核对版本号与定义哈希未变，并在文档里列出来。

而定义哈希本身也修过一个洞：**它原先只哈希了阈值和迁移图，没有哈希"哪些观测项算作证据"**。于是改了证据规则而哈希不变，已持久化的历史快照就变得无法归因——你再也说不清某条历史记录是用哪一版规则产生的。

> **可归因性的要求是：任何会改变输出语义的东西，都必须进指纹。** 只哈希"参数"而不哈希"规则"，是这类系统最常见的归因漏洞。

### 优化不得移动数字

增量统计的实现与朴素实现在**3 种容量 × 3 种窗口**下逐一比对完全相等。有了这条证据，"优化"和"改了行为"才能被区分开。
